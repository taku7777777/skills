# コンテキスト経済スキル

Anthropic公式ドキュメント(Claude Codeのコスト管理・プロンプトキャッシュ挙動・ベストプラクティス・コンテキストウィンドウ)と、Claude Code利用コストの実測に基づく行動変容システムmetsukeの知見を統合した、セッション・コンテキスト・キャッシュの経済運用プロセス。数字の羅列ではなく「どの場面でどの操作を選ぶか」の行動変容を目的関数とする。

領分の境界: CLAUDE.mdやドキュメントの内容・体系の設計は `docs-for-ai` の領分(本スキルはサイズ・常駐コスト・反映タイミングだけを扱う)。タスクをどのモデル・どの委任形態に割り当てるかは `delegation-economy`、1回の依頼文の設計と迷走の早期停止は `prompt-economy`、利用費の計測基盤・指標・介入の設計は `llm-cost-observability` の領分。本スキルは「開いているセッションをいつ続け、いつ切り、どう離れ、どう戻るか」というセッションとキャッシュの運用判断を扱う。コスト効率4スキルは「計測 → 気づき → 行動 → 再計測」の1つのループを成し、本スキルはセッション・キャッシュ運用という行動側を担う。

定額プランでの読み替え: 以降の金額表現はAPI従量課金レーンのもの。定額購読では同じ操作をしても請求額は動かず、動くのは**利用枠(ローリング枠と週次上限)の消費速度**である(枠の窓長はプラン種別で異なる。現行の記載は `references/evidence.md`)。ただし機構 — tools→system→messagesの3層キャッシュ・TTL・トークン量 — はレーンに依存しないので、打ち手は1つも変わらない。不変量はトークンであり、ドル建ての閾値はトークン建て(枠の消費割合・キャッシュ書き込み全体に占める比率)へ読み替える(読み替え表は `references/evidence.md`)。自分のレーンは `/status` で確認する。レーンの違う数字を1つの総額に合算しない(換算値と実請求額は足せない — `llm-cost-observability`)。

## 大原則

1. **毎ターン全履歴再送が課金構造の土台である。** APIはステートレスで、エージェントは毎リクエストにシステムプロンプト+ツール定義+全会話履歴を再送する。変化しない部分はキャッシュ読み(cache read。トランスクリプトの `cache_read_input_tokens`。入力単価の約0.1倍)で賄われるが、それも消費に乗る — 開きっぱなしのセッションでの1行の質問にも履歴全体分のトークンが付く。キャッシュ書き込み(cache creation。`cache_creation_input_tokens`。本スキルで「再書込」と呼ぶのも同じもの)は入力単価の1.25〜2倍で、TTL(キャッシュエントリの有効期間。ヒットのたびに測り直され、切れると同じ内容でも書き込みからやり直しになる)内に再利用されて初めて元が取れる。
2. **主犯は離席であって長い会話ではない。** 連続作業中の再書込率は数%で削る余地がほぼない一方、TTLを超えて離席するとその後の復帰リクエストは全面再書込になる(TTL=1時間の環境での実測は60分超の離席で再書込率73%。値と測定条件は `references/evidence.md`)。
   復帰コストはプレフィックス(前回リクエストと共通する先頭部分。ツール定義→システムプロンプト→それまでの会話の順に積まれ、キャッシュはこの先頭一致でしか効かない)全体の再書込で決まるため、打つ指示の長さと無関係 — 数十文字の指示に数ドル(定額レーンなら数十万トークンの枠消費)が付く。
   したがって判断基準は「何ターン経ったか」ではなく「これから自分のTTL以上離れるか」の一点になる(TTLはレーンで大きく違うため、まず自分の値を確定する。手順はステップ3)。
3. **CLAUDE.mdダイエットは幻想である。** 数百トークンの常駐コストは平均プレフィックスの1%未満で、削っても請求は動かない。起動固定費で効くのはMCPツール定義と大型スキルの呼び出し頻度。CLAUDE.mdを小さく保つ理由はコストではなく指示の埋没防止であり、その内容設計は `docs-for-ai` に従う。
4. **キャッシュはtools→system→messagesの3層で、上位を触ると下位が全部落ちる。** 能動的な操作で全層(tools以下すべて)を失効させるのは2系統だけ — ツール定義の変更(MCP接続/切断・プラグイン着脱等)と、キャッシュキーの変更(モデル切替・effort変更・fast mode)。加えて本体アップグレードはsystem層以下を、/compactは会話層を作り直す(層ごとの内訳は `references/session-cache-catalog.md`)。セッション途中の/model切替1回で全履歴の再書込が走る。モデルとeffortはセッション冒頭に決めて固定し、変更はタスク境界(/clear直後)へ寄せる。ファイル編集・permission mode切替・スキル起動はどの層も壊さない。
5. **compactは無料の掃除ではない。** 要約リクエスト自体が会話全体を読み、新しいプレフィックスの書き込みが発生し、判断構造(却下した案・フェーズの前提)が落ちて圧縮後の迷走を招く。別タスクへ移るなら/clear(コストゼロ)、失敗経路の破棄なら/rewind(キャッシュ済みプレフィックスへの切り戻しでcompactより安い)を先に検討する。休止明けの巨大セッションをcompactするのが最悪手 — 要約のために全履歴をフル単価で読む。
6. **過剰最適化も失敗である。** ヘッドルームは使い切ってよい予算であり、コンテキスト残量の節約自体は目的ではない。文脈を捨てすぎて手戻り・再説明が増えたら本末転倒。施策はcounter-metrics(手戻り率・再説明の往復)とセットで判断し、対象の損失が小さければ「何もしない」を正式な結論にする。

## ワークフロー

### ファストパス: 計測基盤がないときの最初の30分

まず免除規定: **単発の運用判断**(「いまcompactすべきか」「このまま続けてよいか」「切り替えてよいか」)は基盤整備へ回さず、大原則とステップ2〜4の判断表でその場で答えて終える。計測は反復的な施策検証の道具であって、1回の判断の前提条件ではない。

計測基盤が無い状態で診断を頼まれたら、ステップ1で止まらずこの順で進む。各項は新しい手順ではなく既存ステップへの入口で、支配要因が1つに絞れた時点で打ち手へ移ってよい。

1. `/status` で請求レーンとTTLを確定する(→ステップ3)。ここを取り違えると以降の閾値がすべてずれる
2. `/context` で起動固定費の内訳と未使用MCPを見る(→ステップ5)。`/context` だけで完結し、実測では削減効果が最も大きい — **ここだけで打ち手に届くことが多い**
3. `/usage` の警告を見る(cache miss / long context が直近使用量の10%超なら表示される粗いyes/no。→ステップ1)
4. まだ支配要因が絞れなければ、ローカルのセッショントランスクリプトを jq で読む(→ステップ1)
5. 施策の前後比較を反復する段になって初めて計測基盤を整える(→ステップ6、`llm-cost-observability`)

### ステップ1: 現況とキャッシュ健全性の確認

- 診断に必要な入力は「セッション別の起動トークン・cache creation/read内訳・離席ギャップ・切替イベント」。**計測基盤が無くても4つとも取れる** — ローカルのセッショントランスクリプト(JSONL)から jq で取り出す(リクエストごとの `timestamp` の差分=離席ギャップ、`model` の変化=切替イベント、`cache_creation_input_tokens`/`cache_read_input_tokens`=内訳、セッション初回リクエストの合計=起動固定費)。起動固定費の**内訳**(システムプロンプト/ツール定義/CLAUDE.md/スキル)まで割りたいときだけ `/context` を使う。コピペで動くレシピと、この経路では取れないものの境界は `llm-cost-observability` の data-sources.md にある
- 取得は段階的に上げる: `/context`・`/usage` で支配要因が絞れたらそこで終える → 絞れなければトランスクリプトを jq で読む → 反復的な前後比較が要る段になって初めて `llm-cost-observability` に従って計測基盤を整える。診断1回のために基盤整備を先行させない
- cache creation が毎ターン高止まりしていればプレフィックスが壊れている兆候。直近のモデル・effort切替、MCP着脱、ツール設定の変更を疑う
- 支配要因を1つ特定してから打ち手に進む(離席起因の再構築 / 途中の切替操作 / 会話の肥大 / 起動固定費)。症状→要因→打ち手の対応は `references/session-cache-catalog.md` の診断表に従う

### ステップ2: セッション境界の設計

- 無関係なタスクを1セッションに混載しない(kitchen sinkセッション)。タスクの切れ目で /clear — コストゼロで新規開始できる
- /clear・/compact・/rewind は用途が違う: 別タスクへ移る→/clear、同一タスクで文脈を圧縮して続ける→切れ目で指示付き/compact、失敗した経路を捨てる→/rewind。判断表は `references/session-cache-catalog.md`
- auto-compact に任せない。発火はタスクの途中で起き、残す情報を選べない。水位警告が出たら、切れ目で「決定事項・TODO・却下案と棄却仮説を残せ」と指示を付けて自分のタイミングで打つ
- **/clear の前に必ず書き出す。** /compact には保全の指示を付けるのに /clear は履歴を丸ごと捨てるため、保全が抜け落ちやすい。切る前に、決定事項・未解決TODO・次の一手・関連ファイルパスに加えて**却下した案と棄却した仮説を理由つきで**ファイルへ書き出させる。棄却仮説は「何を否定済みか」として探索空間を狭める資産であり(`systematic-debugging`)、捨てると次セッションで同じ袋小路をなぞる。この書き出しをセッション終了時の定型手順として基盤側へ常設するなら `harness-engineering` の領分(ハーネス・hooks・CI設定への変更はHARDゲート対象で、人間の承認を通す)
- 同じ問題で2回訂正したら、そのセッションの文脈は失敗アプローチに汚染されている。/clear して学びを織り込んだ依頼で再開する(依頼文の再設計は `prompt-economy`)。ただしデバッグの仮説検証ループは対象外 — 仮説が連続で外れるのは正常な進捗であり、そこでの中断基準は `systematic-debugging` に従う(/clearするなら棄却仮説を持ち出したうえで再開する)

### ステップ3: 離席と再開の管理

- 離席前の自問は1つ: 「これからTTL以上離れるか」。離れるなら進捗の要点(決定事項・未解決TODO・次の一手・却下案と棄却仮説)を書き出させて区切る。TTL内に戻るなら何もしない(過剰最適化しない)
- TTLは認証方式・プラン設定で5分〜1時間と桁で異なる(現行値は `references/evidence.md`)。診断ではまず `/status` で「どのレーンにいるか」を確定する — 短TTLのレーンでは1時間の折り返し前に再構築が起きるため、短い中断の後の再書込は「長時間離席」ではなくレーン設定の問題
- 長TTLへのオプトインは**採否を損益分岐で確かめてから打つ**。長TTLは全リクエストの書込単価を×1.25→×2.00へ上げるので、それで救える再書込がキャッシュ書き込み総量の4割弱を超えない限り差し引きで損になる(導出は `references/evidence.md`)。「設定は見送り、短い中断も行動側で扱う」は正当な結論であり、設定で吸収できない長い中断には別途行動側の打ち手を割り当てる
- 長い休止をまたいだ再開は、巨大セッションの続行が最も高い。新セッション+要点の再指定か、サマリからの再開を既定にする。休止直後の/compactは禁じ手(大原則5)
- エージェント本体のアップグレード直後の再開も全履歴再処理になる — 巨大セッションへの復帰が最も高い1ターンになると見込む
- キャッシュは実質マシン+作業ディレクトリ単位。worktreeや別マシンへ移ると温まったキャッシュは持ち越せない

### ステップ4: キャッシュを壊す操作をタスク境界へ寄せる

- モデル・effortはセッション冒頭に決める。途中で切り替えたくなったら /clear か新セッションを経由する(そのまま切り替えると全損+新モデルで再書込)
- MCPサーバの接続/切断・プラグイン着脱・ツール設定の変更もタスク境界で行う。ただし共有設定(リポジトリのMCP定義・settings・hooks・CI)に触れるなら、タスク境界かどうか以前に `harness-engineering` のHARDゲート対象 — 人間の承認を経てから入れる(自分のローカル設定だけならタスク境界の判断で足りる)
- CLAUDE.mdのセッション中の編集はキャッシュを壊さないが反映もされない — 「直したのに効かない」ではなく、次の/clear・/compact・再起動から効く仕様。即時に効かせたい指示はプロンプトで直接渡す
- 壊す操作・壊さない操作の一覧は `references/session-cache-catalog.md` の判断表を使う

### ステップ5: 起動固定費の棚卸し

- 起動固定費(システムプロンプト+ツール定義+常駐コンテキスト)は毎セッション・毎リクエストのプレフィックスに入る恒常費。ここの削減だけが全セッションに効く
- 順序を守る: (1)未使用MCPサーバの無効化とCLI代替(`gh` 等のCLIはツール定義コストゼロ) (2)大型スキルの呼び出し頻度の確認(1回のロードが常駐の桁違いになりうる) (3)CLAUDE.mdは最後 — コスト理由では削らない(大原則3)
- 巨大なテスト出力・ログの生読みは hook の前処理で絞る。**hook・CI・共有設定への変更はコスト削減が理由であっても `harness-engineering` のHARDゲート対象**で、人間の承認を経てから入れる(エージェントが自己判断で検証系の設定を書き換えない)。チェックリストは `references/session-cache-catalog.md`

### ステップ6: 効果確認とcounter-metrics

- 施策は一度に1つ。前後比較は診断と同じデータソース(cache creation/read内訳)を施策の後にもう一度取って行う — 1回の検証なら jq の再実行で足りる。これを毎週回す・チームへ配るとなった段階で計測の常設化(指標定義・プロンプト単価分布・介入設計)を `llm-cost-observability` に従って行う
- counter-metricsを必ず併記する: 再説明の往復回数(文脈を捨てすぎのサイン)、同一ファイルの再読量、手戻り率
- 対象の損失が小さければdeprioritizeする。再構築費が誤差なのに離席管理を強いるのは、行動コストが節約額を上回る過剰最適化。「打つべき施策がない」は正当な結論

## アンチパターン

| アンチパターン | なぜ高くつくか | 修正 |
|---|---|---|
| 開きっぱなし+離席の放置 | TTL失効のたびにプレフィックス全体の再書込が走る。復帰初ターンが最も高いリクエストになる | 離席前の手放し(ステップ3)/ 損益分岐を確かめたうえでの長TTLオプトイン |
| kitchen sinkセッション | 無関係な履歴を毎ターン再送し続け、性能も劣化する | タスク境界で/clear |
| セッション途中の/model・/effort・fast mode切替 | キャッシュ全損→次ターンで全履歴を再書込 | セッション冒頭に固定。変更は/clear後 |
| 休止明けの巨大セッションをcompact・続行 | 要約リクエストが全履歴をフル単価で読む | 新セッション+要点再指定 / サマリ再開 |
| auto-compact任せ | タスク途中で発火し、残す情報を選べず判断構造が落ちる | 切れ目で指示付き/compact |
| CLAUDE.mdダイエットへの注力 | 常駐は誤差で請求が動かず、効く施策(MCP・離席)が後回しになる | 起動固定費はMCP定義と大型スキル頻度から見る |
| 節約のための細切れ/clear | 文脈を捨てすぎて再説明・再読・手戻りが増える(過剰最適化) | counter-metricsで監視し、悪化したら緩める |

## 成果物フォーマット

診断・運用設計の依頼では、散文の助言で終えず以下の構成で出す:

```markdown
# セッション運用診断書
## 1. 現況サマリ(起動固定費・cache creation/read内訳・離席/切替イベント)
## 2. 支配要因(最大コスト要因を1つ、数値根拠つきで特定)
## 3. 行動変更表(場面 × いまの行動 × 変える行動 × 期待効果の桁)
## 4. やらないこと(効果が誤差の施策と、その数値根拠)
## 5. counter-metricsと見直し条件(再説明往復・手戻り率、deprioritize基準)
```

実例: `references/worked-example.md`
