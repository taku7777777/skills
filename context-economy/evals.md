## 検証シナリオ

役割分担: task manifest に登録された実行可能ケース(`context-economy-usage-week`)は**集計済みログからの診断=実践の想起**を測る。以下のS1〜S3はそれと重ならない軸を測る — S1は**データが与えられない状態での設計**(数値を記憶で断定せず取得手段を指示できるか)、S2は**同一の問いに対する文脈依存の判断**、S3は**会話途中の宣言への介入**。task caseと同じ論点を再テストしている条件は、S1固有の軸(取得手段の指示・レーン混在・保全手順)へ寄せてある。

### S1: リモートチームのセッション運用ガイドライン策定

- **タスク**: 「架空の5人のリモート開発チーム。会議・レビュー割り込みで1人あたり1日3〜5回の中断があり、全員がClaude Codeのセッションを朝から夜まで開きっぱなしにしている。定額プランの上限に毎週ぶつかるようになった。3人はサブスクリプションログイン、2人は社内の共通APIキーで動かしている。チーム内では『共通のCLAUDE.mdを1,200行から半分に削る』案が最初の施策として出ていて、来週から実施しようとしている。中断・再開・タスク切替・モデル変更を含むセッション運用ガイドラインを作ってほしい」と依頼する(worked-exampleのフリーランス1日運用とは別題材)。
- **スキルなしで予想される欠落**: 素のモデルはCLAUDE.md半減案に同調し、「こまめに/clearする」程度の一般論を足して終わる。「これからTTL以上離れるか」という離席判断軸、認証方式でTTLが5分〜1時間と桁で違うこと(同じルールを両レーンに配れない)、モデル・effort切替の全損コスト、CLAUDE.md削減が誤差である点、counter-metricsが落ちる。
- **合格条件**:
  - [ ] 提示されたCLAUDE.md半減案を主要施策から明示的に外す。このシナリオは数値を与えていないので、常駐コストの桁を記憶で断定せず、確認手段(`/context` の実測、またはトランスクリプトからの集計)を示したうえで結論を述べている(内容整理の必要性を別軸として認めるのは可)
  - [ ] 診断データの取得を最初の行動として指示し、「計測基盤が無いから」を理由に基盤整備を先行させない(`/status`・`/context`・ローカルのトランスクリプトで初回診断は閉じる)
  - [ ] 離席の判断基準が「これからTTL相当以上離れるか」で書かれ、経過ターン数や時刻ではない
  - [ ] サブスクリプション組とAPIキー組でTTLが異なることを扱い、レーンごとに閾値または設定を分けている。長TTLへのオプトインを勧める場合は書込単価の上昇との損益分岐に触れる(採用・不採用いずれの結論でも可)
  - [ ] モデル・effort・MCP構成の変更をセッション冒頭またはタスク境界(/clear直後)へ固定するルールがある
  - [ ] 休止明けの再開手順(新セッション+要点再指定またはサマリ再開。休止後compactの禁止)が具体的にある
  - [ ] セッションを切る前(/clear・離席)に、決定事項・未解決TODO・次の一手に加えて**却下した案と棄却した仮説**を理由つきで書き出す手順が含まれる
  - [ ] 共有設定(リポジトリのMCP定義・settings・hooks・CI)の変更を伴う施策には、人間の承認を経る手順が添えられている
  - [ ] 定額プラン組の削減目標を、ドル建てではなく利用枠(ローリング枠・週次上限)の消費速度(トークン量・枠の消費割合)で表現し、APIキー組の従量請求額と1つの総額に合算しない
  - [ ] 再説明往復・手戻り率などのcounter-metricsと見直し条件が含まれる

### S2: 「compactすべき?」への文脈依存の判断

- **タスク**: 「同じ開発者から3つの状況で『/compactすべき?』と聞かれた。(a) 機能実装の真っ最中にコンテキスト警告が出た (b) 機能が完成しテストも通った直後で、次は別リポジトリの調査に移る (c) 2時間の外出から戻ったところで、昨日から続く巨大セッションが残っている。それぞれに答えてほしい」と依頼する。
- **スキルなしで予想される欠落**: 素のモデルは3つとも一律に「compactでコンテキストを整理しましょう」と答えがち。(b)での/clear(要約費用も文脈持ち越しも不要)、(c)での「休止後compactは全履歴をフル単価で読む最悪手」の指摘、compactが判断構造を落とすリスクが欠ける。
- **合格条件**:
  - [ ] (a)で即compactせず、切れ目まで待って指示付きcompact(または/rewindでの経路破棄)を提案する
  - [ ] (b)でcompactではなく/clearを提案し、理由をコスト構造(要約リクエストの費用・不要な文脈)で説明する
  - [ ] (c)でそのままのcompact・続行を止め、新セッション+要点再指定またはサマリからの再開を提案する
  - [ ] compactで判断構造(却下案・前提)が落ち、圧縮後の迷走コストになるリスクに言及する

### S3: 途中介入 — セッション途中のモデル切替宣言

- **タスク**: 決済モジュールのリファクタリング相談の途中で、ユーザーが「このセッション重くなってきたし、ここからは単純作業だから/modelで安いモデルに切り替えてこのまま続けるね」と宣言する。
- **スキルなしで予想される欠落**: 素のモデルは「良いコスト意識ですね」と同調して本題に戻る。切替がキャッシュ全損を招き、直後の1ターンの再書込で節約分が飛びうること、「切替は/clear後・セッション冒頭で」という介入が落ちる。
- **合格条件**:
  - [ ] セッション途中の/model切替がキャッシュ全損を招くことを、本題に進む前に指摘する(人間判定)
  - [ ] /clearまたは新セッションを経由した切替という代替行動を名指しで提案する
  - [ ] 安いモデルの活用自体は否定しない(切替の是非でなくタイミングの問題として扱う)
  - [ ] 残作業の量で分岐させる — 残りが小さいなら切り替えずそのまま終える方が安い(再書込費が単価差の節約を上回る)という選択肢を出す

| 日付 | モデル | 条件 | シナリオ | 判定 | メモ |
|---|---|---|---|---|---|
| 2026-07-31 | claude-opus-5 | baseline | task case `context-economy-usage-week`(本ファイルの検証シナリオS1〜S3とは別のタスク) | 平均6/9 (3回: 7/9・6/9・5/9) | critical失敗4、平均6,269,519 tokens、平均681秒、tool error 0 |
| 2026-07-31 | claude-opus-5 | with-skill | 同 task case `context-economy-usage-week` | 8/9 (3/3回) | critical失敗3(`ttl-lane` 2回・`model-switch` 1回)、平均1,169,869 tokens、平均700秒、tool error 0。改善前スナップショットを評価 |

上表の task case は `quality/tasks/cases.jsonl` に登録された実行可能ケースであり、このファイルの検証シナリオS1〜S3とは別物。実行モデル・採点モデルともclaude-opus-5で、採点は条件を伏せた匿名タグによるblind採点。**ただし blind は条件の秘匿までで、実行者と同一モデルによる自己採点である** — 同系の出力を妥当と読む方向のモデル固有バイアスは除去できておらず、これが delta の解釈の上限になる(`quality/results/2026-07-31/context-economy-usage-week/run.json` の limitations 参照)。pass rate delta +0.222、`token_overhead_ratio` 0.187、latencyはwith-skill側が約19秒増、decision=`adopt`。ただし `adopt` は「平均品質が厳密に改善し、critical失敗とtool errorが悪化しない」を満たしたという意味であり、critical基準を全て満たしたという意味ではない。反復3回は粗い退行検出用であり統計的有意性の主張ではない。

**この数値の読み方(headlineの +0.222 を単独で引用しない)**

- **基準別の内訳**: 差分は27点満点で +6 — `compact-cost` +3、`healthy-baseline` +2、`no-claudemd-diet` +1、`ttl-lane` +1、`model-switch` −1。このうち `ttl-lane` の1点は下記のとおり壊れた基準に由来し、`no-claudemd-diet` の1点は同じ結論・同じ根拠に達した2出力が分母の取り方だけで割れたもの、`compact-cost` の3点のうち2点は「離席前に/compactを打つ」という規定と異なる(が優れうる)代替策を出したためのfailである(内訳の点数は scores.jsonl からの算出。基準ごとの妥当性判断は外部レビューによる)。外部レビューの見積りでは、能力差として責任をもって読める値は概ね +0.11 前後。
- **判別力**: 9基準のうち `idle-rebuild`・`no-edit`・`mcp-overhead`・`prioritized` の4基準は6実行すべてpassで、条件間の差を作っていない。「9基準・n=3」に見えるが実効的には5基準・n=3。`mcp-overhead` の6/6は、当時のfixtureが「deferredではなく」と基準側の語彙を先出ししていたことによる(サイクル3で修正済み)。
- **delegation側との対比**: `delegation-task-portfolio` の +0.259 は `switch-timing`(baseline 1/3)と `subagent-output-contract`(baseline 0/3)という、fixtureがヒントを与えていない非自明な運用知識が動かしている。本ケースの差分は主に成果物フォーマット由来の規律(counter-metrics・非推奨施策の明示・deprioritize基準)であり、質的に別物として読む。
- **tokens の定義**: 実行エージェントのセッション全体のusage合計(キャッシュ読取を含むためターン数に対して超線形に伸びる)であり、成果物1件の生成コストではない。ばらつきが大きいので中央値とレンジを併記する — baseline 中央値 5,862,461(3,093,778〜9,852,319)、with-skill 中央値 1,235,456(575,751〜1,698,399)。中央値比は 0.211 で、平均比 0.187 が示唆するほど安定した効果ではない。
- **採点の校正**: 6出力は2バッチ(3出力ずつ)に分けて採点され、バッチは条件バランスされていない(バッチ1=with-skill 1/baseline 2、バッチ2=with-skill 2/baseline 1)。バッチ2の判定メモにだけ「厳格読みを適用した」宣言があり、バッチ間で厳格度が一様である保証はない。実際 `no-claudemd-diet` の反転はバッチ2のbaselineに落ちている。反復3回ではこのノイズを吸収できない。
- **`no-edit` の判定根拠**: 成果物の記述のみに基づく自己申告判定で、executor transcript の変更操作は照合していない。サイクル3で「免責文の有無は加点も減点もしない」へ文言を直したが、判定経路自体はまだ成果物ベースである。

**サイクル3でのrubric・fixture改訂(再採点は未実施)**: 上表の数値は改訂**前**のrubricとfixtureに対する値であり、当時の版は `quality/results/2026-07-31/context-economy-usage-week/rubric.json` と同ディレクトリの `task.md` に保存されている。サイクル3で `ttl-lane`・`no-claudemd-diet`・`compact-cost`・`healthy-baseline`・`prioritized`・`no-edit` の記述と fixture の1行を改訂したため、現行graderで再実行しても上表は再現しない。改訂の主因は `ttl-lane` の判別妥当性の反転 — 旧文言は1時間TTLへのオプトイン提案を要求していたが、このfixtureの数値では長TTLは差し引きで損(救えるのは60分未満の296,000トークンのみ、損益分岐 S>0.375W に対し S/W=10.9%)であり、正しく計算して却下した5実行がfailし、施策として曖昧に留保した1実行だけがpassしていた。記録された critical失敗7件のうち5件(baseline 3・with-skill 2)がこの基準に由来しており、スキルの欠陥ではなく採点基準の欠陥を測っている。**再採点まで、上表の critical失敗数と pass rate delta は「改訂前rubricに対する値」としてのみ引用する。**
