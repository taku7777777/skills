# モデル選択・委任・並列化の経済性スキル

Anthropic公式ドキュメント(pricing、Claude Codeのcosts / sub-agents / best-practices)と、metsuke(Claude Codeの利用コストを34,000超リクエスト規模で実測した行動変容システム)の知見を統合した、「どのタスクを・どのモデルで・どの実行形態で走らせるか」の設計プロセス。

領分の境界: 委任してよいかの判断・検証ゲート・エスカレーション基準は `harness-engineering` の領分(本スキルは「委任すると決めた作業を、いくらで・どの構成で実行するか」)。キャッシュのメカニズムとセッション運用は `context-economy`、1回の依頼文の設計と迷走の中断は `prompt-economy`、利用費の計測・帰属・介入設計は `llm-cost-observability`、LLMを組み込む製品側のモデルルーティングは `arch-security-design` の領分。コスト効率4スキルは「計測 → 気づき → 行動 → 再計測」の1つのループであり、本スキルは行動側(モデルと委任構成の変更)を担う。

定額プラン(サブスクリプション)での読み替え: 定額レーンには「requestごとの実請求額」という概念が無く、希少資源はドルではなく**利用枠(セッション枠・週次上限)の消費速度**になる(公式に「5時間ローリング窓」と明記されているのはTeams/Enterpriseのシート許容量で、Pro/Maxではsession limit / weekly limitとして案内される。どのレーンにいるかは `/status`、消費の内訳は `/usage` で確認する)。それでも単価比は「同じ作業が枠を何倍速く削るか」の比としてそのまま効くので、階層を下げる・effortとthinkingを下げる・二重払いを消す・小タスクのspawnをやめる、という打ち手は従量課金レーンと変わらない(便益が請求減ではなく枠の節約として現れるだけ)。**例外はBatch(大原則5)** — Batch APIはAPI従量課金側の機能で、Claude Codeの対話セッションから直接は使えない。定額レーンの作業をBatchへ移すと枠は空くが、その分はAPI実費として別レーンに発生する。レーンをまたぐ移動として別に扱い、枠の節約とドルの発生を1つの総額に合算しない。ドル建て閾値をトークン建てで置き換える指標は `references/evidence.md`。

## 大原則

1. **モデル選択はコンテキスト整理やキャッシュ運用より大きな桁で効く。** 単価差は全リクエストに乗算で効くため、最上位モデルの常用は他のどの節約も飲み込む。ある実測では最上位モデルが総額の過半を占めた(単一環境の値。自チームの構成比は自前の計測で確かめる)。単価比の桁感覚は Haiku:Sonnet:Opus:Fable ≒ 1:3:5:10(現在値と改定予定は `references/evidence.md`)。コスト診断ではまずモデル構成比を見る。構成比が低ければ支配費目の分析へ回す(`llm-cost-observability`)。
2. **委任は悪ではない。二重払いが悪。** 調査・大量読み込みのサブエージェント外部化は本体コンテキストを守る正当な投資。失敗パターンは「委任した上で、本体でも同じファイル群を読み直す」二重払い。委任コストは常にspawn元の指示に合算して評価する(1プロンプト=その指示が引き起こした因果総コスト — `prompt-economy`・`llm-cost-observability` と共通の帰属単位)。
3. **品質要求はタスクに紐づく。セッションや人には紐づかない。** 「品質最優先だから常に最上位モデル」は誤配分 — 機械的な作業では上位モデルの品質差はほぼ出ず(差が出るなら機械的検証で拾える)、単価差だけが確実に乗る。逆に、安価モデルへの割当は機械的検証(テスト・lint・型)とのセットでのみ成立する。検証手段なしの引き下げは差し戻しで逆転する。
4. **サブエージェントはコンテキスト分離を買う道具であり、無料ではない。** 各サブエージェントは独立コンテキストで、初回はキャッシュゼロから始まり、キャッシュTTLも短い側に固定される(`references/evidence.md`)。数往復で終わる小タスクを毎回spawnすると、起動費が分離の便益を食う。また組み込みサブエージェントの既定モデルは製品バージョンで変わるため、安く保ちたいものはモデルを明示指定する。
5. **ファンアウトは磨いてから展開する。** 一括処理は最初の2〜3件で失敗からプロンプトを改良し、通ることを確認してから全量に回す。リアルタイム性が不要な一括処理はBatch(半額、キャッシュ割引と重畳)へ逃がす。
6. **計測範囲の外へ逃がしたコストは削減ではない。** 外部エージェント(Codex等)への委譲はClaude Code側のトークンを減らすが、総コストが減ったとは限らない。委譲先に規約ファイル(AGENTS.md等)が無いと委譲のたびにリポジトリ探索が繰り返され、その費用は手元の台帳に現れない。比較は常に委譲先込みの総コストで行う。
7. **過剰最適化も失敗。** 階層の引き下げで差し戻しが増えれば、人の確認時間と再実行費で節約は逆転する。割当表はcounter-metrics(差し戻し率・上位モデルへの再依頼率)とセットでのみ運用し、悪化したタスク種別だけを一段上へ戻す。高品質が必要なタスクは高価でよい — 「安くする」を単独のKPIにしない。

## ワークフロー

### ステップ1: 現状棚卸し — モデル構成比と委任実態

- モデル別のコスト構成比を出す。`/usage` が出すのは**セッション単位**の内訳なので、数週間の構成比が要るならローカルのセッショントランスクリプトをjqで集計する(取得レシピは `llm-cost-observability` の data-sources.md)か、OTelメトリクス・Analytics APIを使う。**最上位モデルが過半なら、モデル割当が最優先の打ち手**。fan-outや依頼文の改善はその後
- 定常タスクを列挙し、頻度・検証可能性・現状のモデルを添える(判断の新規性・出力量は判断が割れたときだけ足す。棚卸しテンプレートは `references/delegation-matrix.md`)
- 現在の実行形態(メインセッション直 / サブエージェント / headless / 外部エージェント)も記録する。外部委譲があれば委譲先のコストを確認する(大原則6)

### ステップ2: タスク種別×モデル階層の割当

- 3つの問いで階層を決める: (a) 失敗を機械が検出できるか (b) 判断の新規性は高いか (c) 出力量は大きいか。判断表は `references/delegation-matrix.md`
- 目安: 機械的タスク(リネーム・依存更新・定型追加・整形)→ 最安階層+機械的検証。標準的な実装・再現テストのあるバグ修正 → 中位。設計判断・多段推論・レビューの最終判断 → 上位を温存
- **割当は必ず検証手段とペアで書く。**「Haiku級に割当」単独は不完全で、「Haiku級+既存テストgreen+lint green」が1つの割当
- **greenの出所を区別する。** 既存テスト・先に置いた再現テストのgreenは正しさの証拠になるが、**その割当自身が生成したテストのgreenは証拠として大きく割り引く**(同じモデルが書いたテストは実装の誤解を共有する — `impl-review`)。新規テスト生成を含む割当では、テストを書く側と合否を判定する側を分ける(Writer/Reviewer分離)を必須にする。既存テストで合否が出る割当(リネーム・依存更新・整形・デッドコード削除)はこの限りではない
- テスト・CI設定・hooks・lint設定など**検証資産そのものを変更する割当**(flakyテストの修正等)は、階層割当は通常どおり行う(原因調査は再現手順が不明なら上位寄り)。ただしgreenはアサーション緩和やskipで買えてしまうため通過条件にならず、**変更の反映**が `harness-engineering` のHARDゲート(人間承認必須)対象になる
- effort・thinkingも同じレバー: thinkingトークンは出力単価で課金される。機械的作業はeffortを下げる・thinkingを切る。**モデル・effortの切替はセッション冒頭か `/clear` 直後で行う**(途中切替のキャッシュ全損は `context-economy` を参照)

### ステップ3: 実行形態の選択

`references/delegation-matrix.md` の判断表で選ぶ。目安:

- **メインセッション直**: 数往復で終わる・文脈を引き継ぎたい作業。分離の便益が起動費を下回る小タスクはspawnしない(大原則4)
- **サブエージェント**: 検索結果・ログ・二度と参照しないファイル読みで本体が溢れる作業。安価モデルを `model:` で明示割当する
- **headlessファンアウト**: 同型の変更を多数のファイル・リポジトリへ展開する作業。最初の2〜3件で磨いてから全量(大原則5)
- **Batch**: リアルタイム性が不要な分類・要約・一括評価。半額
- **agent teams**: 並行性が本当に必要な場合のみ。トークン倍率が大きい(`references/evidence.md`)。小さく組み、安価モデルを割当て、終わったら畳む

### ステップ4: 二重払いの検出と排除

- 症状: 委任結果を受け取った直後に本体で同じファイル群をReadしている / サブエージェント込みの指示単価が、本体で直接やった場合の見積りを上回る
- 原因の多くは出力契約の設計不良: 委任の戻り値を構造化(結論+根拠のファイルパス・行番号+検証結果)し、本体が再読しなくても次の行動へ進める形にする。診断チェックリストは `references/delegation-matrix.md`
- 「委任結果が信用できないから読み直す」が常態なら、それは委任の検証ゲートの問題 — `harness-engineering` へ

### ステップ5: counter-metricsの設定と見直し運用

- 最低2つを割当表に添える: **差し戻し率**(安価モデルの成果物を上位モデルまたは人間がやり直した割合、タスク種別ごと)と**再依頼率**。計測の実装は `llm-cost-observability`
- 悪化したら、悪化したタスク種別だけを一段上の階層へ戻す。1種別の失敗を全体の反証にしない(「Haikuでリネームが失敗した」は「Haiku全面禁止」を意味しない)
- 見直しトリガーを明文化する: 単価改定・新モデル追加・counter-metrics悪化・タスク種別の追加。単価と製品挙動の現在値は `references/evidence.md` で確認する(記憶で断定しない)

### ステップ6: セルフチェック

- [ ] 最上位モデルの構成比に、タスク種別で説明がつくか(「なんとなく既定のまま」が残っていないか)
- [ ] 安価モデルへの割当すべてに機械的検証が添えてあるか。その検証が「その割当自身が書いたテスト」になっていないか
- [ ] 委任と本体の重複読み(二重払い)を検出する手段があるか
- [ ] counter-metricsと悪化時の行動(部分的な巻き戻し)が決まっているか
- [ ] 外部委譲分を含めた総コストで比較しているか

## アンチパターン

| アンチパターン | 修正 |
|---|---|
| 既定モデルのまま全作業(構成比が過半) | 構成比を確認し、タスク種別で割当を設計する(ステップ1〜2) |
| 「品質最優先=常に最上位」 | 品質が効くタスク(設計・最終判断)にだけ温存する(大原則3) |
| 検証手段なしの階層引き下げ | 割当は検証手段とペアでのみ書く(ステップ2) |
| 自作テストのgreenを委任成立の証拠にする | greenの出所を区別する。新規テスト生成を含む割当はWriter/Reviewer分離を必須に(ステップ2) |
| 委任結果のファイル読み直し(二重払い) | 出力契約を構造化する(ステップ4) |
| fan-out数の一律制限で対処 | 委任自体は正当。二重払い診断から入る(ステップ4) |
| 外部委譲で「安くなった」と報告 | 委譲先込みの総コストで比較する(大原則6) |

全量版と診断チェックリストは `references/delegation-matrix.md`。
