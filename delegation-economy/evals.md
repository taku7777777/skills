## 検証シナリオ

**役割分担**: task case `delegation-task-portfolio`(データ一式を渡した設計依頼)は**実践の想起** — 割当と検証手段のペア化、counter-metricsと部分巻き戻し、切替タイミング、出力契約といった「スキルが教える手順を思い出して適用できるか」を測る。本ファイルのS2〜S4はそこで測れない2種類を担う: **生の証拠からの検出**(解釈を付けない記録を渡し、浪費や誤帰属を自力で見つけられるか)と**途中介入**(別作業の会話中に出た誤った宣言を、本題へ戻る前に止められるか)。S1はtask caseと題材が近いため、**差がつく軸(データ未提供の状態で測定を先に要求できるか / 単価を記憶で断定しないか)だけに絞ってある** — task case rubric で測る条件をここで重複して問わない。

### S1: 受託開発スタジオのモデル使い分けポリシー策定(データ未提供)
- **タスク**: 「5人の受託開発スタジオ。クライアント3社の保守案件(Laravel 2件、React 1件)でClaude Codeを使っている。全員が既定モデルのまま使っており、先月の利用費が想定の2.5倍になった。日々の作業はバグ修正、見積りのための調査、定型のCRUD追加、本番リリース前のコードレビューが中心。チームのモデル使い分けポリシーを作ってほしい」と依頼する(worked-exampleの請求管理SaaSとは別題材)。**コスト構成比も単価表も渡さない**のがこのシナリオの要点。
- **スキルなしで予想される欠落**: 素のモデルは「簡単な作業はHaiku、複雑な作業はOpus」の一般論を即座に書き始め、構成比を測る手順を挟まない。単価も記憶から具体額で断定しがち。
- **合格条件**(割当と検証手段のペア化・counter-metrics・切替タイミングは task case rubric 側で測るため、ここでは問わない):
  - [ ] モデル別コスト構成比の確認を**最初の行動**として指示している(データが渡されていないことに気づき、割当設計より先に測定を置く)
  - [ ] 構成比の取得手段を具体的に示している(`/usage` はセッション単位なので、数週間分はローカルトランスクリプトの集計かOTel・Analytics API)
  - [ ] 単価の具体額を記憶で断定せず、確認先(一次情報)を示している(人間判定)

### S2: サブエージェント運用の生ログレビュー
- **タスク**: 「データ基盤チームのメンバー1人の、ある1日の作業記録を渡す。この委任のやり方をどう変えるべきか出してほしい。ファイル変更はしないこと」と依頼し、以下を**解釈を付けない記録のまま**渡す。
  - 集計: 指示12件、うち9件でサブエージェントを計47回spawn。その日の費用は本体セッション$18・サブエージェント47件の合計$44。チームのコストレポートは本体セッション分だけを「指示単価」として集計しており、サブエージェント分は別テーブル
  - `10:02` 「決済失敗の原因を調べて」→ サブエージェント5件をspawn
  - `10:14` 5件の報告を受領。報告本文が参照したファイル: `billing/invoice.ts` (L120-190)、`billing/retry.ts`、`webhook/stripe.ts`
  - `10:16` 本体セッションが `billing/invoice.ts` をRead / `10:17` 本体セッションが `billing/retry.ts` をRead
  - `11:40` 「`utils/date.ts` のtypoを2箇所直して」→ サブエージェント1件をspawn / `11:41` 完了、往復1回
  - `14:05` 「この変更の影響範囲を洗い出して」→ サブエージェント6件をspawn(対象はいずれも `services/` 配下)
  - `14:20` 6件の報告が挙げたファイル: agent-1 `order.ts`,`pricing.ts` / agent-2 `order.ts`,`mail.ts` / agent-3 `order.ts`,`pricing.ts` / agent-4 `pricing.ts`,`notify.ts` / agent-5 `audit.ts` / agent-6 `order.ts`,`notify.ts`
  - `15:30` ログ調査のサブエージェント報告を受領(対象 `logs/2026-07-14.jsonl`)/ `15:33` 本体セッションが `logs/2026-07-14.jsonl` をRead
- **スキルなしで予想される欠落**: 素のモデルは記録を「サブエージェントの使いすぎ」と読み、並列数の上限やspawn回数の削減に飛ぶ。報告受領直後の本体Readが同じ対象を指しているという突き合わせ、委任自体は正当で出力契約の設計不良が原因という切り分け、1往復で終わったspawnの起動費、本体費とサブエージェント費を分けて集計していることの誤り(spawn元への因果帰属)が落ちる。
- **合格条件**:
  - [ ] `10:16`・`10:17`・`15:33` の本体Readが直前の報告で参照済みの対象と重なっている事実を突き止め、これを主要な浪費として扱っている
  - [ ] 対策として委任の出力契約の構造化(結論+ファイルパス・行番号+検証結果)を提案し、本体が再読せず次へ進める形にしている
  - [ ] `11:40` の1往復で終わったspawnを、分離の便益が起動費を下回る例として指摘している
  - [ ] サブエージェント$44を本体$18と別集計にせず、spawn元の指示に合算した単価で評価すべきだと指摘している
  - [ ] 並列数の上限・spawn回数の削減だけで済ませていない(人間判定)

### S3: 「全部一番いいモデルで。品質最優先」への途中介入
- **タスク**: 別の作業(在庫同期バッチの修正依頼)の会話中に、ユーザーが「今後はチーム全員、常に最上位モデル・effort最大で統一しようと思う。品質最優先だから」と宣言する。
- **スキルなしで予想される欠落**: 素のモデルは「品質重視の方針ですね」と同調して本題に戻る。品質はタスクに紐づくという原則、機械的タスクでは品質差がほぼ出ない一方で単価差は確実に乗るという指摘、counter-metricsつきの棲み分け提案が落ちる。
- **合格条件**:
  - [ ] 機械的タスクでは上位モデルの品質差がほぼ出ない一方、単価差は確実に乗ると指摘している(差が出るかは機械的検証で確かめられる旨を添えている)
  - [ ] 品質要求が本当に効くタスク種別(設計判断・レビュー最終判断等)に最上位を残す棲み分けを提案している
  - [ ] 品質低下の不安に対し、counter-metrics(差し戻し率等)による監視で応えている
  - [ ] 指摘が同調の後付けでなく、宣言への応答として本題に進む前に行われている(人間判定)

### S4: 定額プランチームの「Batchへ逃がして枠を空ける」宣言への途中介入
- **タスク**: 別の作業(検索APIのページング修正)の会話中に、ユーザーが「うちは全員Maxの定額だから請求額は関係ない。問題は週次上限で、テスト拡充がそれを食う。だからテスト拡充はSonnetに書かせて、**生成されたテストがgreenならマージ**で回す。ついでにログ要約もBatchに流せば半額なので、その分の枠が空いて実質もっと得になる」と宣言する。
- **スキルなしで予想される欠落**: 素のモデルは「定額なら請求は増えませんね」と同調し、green条件もそのまま通す。(a)その割当自身が生成したテストのgreenは正しさの証拠にならない(同じモデルが書いたテストは実装の誤解を共有する)、(b)BatchはAPI従量課金側の機能で、定額レーンの作業を移すと枠は空くがAPI実費が別レーンで発生するため「枠の節約」と「半額」を1つの得に合算できない、(c)定額レーンの判断材料はドル建てでなく枠の消費速度、の3点が落ちる。
- **合格条件**:
  - [ ] 生成テストのgreenを通過条件にせず、既存スイート全体のgreen(退行なし)+Writer/Reviewer分離を課している(greenの出所を区別している)
  - [ ] Batchへの移送を**レーンをまたぐ移動**として扱い、枠の節約とAPI実費の発生を1つの総額に合算しない旨を指摘している(「実質半額」を否定している)
  - [ ] 定額レーンでの判断材料をドル建てでなくトークン建て・枠の消費率(構成比、消費率 vs 期間の経過率)で示している
  - [ ] 階層引き下げ自体の便益は定額レーンでも枠の節約として残ると方向を保っている(「定額だから何をしても同じ」にも「全部やめろ」にも倒れていない)
  - [ ] 指摘が本題(ページング修正)に戻る前に、宣言への応答として行われている(人間判定)
