# LLM利用コスト可観測性スキル

metsuke(Claude Code利用費を実測し行動変容へつなげる計測システム — 離席支配・因果帰属・介入conversionの実測知見)と、Anthropic公式ドキュメント(Claude Codeのコスト管理・プロンプトキャッシュ挙動・OpenTelemetryモニタリング)の知見を統合した、開発者・チーム自身のLLM利用コストの計測・帰属・介入の設計プロセス。

領分の境界: 本番システムのSLO・監視・インシデント対応は `ops-observability`、LLMを組み込む製品側の推論コスト設計は `arch-security-design` の領分。本スキルは「開発者・チーム自身のLLM利用費を測り、気づきを行動に変える仕組み」を扱う。計測が特定した支配費目を受けての個別の行動変更は兄弟スキルの領分 — セッション・キャッシュ・コンテキストの運用は `context-economy`、モデル選択・委任・並列化の構成は `delegation-economy`、依頼の設計と迷走の停止は `prompt-economy`。4スキルで「計測 → 気づき → 行動 → 再計測」の1つのループを成す。

## 大原則

1. **目的関数は行動変容である。数字の表示ではない。** 「見たが行動が変わらない」計測は失敗と定義する。ダッシュボードの枚数もレポートの精緻さも成果ではない。すべての指標・介入は「どの行動をどう変えるか」とセットで設計し、行動が変わらなければ計測側(文面・置き場所・閾値)を直す。
2. **過剰最適化も失敗である。** ヘッドルームは使い切ってよい予算であり、最小化目標ではない。節約で手戻りが増えれば負け — counter-metrics(手戻り率・上位モデルへの差し戻し率・タスク品質)を削減指標に必ず併記する。高品質なタスクは高価でよい。
3. **事実を永続化し、導出金額を保存しない。** 保存するのはトークン数と、出典URL・確認日つきの単価表(過去の行を上書きせず版で閉じて持つ)。金額は読み出し時に計算する — こうすると単価校正・定義変更・分類器の改良が全履歴に遡及する。未知モデルは暗黙のデフォルト単価で埋めず、コスト欠損として警告する(静かに間違うより煩く正しい)。
4. **平均で語らない。** プロンプト単価も日次コストもp50/p90/p99の分布で読む。平均はテールに引きずられ、行動対象である高額テールを隠す。異なるカテゴリ・規模のタスクを平均費用で順位付けしない。
5. **支配費目が打ち手を決める。** キャッシュ読み(履歴再送)支配ならセッション境界の運用、キャッシュ書き込み支配なら失効原因(離席・セッション途中の切替)、出力支配なら成果物の粒度、サブエージェント費支配なら役割の重複 — 費目分解のない「使いすぎ」議論は行動につながらない。
6. **介入は行動が決まる場所に置き、必ず代替行動を1つ名指す。** 「見に行く画面」は行動の瞬間から遠い。警告はプロンプト送信の直前とstatuslineの常時1行に出す。コストを下げる代替行動(新セッションでの再開・重い作業の翌日送りなど)を名指さない警告は無視される。介入にはconversion(従った率)の計測と改訂基準を最初からつけ、効かないルールは黙って消さず文面を改訂する。
7. **計測側で送信を自動ブロックしない・モデルを自動で切り替えない。** 換算値が予算100%に達しても計測ツールは送信を止めない。API単価換算値は定額購読の請求上限ではないし、誤爆1回で計測系全体の信頼が死ぬ。機械は警告とドル建ての事実提示まで、制御判断は人間に残す。禁じているのは計測・警告系による自動制御であって、請求側のハードキャップ(workspace spend limits・usage creditsの上限)は別レイヤであり、事故の最終防波堤として併用してよい。

## ワークフロー

### ステップ1: 請求レーンと計測手段の確定

- まず「どの請求レーンにいるか」を関係者で合意する(`/status` で確認)。定額購読とAPI従量課金では同じ数字の意味が違う。**API単価換算値と請求額を混同しない** — 定額プランには「request単位の実請求額」という概念自体が存在しない。レーンの違う金額を1つの総額に合算しない(換算値と実請求額は足せない)。
- **レーンごとに希少資源が違う。何を節約しているのかを最初に言語化する。** API従量ではドルが希少資源で、削減はそのまま請求減として現れる。定額購読で希少なのは**利用枠の消費速度**(公式に「5時間のローリング枠+週次枠」と明記されているのはTeams/Enterpriseのシート許容量。Pro/Maxではsession limit / weekly limitとして案内され窓長は非公開)であり、モデルを1階層下げても請求は1円も動かない — 動くのは上限に当たるまでの時間と、当たった後に手が止まる回数である。
- **打ち手はレーンに依存しない。変わるのは測り方と閾値だけ。** 機構(キャッシュTTL・プレフィックス再構築・トークン量・モデル階層差)はどちらのレーンでも同じに働くので、本スキルと兄弟スキルの介入はそのまま移る。ただし定額レーンではドル建て閾値が一度も発火しないため、`references/evidence.md` のトークン建て閾値に置き換え、成果は「請求$が減った」ではなく「上限に当たった回数・枠の消費速度が下がった」で報告する。
- `ANTHROPIC_API_KEY` が環境変数に残っていると、購読ログイン中でも従量課金レーンに入る事故が起きる。計測設計の前にこれを除去する。
- 公式手段を棚卸しする: `/usage`(セッション内訳と警告、定額レーンでは枠の消費状況)、`/context`、ローカルトランスクリプト、statusline、OTelエクスポート(全セットアップで動作する唯一のニアリアルタイムper-user手段)、Analytics API、workspace spend limits。規模に応じた選定は `references/cost-metrics-catalog.md` の導入ステージ判断表に従う。クラウドプロバイダ経由(Bedrock等)は公式ダッシュボードの対象外なのでOTelかgatewayで拾う。
- **基盤が無いことを着手しない理由にしない。** ローカルトランスクリプト(`~/.claude/projects/**/*.jsonl`)に費目内訳・離席ギャップ・モデル切替・起動固定費が揃っており、追加契約も基盤構築もなく `jq` だけで取れる。コピペで動くレシピは `references/data-sources.md`。
- ただしこの経路の届く範囲を先に確認する。**ワンライナーで閉じる**のは上の4入力。**プロンプト単位のspawn連鎖帰属(=ステップ2の帰属意味論そのもの)はワンライナーでは閉じず、小さなスクリプトが要る** — 支配費目でサブエージェント費が上位に来てから着手する。**そもそも取れない**のはチーム横断集計・介入conversion・差し戻し率で、後2つはテレメトリではなく人間の判断の記録なので、介入を作る時点で記録経路も一緒に作る(大原則6)。OTelへ上げるのは、この「取れないもの」が実際に意思決定を止めたときだけ。
- 日次境界を1つに固定する(ローカル日かUTC日か。トランスクリプトの `timestamp` はUTC)。請求突合のときだけ換算し、混ぜて並べない。

### ステップ2: 指標設計

- 指標は少数に絞る: 日次コスト(分布つき)/ ペース比・着地予測(同曜日の過去実績「中央値」比 — 平均は使わない)/ 燃焼レート(直近の時給換算)/ プロンプト単価分布(p50/p90/p99)/ 起動固定費 / 支配費目分解 / サブエージェント構成比。各指標の定義・読み方・対応する行動は `references/cost-metrics-catalog.md` の指標カタログに従う。
- 帰属の意味論を最初に固定する: **1プロンプト = 人間のその指示が引き起こした因果総コスト**。サブエージェント費は時間帯の重なりではなくspawn連鎖で起点プロンプトへ帰属する(時間帯帰属は高額ランキングを逆転させた実測がある)。帰属済みの費用を構成比集計で二重加算しない。ハーネスが注入する擬似プロンプト(タスク通知類)は人間の指示へ畳み込む — 人間が発していないプロンプトに費用が付くと指示単位の意思決定が成立しない。
- 外部エージェントへの委譲(Codex等)は計測範囲の外へコストを逃がす。「Claude Code側のトークン減少 = 総コストの減少」ではないことをレポートの注記に固定する。
- 健全域の目安と実測閾値は時点依存のため `references/evidence.md` に置き、設計書からはそちらを参照する。

### ステップ3: 介入設計

- 注意の3層で設計する: ambient(statusline常時1行)/ just-in-time(送信時警告・OS通知)/ deliberate(週次レビュー)。常設ダッシュボードから始めない — 保守費が先に立ち、行動の瞬間から遠い。
- **介入の実装手段がハーネス側に及ぶ場合、その変更自体はコスト判断で通してよいものではない。** statusline設定・hooks・CI設定・`settings.json` への変更は検証ハーネスの一部であり、`harness-engineering` のHARDゲート対象(人間の承認必須)。「コストが下がるから」を根拠にhookを勝手に足さない — 提案し、承認を得てから入れる。基盤側の設計そのものは `harness-engineering` の領分。
- 警告の規律: 代替行動を1つ名指す / 一回性(同じ警告を連発しない)・日次上限を持つ / conversion(従った率)を発火時点+観測窓で判定し、沈黙を成功に数えない / 効かない警告は自動ミュートせず、棚卸しで文面・閾値を改訂する。文面テンプレートは `references/cost-metrics-catalog.md`。
- 予算は段階運用にする: 50%で情報提示、80%で重い作業の計画変更を促し、100%でも停止せず「緊急以外を翌日へ」という人間の判断を促す(大原則7)。段階警告は換算値ベースの気づきの層であり、請求側のハードキャップとは別に設計する。**定額レーンでは分母が予算$ではなく `/usage` が示す5時間枠・週次上限の消費率になる** — トークン量から上限%を推定する式を自作しない(根拠のない分母は誤爆を生む)。
- 表示の規律: データが無ければその項目は丸ごと消す(空欄・ゼロ埋めは「未取得」と「ゼロ」を混同させる)。コンテキストは%でなく絶対トークン量で出す。**常時表示**のキャッシュ失効は「残N分」でなく絶対時刻にする(相対表示は描画凍結・取込遅延で腐り、常時表示は最後に描かれた時刻が分からない)。発火の瞬間に読まれるone-shot通知は残分数を添えてよい。

### ステップ4: 高額プロンプトの原因分解(explain)

- 高額テール(p99超・単発ガード超え)は費目5分類(cache read / cache write / output / input / ツール・エージェント費)に分解してから打ち手を対応付ける。支配費目→打ち手の対応表は `references/cost-metrics-catalog.md`、その場で構成比・離席ギャップ・切替イベントを出す手順は `references/data-sources.md`(基盤不要)。サブエージェント費は本体セッションのログに現れないので、別ファイル分を足し忘れると委任の多いセッションで系統的に過小評価する。
- **支配費目を見る前に犯人を決めない。** cache write支配のテールでは、最高額はしばしば最も短い指示になる — 費用は入力文字数ではなく、そのとき再処理されるプレフィックス全長で決まるからだ(休止後再開の一言指示が同セッションのrequest単価中央値の17倍についた実測がある。`references/evidence.md`)。一方 input支配なら巨大ログの生貼り付け、output支配なら生成量そのものが主因で、そこでは長い入力・長い出力が実際の犯人である。「誰が長文を打ったか」は費目を見る前には答えられない。
- cache write のなかでは、連続作業中の再構築は少なく、長い離席後の再開とセッション途中の `/model`・`/effort` 切替に集中する(実測は `references/evidence.md`)。ただしこれはcache write内部の分布であって、費目全体の支配を意味しない — 構成比を先に見て、離席起因の再構築費が施策化に値する規模か(`references/evidence.md` の deprioritize 目安)を確認する。診断は「普段の使い方は既に効率的」の順で伝え、個人の失敗探しにしない。
- 分解の結果はループの次工程へ接続する: セッション・キャッシュ起因は `context-economy`、モデル・委任構成起因は `delegation-economy`、依頼の曖昧さ・迷走起因は `prompt-economy`。

### ステップ5: 週次レビューと施策検証

- 週次レビューは仮説のpush型提示にする: 変化の主張ごとに「どのレバーが動いたか」を1つ以上特定し、対応する指標変化と再現手段(集計コマンド等)を併記する。どのレバーでも説明できない変化は外生ショック(ツール更新・モデル追加・休暇)を疑い、記録してから解釈する。
- 施策は台帳で管理する: 仮説・期待効果・判定日を書いてから着手し、同時に走らせる施策は2本以下。1回の実施で勝敗を断じず、判定日に人間がverdictを記録する。
- 施策化の前に損失規模を確認する: 再構築費・対象費目が小さければ着手しない(deprioritize)。「打つべき施策が無い」という結論自体が成果であり、実体のない施策を作らない。
- 計測の是正で見かけの数字が悪化することがある(誤帰属の修正でカバレッジが下がる等)。**カバレッジ低下は劣化ではなく水増しの是正**でありうる — 定義変更はレポートに明記する。

### ステップ6: 計測ヘルスとROI・撤退基準

- 鮮度は「プロセスが生きているか」でなく「最後に正常パースしたデータの時刻」で監視する。staleが出たら分析より先に計測を直す — 古い数字で警告を出す方が、警告が無いより害が大きい。単価表の欠落・請求レーンの混在・同一利用の二重計上といった意味の壊れも同じ扱いで、削減施策の優先順位づけより先に是正する(壊れた総額の上に立てた優先順位は根拠にならない)。
- 独立した第2推定器(クライアント側推計や請求書との定期突合)を1本持ち、乖離を意味的な破損のカナリアにする。乖離は校正情報でありゲートではない。
- 計測システム自身にROIと撤退基準を最初から組み込む: 検証済み削減額が計測の総コスト(ツール費+人時間)を下回り続けたら、構成を縮退する。金額算出・集計・描画はローカルで完結させ、statusline・hookのようなホットパスからLLMを呼ばない。週次レビューの分析にLLMを使うのは可 — ただしそのanalyst費をROIの分母へ算入し、赤字が続けば縮退の対象にする。

## アンチパターン

| アンチパターン | なぜ失敗するか | 修正 |
|---|---|---|
| ダッシュボード構築から始める | 保守費が先に立ち、「見に行く画面」は行動の瞬間から遠い | statusline 1行と送信時警告から始め、pull型の精査画面は後回し |
| 導出金額をDBに焼き込む | 単価校正・定義変更のたびに過去が誤ったまま残る | 事実(トークン)+版管理された単価表、金額は読み出し時に計算 |
| 未知モデルをデフォルト単価で埋める | 静かに間違い続け、校正の機会を失う | コスト欠損として警告し、単価表への追加を促す |
| 高額ランキングを時間帯・セッション所有者で帰属 | サブエージェント費の誤帰属でランキングが逆転する | spawn連鎖による因果帰属。監査してから個人の話をする |
| 計測系が換算値ベースで送信を自動停止・モデルを自動切替 | API換算は定額購読の実上限ではない。誤爆1回で信頼が死ぬ | 段階警告+代替行動の名指し+人間の判断。ハードキャップが要るなら請求側のspend limitで別に張る |
| 「見せた」を成果として報告 | 行動が変わらなければ計測は失敗(目的関数の取り違え) | 介入conversionを計測し、低ければ文面・閾値を改訂 |
| 節約額だけを報告する | 手戻り・品質低下・利用の萎縮という裏面が見えない | counter-metrics(手戻り率・差し戻し率)を必ず併記 |
| 参照・描画・ホットパスでLLMを呼ぶ | コスト削減の道具が追加のAI利用を要求する逆転 | 金額算出・集計・描画はローカル完結。週次のLLM分析は可 — analyst費をROIに算入し、赤字が続けば縮退 |

```markdown
# <チーム/個人> LLM利用コスト計測・介入設計書
## 1. 請求レーンとデータソース(レーン確認結果、レーンの希少資源、混同の禁止事項、日次境界)
## 2. 指標定義(指標 × 定義 × 健全域 × 読み方→行動。分布で定義する)
## 3. 介入一覧 — 表は必須3列(介入 × 層 × 発火条件)。文面・conversion判定・抑制規則は表の下に介入ごとの箇条書きで書く(文面は長文になり表内で崩れる)
## 4. 予算の段階運用(50/80/100%の各行動。自動停止しない根拠を明記)
## 5. 施策台帳(仮説 × 期待効果 × 判定日 × counter-metrics。同時2本以下)
## 6. 計測ヘルスとROI(鮮度監視、第2推定器、撤退基準)
```
