スキルの効果を測定するための評価定義。運用方法は skill-improvement スキルの
references/eval-template.md を参照。

## 検証シナリオ

### S1: API従量課金の個人開発者の計測導入

- **タスク**: 「フリーランスの個人開発者。Claude CodeをAPIキーの従量課金で使っていて、月の請求が$80〜$400とぶれて読めない。高い月に何が起きたのか分からないのが不安。手間をかけずに、使いすぎに気づけて原因も追える最小限の仕組みを段階的に入れたい」と依頼する(worked-exampleのチーム導入・fixtureの部門レポート診断とは別題材)。
- **スキルなしで予想される欠落**: 請求レーンの確認と換算値/請求額の区別、分位点での指標定義、導入ステージの段階論(最小構成から始めてROIで増設)、警告への代替行動の名指し、計測自体の撤退基準。素のモデルは「ダッシュボードを作る」「上限アラートを設定する」型の一般論と自動停止の提案に流れる。
- **合格条件**:
  - [ ] 請求レーン(API従量)の確認と、TTLが認証方式で異なることへの言及がある
  - [ ] 指標が平均でなく分布(p50/p90等)で定義されている
  - [ ] 介入が行動の決まる場所(statusline・送信時)に置かれ、警告文面に代替行動が名指しされている
  - [ ] 計測ツール側の送信自動ブロック・自動モデル切替を統制の主軸にせず、警告と本人の判断を主軸に置く(critical。請求側の spend limit をバックストップとして併用する提案は可 — 換算値ベースの自動制御と請求側のハードキャップを区別できているか)
  - [ ] 計測の手間自体にROI・撤退基準(効かなければ縮退する条件)が定義されている

### S2: 高額プロンプトランキングの帰属監査

- **タスク**: 「データ分析チーム5名。毎週『高額プロンプトランキング』を社内に貼り出しており、サブエージェントを多用するメンバーBが毎回ワースト上位で肩身が狭い。ランキングは各リクエストの発生時間帯とセッション所有者から集計している。本当にBの使い方が悪いのか、この運用を続けてよいのか調べてほしい」と依頼する。
- **スキルなしで予想される欠落**: 時間帯ベースの帰属がspawn連鎖ベースと食い違い高額側で逆転する問題、サブエージェント費のspawn元帰属と二重加算の禁止、カテゴリの異なるタスクを費用で順位付けしない原則、個人の失敗探しにしない診断の順序。素のモデルはランキングの見た目を信じてBの使い方指導に進む。
- **合格条件**:
  - [ ] 時間帯・所有者ベースの帰属方式そのものを疑い、spawn連鎖(因果)帰属との突合を先に求める(critical)
  - [ ] サブエージェント費は起点プロンプトの因果総コストへ帰属し、二重加算しない意味論を示す
  - [ ] タスク種別・規模の異なるメンバー間を単純な費用順位で比較しない原則を指摘する
  - [ ] 委任(サブエージェント利用)自体を悪と断定せず、二重払い(委任先と本体の同一ファイル再読)の検出へ論点を移す
  - [ ] 帰属し直しても起点を特定できないサブエージェント費が残ることを見込み、それを暗黙に0とせず「欠損」として量と割合で報告する運用を求める(大原則3。カバレッジを併記しない順位表は委任の多いメンバーを過小評価したまま順位づけする)
  - [ ] 個人名の貼り出しという運用への修正(行動変容につながる形への変更)を提案する(人間判定)

### S3: 「AI利用費を半分にしろ」への途中介入

- **タスク**: 別の作業(四半期のチーム目標資料の作成)の会話中に、ユーザーが「そういえば経営からAI利用費を来月までに50%削減しろと言われた。手っ取り早く全員Haiku固定にして、日次上限を超えたら自動で使えなくする設定にしようと思うが、どう思う?」と尋ねてくる。
- **スキルなしで予想される欠落**: 自動ブロック・一律モデル固定をしない原則(誤爆による信頼喪失・換算値と請求の乖離)、削減の前に支配費目分解を求める順序、counter-metrics(手戻り率・差し戻し率)の併記、段階警告+人間の判断という代替案。素のモデルも「品質が落ちるリスク」までは言えるが、換算値と請求額の乖離・誤爆による計測系の信頼喪失・支配費目を測る前に削減幅を約束しない順序までは出さない。
- **合格条件**:
  - [ ] 一律Haiku固定・自動停止に同調せず、換算値と実請求額の乖離(換算$の50%削減は請求の50%削減を意味しない)と誤爆1回で計測系の信頼が死ぬことを根拠として示す(critical)
  - [ ] 削減施策の前に支配費目分解(何が費用を支配しているかの計測)を求め、測る前に削減幅を約束しない(critical)
  - [ ] counter-metrics(手戻り率・差し戻し率等)を削減目標に併記することを提案する
  - [ ] 段階的予算運用(50/80/100%・警告+代替行動・停止しない)を代替案として示す
  - [ ] 指摘が本題(資料作成)へ戻る前の介入として行われている(人間判定)

### S4: 定額プラン・計測基盤ゼロのチームリード

- **タスク**: 「6人のチーム全員がClaude Codeのサブスクリプション。最近みんな週の後半に上限に当たって手が止まる。計測ツールの類は一切入れていないし、SaaSを増やす稟議は通らない。今週中に原因を掴んで手を打ちたい」と依頼する(S1のAPI従量・個人とは別レーン別規模。worked-exampleのチームは初期構築工数を確保できる点が異なる)。
- **スキルなしで予想される欠落**: 定額レーンの希少資源が枠の消費速度でありドルではないという読み替え、基盤を建てずにローカルトランスクリプトから当日中に費目分解する経路、ドル建て閾値が定額レーンでは発火しないこと、ハーネス変更(statusline・hooks)が人間の承認を要すること。素のモデルは「OTelを入れましょう」「ダッシュボードを作りましょう」という基盤先行の提案、またはドル建ての削減目標に流れる。
- **合格条件**:
  - [ ] 計測基盤の構築を先行させず、既存の手段(`/status`・`/usage`・`/context`・ローカルトランスクリプトのjq集計)で当日中に費目分解へ着手する経路を示す(critical)
  - [ ] 定額レーンの希少資源を5時間枠・週次上限の消費速度として言語化し、「請求$がいくら減るか」を成果指標に置かない(critical)
  - [ ] 閾値・成果をトークン建て(または枠消費率)で示し、ドル建て閾値をそのまま持ち込まない
  - [ ] statusline・hooks・設定ファイルへの変更を提案する場合、それが人間の承認を要する基盤変更であることに触れる
  - [ ] トランスクリプトにプロンプト本文が含まれるため、メンバー分を集める運用にはプライバシー上の合意が要ることに触れる(人間判定)
