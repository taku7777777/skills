# コスト指標・介入カタログ(定義表・対応表・テンプレート集)

SKILL.md ワークフローの各ステップから参照する詳細カタログ。閾値の実数は時点依存のため `evidence.md` を正とし、本カタログでは構造(定義・読み方・対応する行動)だけを固定する。

## 目次

- 指標カタログ(ステップ2)
- 支配費目→打ち手対応表(ステップ4)
- 介入テンプレート集(ステップ3)
- 予算の段階運用テンプレート(ステップ3)
- 導入ステージ判断表(ステップ1)
- 週次レビュー・施策台帳テンプレート(ステップ5)
- 落とし穴チェックリスト(全ステップ)

## 1. 指標カタログ(ステップ2)

| 指標 | 定義 | 読み方 → 行動 |
|---|---|---|
| 日次コスト | その日の因果帰属済み費用の合計。単一値でなく直近数週のp50/p90を添える | 予算比で読む。単日の高低で騒がない — 分布から外れた日だけ原因分解へ |
| ペース比 | 本日累積 ÷ 同曜日・同時刻までの過去実績の**中央値**(平均は使わない) | 閾値超で「今日は重い作業を続けるか」の判断材料。朝など分母が小さい時間帯は参考値扱い |
| 着地予測 | 本日累積 + 過去同曜日の残り時間帯支出の中央値 | 予算超過を「日が終わってから」でなく実行中に気づかせる |
| 燃焼レート | wall-clock直近30分程度の費用の時給換算 | 「今燃えているか」。手を止めれば下がるのは意図した挙動であり異常ではない |
| プロンプト単価分布 | 1プロンプト=因果総コスト(サブエージェント込み)のp50/p90/p99 | p50は日常の健全性、p90/p99が行動対象。テール1件の分解がステップ4 |
| 起動固定費 | セッション初回リクエストの合計トークン | 全セッションに乗る恒常費。最安レバー。同一モデル内でのみ推移比較する |
| 支配費目分解 | cache read / cache write / output / input / ツール・エージェント費の構成比 | 構成比の変化が「どのレバーが動いたか」の裏付けになる |
| サブエージェント構成比 | プロンプト費用に占める委任分 | 委任は悪ではない。「委任した上で本体でも同じファイルを読む二重払い」の検出が本義 |
| 介入conversion | 警告に従った率 = followed ÷ (followed + not_followed)。unknownは分母に入れない | 低迷が続いたら文面・閾値を改訂(撤退基準)。自動ミュートはしない |
| 計測ヘルス | 最後に正常パースした時刻、欠損レコード数、第2推定器との乖離 | staleなら分析より計測を直す。乖離は校正情報でありゲートではない |

指標設計の検収基準: 各行に「この数字が動いたら誰が何をするか」を書けること。書けない指標は載せない(1画面=1問い)。

## 2. 支配費目→打ち手対応表(ステップ4)

高額プロンプト・高額日の explain は、まずこの表で支配費目を特定してから兄弟スキルへ接続する。

| 支配費目 | 典型原因 | 打ち手の方向 | 接続先 |
|---|---|---|---|
| cache read(履歴再送) | セッションの肥大・kitchen sink化 | タスク境界でセッションを切る運用 | `context-economy` |
| cache write(再構築) | 長い離席後の再開、セッション途中のモデル・effort切替、ツール定義変更 | 再開判断・切替タイミングの運用変更。**入力文字数は無関係** — 短い指示を犯人にしない | `context-economy` |
| output | 成果物の粒度が大きすぎる、verbose出力の生成、thinkingの常時最大 | 成果物分割・effort調整・出力先の変更 | `delegation-economy` / `prompt-economy` |
| input(非キャッシュ) | 巨大ログ・ファイルの生貼り付け | 前処理(grep・要約)してから渡す | `prompt-economy` |
| ツール・エージェント費 | fan-out過多、委任先と本体の二重読み、役割重複 | 委任構成の見直し。spawn元帰属で「どの指示が起こしたか」を先に特定 | `delegation-economy` |

診断の順序規律: **まず構成比で支配費目を確定し、そのあとで原因イベントを探す**。「離席が主因」は cache write が支配費目のときの話であって、outputやinputが支配的な環境では別の結論になる。支配費目を決めたら、全体を疑う前にテールと離席・切替イベントを見る — 「普段の使い方は既に効率的」が実測の通例(連続作業中の再書込はごく僅か)。離席起因の再構築費は施策化前に規模を確認する(`evidence.md` の deprioritize 目安)。

## 3. 介入テンプレート集(ステップ3)

各介入は「発火条件 / 文面(代替行動の名指し必須)/ conversion判定 / 抑制」の4点を埋めて初めて設計完了とする。文面中の閾値は `evidence.md` の実測目安(定額レーンならトークン建て閾値)から各自の予算に合わせて決める。

一覧は必須3列だけを表にする。文面は長文になり表内で崩れるので、下の箇条書きに分ける。

| 介入 | 層 | 発火条件の型 |
|---|---|---|
| cold cache警告 | just-in-time | 前回リクエストからの間隔がキャッシュTTL超、かつ再構築量が下限以上 |
| 失効前通知 | just-in-time | TTL失効の直前窓、かつ進行中プロンプトなし |
| コンテキスト警告 | just-in-time | コンテキスト使用量が水位超(絶対量で判定) |
| 予算段階警告 | just-in-time | 日次累計/予算 ≥ 50 / 80 / 100%(定額レーンは `/usage` の枠消費率) |
| 暴走ガード | ambient→通知 | 進行中プロンプトの累積が単発上限超 |
| 領収書 | just-in-time | 高額プロンプト完了直後 |
| statusline常時1行 | ambient | 常時 |
| 週次レビュー | deliberate | 週1回(欠報検知つき) |

文面の型(代替行動の名指しは必須):

- **cold cache警告**: 「再構築 ≈ <量>。前の作業の続きでなければ、新セッションで始める方が安い」
- **失効前通知**: 「HH:MMにキャッシュ失効(残N分)。続けるなら今。終わりなら放置か引き継ぎメモを」— 絶対時刻を主、残分数は発火時点の補助
- **コンテキスト警告**: 「auto-compact接近。区切りの良いところで自分のタイミングの分割を」
- **予算段階警告**: 「本日<累計>/<予算>(着地見込み<予測>)。重い一括作業は明日へ回せる」— 100%でも停止しない
- **暴走ガード**: OS通知で規模を提示。止めるかは人間が判断する
- **領収書**: 「このプロンプト<費用>。主因は<支配費目>。分解は<explain手段>で」— 単価感覚の形成
- **statusline常時1行**: 本日累計/予算・燃焼レート・着地・直近プロンプト費・コンテキスト絶対量・失効絶対時刻。データが無い項目は消す
- **週次レビュー**: 仮説+根拠+再現手段。テンプレートは §6

抑制の共通規則: 同一警告は一回性(セッション・事象単位)、日次上限を設ける、重複を抑止する。警告疲労はconversion低下として観測されるので、低下したら発火頻度でなくまず文面と閾値を疑う。

実装上の注意: statusline・hooks・`settings.json` への変更は検証ハーネスの一部であり `harness-engineering` のHARDゲート対象(人間の承認必須)。介入の設計は本スキルの領分だが、**基盤への適用は承認を経てから**行う。

## 4. 予算の段階運用テンプレート(ステップ3)

| 段階 | 状態 | 促す行動(例) | してはいけないこと |
|---|---|---|---|
| 〜50% | 平常 | なし(表示のみ) | 平常時に警告を出す(疲労の源) |
| 50% | 情報 | 着地見込みの提示 | 行動要求(まだ早い) |
| 80% | 計画変更 | 重い一括作業・大規模探索を翌日へ。当番・チームへの事前共有 | モデルの一律強制切替 |
| 100% | 判断喚起 | 緊急以外を翌日へ、という**人間の判断**を促す | 計測側での送信の自動ブロック(API換算は定額購読の実上限ではない。誤爆1回で信頼が死ぬ)。ハードキャップが要るなら請求側のspend limitで別に張る |

チーム運用では「段階到達時に誰が何をするか」(当番確認・共有チャンネルへの通知)を役割つきで決める。counter-metricsの併記を忘れない: 翌日送りで締切・品質が犠牲になっていないか。

## 5. 導入ステージ判断表(ステップ1)

計測は最小構成から始め、ROIが確認できた分だけ増やす。逆順(基盤から作る)は撤退基準に反する。**ステージ0.5までは基盤構築も追加契約も不要**なので、「計測基盤が無いから着手できない」は成立しない — ステージ1以降(statusline・hooks等のハーネス変更)へ進むときだけ `harness-engineering` のHARDゲート(人間の承認)を通す。

| ステージ | 対象 | 使う手段 | 増設の条件 |
|---|---|---|---|
| 0: 手元確認 | 個人 | `/usage`・`/context`・請求書 | 単発の確認では足りず、費目内訳・原因イベントまで踏み込む必要が出る |
| 0.5: ローカルログ分析 | 個人 | `~/.claude/projects/**/*.jsonl` を jq で集計(`data-sources.md`)。費目構成・離席ギャップ・モデル切替・起動固定費 | 同じ分析を毎日手で回している / 常時把握したい具体的な行動判断がある |
| 1: ambient | 個人 | statusline 1行(累計・燃焼レート・失効時刻) | 「見たのに行動しなかった」事象が繰り返し観測される |
| 2: just-in-time | 個人 | 送信時警告(cold cache・予算段階)+conversion記録 | チームでの帰属・比較が必要になる |
| 3: チーム計測 | チーム | OTelメトリクス(user/部門属性)+ 週次レビュー | 組織の上限管理・請求統制が必要になる |
| 4: 組織統制 | 組織 | Analytics API・workspace spend limits | — |
| 縮退 | 全ステージ | 検証済み削減額 < 計測総コスト が継続したら1段階下げる | — |

## 6. 週次レビュー・施策台帳テンプレート(ステップ5)

```markdown
# 週次コストレビュー <ISO週>
## 数字(分布で)
- 週計 $X(先週 $Y)/ プロンプト単価 p50/p90/p99 / 支配費目構成比の変化
## 帰属(主張ごとに根拠)
- 変化: <何がどれだけ> / 動いたレバー: <どれ> / 裏付け指標: <どれがどう動いたか> / 再現手段: <集計コマンド等>
- どのレバーでも説明できない変化 → 外生ショック(ツール更新・休暇等)の記録を確認
## 施策台帳(同時2本以下)
| 施策 | 仮説 | 期待効果 | 判定日 | counter-metrics | verdict |
## 今週の高額テール(explain 1件以上)
- <プロンプト> $X — 支配費目 / 原因 / 接続先スキル
## 計測ヘルス
- 鮮度 / 欠損 / 第2推定器乖離。stale項目があれば分析より先にここを直す
```

## 7. 落とし穴チェックリスト(全ステップ)

- [ ] API単価換算値を定額購読の「請求額」として報告していないか(レーン確認を先に)
- [ ] `ANTHROPIC_API_KEY` の環境変数残置で従量課金レーンに入っているメンバーはいないか
- [ ] 平均で語っていないか。カテゴリの異なるタスクを費用で順位付けしていないか
- [ ] 日次境界(ローカル/UTC)を混ぜて突合していないか
- [ ] サブエージェント費をspawn元帰属と構成比集計で二重加算していないか
- [ ] 「unknown」を欠測でなく1つのカテゴリとして扱っていないか(帯で読む)
- [ ] 外部エージェント委譲で計測範囲外へ逃げたコストを「削減」と誤認していないか
- [ ] 警告に代替行動の名指しがあるか。conversionを計測しているか。自動ミュートしていないか
- [ ] 計測・警告系に自動ブロック・自動モデル切替を仕込んでいないか(大原則7。請求側のspend limitとは別物で、そちらは併用可)
- [ ] 削減指標にcounter-metrics(手戻り率・差し戻し率)を併記しているか
- [ ] 計測システム自身のROIと撤退基準を定義したか。金額算出・描画やホットパスでLLMを呼んでいないか(週次分析のanalyst費はROIの分母に算入したか)
