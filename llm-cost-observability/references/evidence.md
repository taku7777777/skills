# LLM利用コストのエビデンス(時点依存)

SKILL.md には桁の関係と原則だけを書き、単価・倍率・実測値・閾値の実数はすべて本ファイルに置く。引用時は必ずアクセス日と適用範囲(モデル・認証方式・計測対象)を併記する。

## 使い方

- 価格・倍率は改定される。成果物へ転記するときは本ファイルの値を直接コピーせず、一次URLを再確認してから使う。
- 実測値(metsuke)は単一ユーザー・特定期間の観測であり、普遍的な比率ではない。「自分の環境で再測定するまでの事前分布」として使う。
- 閾値の目安は「行動が決まるならどこでもよい」種類の値。予算・単価の変化に合わせてスケールさせる。

## 一次情報(Anthropic公式)

- [Claude Code: Manage costs effectively](https://code.claude.com/docs/en/costs) — 2026-07-30参照、official。エンタープライズ実績は平均約$13/開発者/稼働日・$150〜250/開発者/月、90%のユーザーは$30/日未満。`/usage` はセッションのモデル別内訳に加え、long contextやcache missが直近使用量の10%以上を占めると警告と削減Tipsを表示。組織はworkspace spend limitsとAnalytics APIでper-userコストを管理。バックグラウンド消費は通常$0.04/セッション未満。クラウドプロバイダ経由(Bedrock/Vertex/Foundry)は公式ダッシュボード対象外。**「OpenTelemetryエクスポートは全セットアップで動作し、per-userのトークン・コストをニアリアルタイムで流せる唯一の選択肢」という記述の出典はこのcostsページ**(monitoring-usageページではない)。
- [Claude Code: Prompt caching behavior](https://code.claude.com/docs/en/prompt-caching) — 2026-07-30参照、official。キャッシュTTLは認証方式で異なる: サブスクリプションは自動1時間(usage credits消費中は5分へ降格)、APIキー/Bedrock/Vertexは5分(`ENABLE_PROMPT_CACHING_1H=1` で1時間へ)。セッション途中の `/model`・`/effort`・fast mode切替はキャッシュ全損。`/rewind` はキャッシュ済みプレフィックスへの切り戻しで `/compact` より安い。長い休止後・アップグレード後の再開は「最初の1ターンが最も高いリクエストになりうる」。キャッシュ実質スコープはマシン+ディレクトリ単位。
- [Claude Docs: Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md) — 2026-07-30参照、official。キャッシュ倍率(対入力単価): 5分書込 ×1.25 / 1時間書込 ×2.00 / 読み取り ×0.10。Batch APIは入出力とも ×0.5 でキャッシュ倍率と重畳。出力単価は入力の約5倍(thinkingも出力課金)。単価比の桁感覚: Haiku : Sonnet : Opus : Fable ≒ **1 : 3 : 5 : 10(2026-09-01以降)**。**Sonnet 5の導入価格($2/$10)が有効な2026-08-31までは 1 : 2 : 5 : 10** で、9/1に$3/$15へ戻る。Claude 4.7以降のモデル(Opus 4.7+・Sonnet 5・Fable 5等。Sonnet 4.6以前は旧トークナイザ)の新トークナイザは同一テキストを約30%多くトークン化する(単価同一でも実効コスト増)。
- [Claude Code: Monitoring usage (OpenTelemetry)](https://code.claude.com/docs/en/monitoring-usage) — 2026-07-30参照、official。`claude_code.token.usage`・`claude_code.cost.usage`(USD)等のメトリクスを `user.id`・`organization.id`・`model`・`session.id` 属性つきでエクスポート。`OTEL_RESOURCE_ATTRIBUTES`(department等)で部門帰属。managed settingsで組織強制も可能。「全セットアップ対応の唯一のニアリアルタイムper-user手段」という位置づけの記述はこのページではなくcostsページにあり、主語はOTelエクスポート全体(部門帰属用の環境変数ではない)。
- [Claude Code: Subagents](https://code.claude.com/docs/en/sub-agents) — 2026-07-30参照、official。サブエージェントは独立コンテキスト・独立キャッシュで動き、親には要約のみ返る。frontmatter `model:` で安価モデルへのルーティングが公式ユースケース。

## 実測値(metsuke)

[metsuke](https://github.com/taku7777777/metsuke) — 2026-07-30参照、industry-research(単一ユーザーのClaude Code全ログ実測。査読なし)。

- **離席はcache writeの中で支配的**: 直前リクエストからの間隔5分未満での再書込率2.6%(312 request)に対し、**60分超では73.0%**(4 request)。連続作業中のキャッシュは既に効率的で、cache writeの削減余地は離席後再開とセッション途中の切替に集中する。**これは再書込「率」の分布であって、総コストに占める費目シェアの話ではない** — 支配費目がoutputやinputの環境では、離席対策は最優先の打ち手にならない。プレフィックスの8割超を書き直した4 requestの実効トークンは9セッション合計の13%。
- **短い指示が最高額になりうる**: 37文字の再開指示が$4.30(内99%が425,826トークンのキャッシュ再書込)。同セッション全105 request(サブエージェント含む・合計$30.91)の**request単価**中央値$0.2480の17倍で、この1 requestだけでセッション合計の13.9%。費用はプレフィックス全長で決まり入力文字数と無関係。**「プロンプト単価の中央値」ではなくrequest単価の中央値**である点に注意(1プロンプト=複数request)。
- **モデル選択は桁で効く**: 34,000超リクエストの実測で最上位モデル(Fable 5)が総額の53%を占有。
- **誤帰属の規模**: 時間帯ベースのサブエージェント帰属は agent系コストの約1/4(総コストの約5%)を誤帰属し、高額プロンプトランキングで数百位→1桁の逆転を起こしていた。ハーネス注入の擬似プロンプトは件数約8%で総コストの約2割を占め、人間の指示へ畳み込まないと指示単位の分析が壊れる。
- **CLAUDE.md常駐費は小さい**: 300トークン常駐の実効コストは平均プレフィックスの+0.15%。起動固定費で効くのはMCPツール定義(短期間で約4割増・数万トークン規模へ肥大した実例)と大型スキルの呼び出し頻度。

## 閾値・健全域の目安(metsukeの運用値。予算に合わせてスケールさせる)

- プロンプト単価: p50 ≤ $1 / p90 ≤ $8。単発 $5超 は暴走ガードと突合。
- ペース比(同曜日中央値比): 緑 ≤1.2 / 琥珀 ≤1.5 / 赤 >1.5。
- 予算段階: 50 / 80 / 100%。100%でも送信は停止しない。チーム例: $150/日を70%で当番確認、85%で重タスク事前共有、100%で緊急以外を翌日へ。
- cold cache警告の下限: 再構築費 $0.5 以上のときだけ発火(小さな再構築に警告を出さない)。
- 介入conversion: 2週間 <10% でルールの文面・閾値を改訂(自動ミュートはしない)。
- 施策検証: 証拠期間28日+10稼働日。TTL系施策は再構築費が1日$5未満または全キャッシュ書込の10%未満なら deprioritize。
- 計測ヘルス: 第2推定器との乖離 ±10% を監視目安(請求突合の校正閾値 ±5% とは別物)。鮮度ゲート15分。
- ROI: 検証済み削減額 ÷ 計測総コスト が低め推定でも1倍超を目標。2四半期連続赤字で構成を縮退。

## トークン建ての代替閾値(定額レーン用)

定額購読ではドル建て閾値が一度も発火しない — 換算値は請求額ではなく、希少資源は5時間枠・週次上限の消費速度だからである。以下は上のドル建て閾値を、同じ判断が下るトークン量へ置き換えたもの。ドルへ換算する必要がないので、`data-sources.md` のjq出力からそのまま判定できる。

換算の基準(2026-07-31時点・Fable 5相当。入力$10/Mtok、1時間書込は×2.00で実効$20/Mtok、キャッシュ読みは×0.10で$1/Mtok、出力$50/Mtok)。**この単価の一次確認先は公式pricingページ(`quality/sources.json` の `claude-pricing` エントリ)であり、本ファイルの数値は転記である。** 改定時は一次表を見てから本節の導出値を引き直す — 単価だけ直して換算基準を放置すると閾値が黙ってずれる(実際に一度起きた):

- 再構築費 $0.5 ÷ $20/Mtok = 25,000トークンのcache write → 運用値 **25,000**
- 再構築費 $5 ÷ $20/Mtok = 250,000トークン → 運用値 **250,000**
- $5 ÷ $50/Mtok = 100,000トークンのoutput → 運用値 **100,000**

安いモデル中心の環境ではトークン量が数倍まで許容される。**自環境で1度だけ換算し、以後はトークンで運用する。**

| 判断 | ドル建て(API従量) | トークン建て(定額レーン) |
|---|---|---|
| cold cache警告の発火下限 | 再構築費 $0.5 以上 | 直前リクエストからの間隔がTTL超、かつ `cache_creation_input_tokens` ≥ 25,000 |
| 単発の暴走ガード | $5 超 | `cache_creation_input_tokens` ≥ 250,000 **または** `output_tokens` ≥ 100,000(費目で単価が2.5倍違うので合算せず、いずれか先に超えた方で発火させる) |
| プロンプト単価テール | p50 ≤ $1 / p90 ≤ $8 | 総トークン(input+cache write+cache read+output)の p50 / p90 を自環境で28日測って初期値とする。単価差があるため絶対値の横比較には使わず、**自分の分布からの逸脱**で読む |
| TTL系施策の deprioritize | 再構築費が1日$5未満 | 1日の `cache_creation_input_tokens` 合計が250,000未満、または全キャッシュ書込の10%未満(**後者は単価もレーンも介在しない**のでこちらを主に使う) |
| 起動固定費の悪化 | — | 新規起動セッションの初回リクエスト入力合計。同一モデル内で前月比。数万トークン規模の増加はMCPツール定義の肥大を疑う |

**予算段階(50/80/100%)にはトークン建ての等価物が無い。** 定額レーンで対応するのは5時間枠・週次上限の消費率であり、これはトランスクリプトのトークン量からは計算できない(上限値が公開されておらず、枠の起点も分からない)。`/usage` が表示する枠の消費状況を直接読む — ここだけはjq経路が閉じないと認めたうえで、段階運用の起点を `/usage` に置く。トークン量から上限%を推定する式を自作しない(根拠のない分母は誤爆を生み、大原則7の「誤爆1回で計測系の信頼が死ぬ」に直結する)。

## 更新規律

- 価格・倍率は四半期ごと、または価格改定アナウンス時に再確認する。**次回の確定イベント: 2026-08-31のSonnet 5導入価格終了**。
- 実測値は自環境での再測定値が得られ次第そちらを正とし、本ファイルの値は「初期の事前分布」へ降格させる。
- 数値が変わっても「行動変容が目的関数」「事実を永続化し導出を保存しない」「支配費目が打ち手を決める」「自動ブロックしない」という安定原則はSKILL.mdに残す。
