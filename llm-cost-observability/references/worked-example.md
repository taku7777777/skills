# llm-cost-observability 適用例

## 題材

架空の予約管理SaaS「ヨヤクル」の開発チーム4名(バックエンド2・フロントエンド1・SRE 1)。全員がClaude Codeをサブスクリプション(Team相当)で半年使用。月次請求が3ヶ月で約2倍になり、経営から「何に使っているのか説明してほしい」と求められたが誰も答えられない。一方でメンバーの1人は費用を気にしてエージェントの利用自体を控える萎縮が起きている。

## 入力

- 依頼: 「チームのClaude Code利用費を見える化して、週次でレビューする運用を作りたい」
- 手元にあるもの: 月次請求書、各自の `/usage` のスクリーンショット。OTel未導入
- 体制: **定常運用**に使えるのはリーダー1名・週30分まで。**初期構築**は別枠として、SREが半日 × 2回まで確保できる
- 制約: 追加SaaS契約なし。モデル利用を自動で制限する統制は(メンバーの反発があり)不可

**工数の分離を最初に行う**(これをしないと「週30分」に構築費が押し込まれ、計画が破綻する):

| 費目 | 内容 | 見積り | 誰が |
|---|---|---|---|
| 初期構築(1回限り) | OTelエクスポータ有効化+収集先の用意、statuslineスクリプトの作成と4名への配布、cold cache警告の実装 | SRE 半日 × 2 | SRE |
| ハーネス変更の承認 | statusline・hooks・`settings.json` はHARDゲート対象。チームで合意してから配布(`harness-engineering`) | 30分 × 1回 | チーム全員 |
| 定常運用(毎週) | 週次レビュー(数字の読み・施策台帳の更新・高額テール1件のexplain) | 25分 | リーダー |
| 定常運用(毎週) | 計測ヘルス確認(欠報・鮮度) | 5分 | リーダー |

ゼロ週目の初手は基盤ではない: `/status` でレーン確認、`/context` で起動固定費、`~/.claude/projects/**/*.jsonl` を jq で費目分解(`data-sources.md`)。ここまでは構築工数ゼロで当日中に終わり、**この結果を見てから**初期構築に着手するかを決めた。

## 各ステップでの判断

**ステップ1(請求レーンと手段)**: `/status` で全員サブスクリプションレーンを確認。設計書の冒頭に「これから出す$はAPI単価換算値であり、請求書の額ではない」を固定した(混同すると『換算$が予算超過だから送信を止めろ』という誤った統制に直結する)。あわせて希少資源を言語化 — このチームで効くのはドルではなく**5時間枠と週次上限の消費速度**であり、成果は「請求$が減った」ではなく「上限に当たって手が止まる回数が減った」で報告すると決めた。閾値は `evidence.md` のトークン建てを採用(ドル建てでは一度も発火しない)。
まず基盤ゼロで測った: 各自のローカルトランスクリプトを jq で費目分解(`data-sources.md`)したところ、4名中3名で cache write が構成比の35〜48%を占め、TTL内訳は全員 `ephemeral_1h` に偏る(=定額レーンの1時間TTLが効いている)ことを確認。この結果を根拠に、ようやく導入ステージ判断表でステージ3を選定した — チーム帰属が必要なのでOTelメトリクス(user・部門属性つき)を最小構成で有効化し、per-prompt粒度は各自のstatuslineに任せる。日次境界はローカル日に固定し(トランスクリプトの `timestamp` はUTCなので変換を1箇所に閉じた)、請求書突合のときだけ換算する。

**ステップ2(指標設計)**: 定常運用の週30分で回せる4指標に絞った — ①日次コスト(ユーザー別・分布つき)②プロンプト単価p50/p90/p99(各自statusline由来)③支配費目分解(input/output/cache read/cache writeの構成比)④モデル構成比。「平均$/人」は指標にしない(大原則4)。サブエージェント費はspawn元プロンプトの因果総コストへ含める意味論を先に文書化し、構成比集計との二重加算を禁じた。

**ステップ3(介入設計)**: 3層で配置。ambient=statusline 1行(本日累計・燃焼レート・キャッシュ失効の絶対時刻)を全員に配布。just-in-time=cold cache警告(再構築が下限量以上のときだけ「新セッションの方が安い」と代替行動を名指す。定額レーンなので下限はトークン建て=`cache_creation_input_tokens` 25,000)と枠消費の段階警告(定額レーンなので予算$ではなく `/usage` の5時間枠・週次上限の消費率で50/80/100%)。statusline と hook の配布は `settings.json` への変更にあたるため、`harness-engineering` のHARDゲートとしてチーム全員の合意を取ってから入れた(コスト削減を理由に無断で足さない)。リーダーは当初「100%で送信を止めたい」と要望したが、大原則7(誤爆1回で計測系の信頼が死ぬ・API換算は購読の実上限ではない)を示して「100%時は当番が緊急以外を翌日へ回すよう声をかける」運用に変更(禁じたのは計測ツール側の自動停止であって、請求側のハードキャップは別レイヤ — 本チームは全員サブスクのため設定対象が無く、この時点では不要と整理した)。萎縮対策として「予算内は使い切ってよいヘッドルーム」「counter-metricは手戻り率」を設計書に明文化した。

**ステップ4(explain)**: 初週の高額テールはp99相当の1件 — `data-sources.md` の離席ギャップ集計(再書込トークンの降順)にかけると、間隔94分・`cache_creation_input_tokens` 41万で単独首位。費目内訳もcache write 91%。昼の全社会議(90分)後にそのまま巨大セッションを再開した1件だった。「誰の指示が長かったか」ではなく離席イベントが原因と特定し、再開・分割の運用は `context-economy` へ接続。モデル引き下げ案はこの週は見送り(モデル構成比は2番手の費目で、施策は同時2本以下の規律を守る)。

**ステップ5(週次レビュー)**: テンプレートで初回レビューを実施。施策1本目「失効前通知の導入」を台帳へ登録(仮説: 離席起因の再構築費が減る / 判定日: 2週後 / counter-metric: プロンプト数の減少=萎縮の再発が起きないこと)。「先週比+18%」の変化は、どのレバーでも説明できない部分が新メンバーのオンボーディング(外生ショック)で説明できると記録してから解釈した。

**ステップ6(ヘルスとROI)**: 第2推定器=ローカルトランスクリプトのjq集計とOTelメトリクスの突合(乖離±10%を監視、ゲートにはしない。全員サブスクなので請求書は突合相手にならない — 換算値と請求額は足せない)。OTel欠報は月曜朝にチェック。撤退基準を最初から明文化 — リーダーの**定常**工数が週30分を超える状態が1ヶ月続く、または四半期の検証済み削減が運用コストに見合わなければ、ステージ2(各自statuslineのみ)へ縮退する。初期構築工数(SRE 1人日)はROIの分母に一度だけ算入し、四半期で償却されたかを判定する。

## 成果物(抜粋)

```markdown
# ヨヤクル開発チーム LLM利用コスト計測・介入設計書
## 1. 請求レーンとデータソース
- 全員サブスクリプション。希少資源は5時間枠・週次上限の消費速度。本書の$はAPI単価換算値であり請求額ではない(送信停止の根拠に使わない)
- 閾値はトークン建て(ドル建ては本レーンで発火しない)。枠の消費率だけは `/usage` 由来
- OTel(user・費目・モデル別、ローカル日)+ ローカルトランスクリプトのjq集計 + 各自statusline
## 2. 指標定義
| 指標 | 定義 | 健全域 | 読み方→行動 |
|---|---|---|---|
| 日次トークン | ユーザー別・分布つき | 直近4週p90以内 | 超過日はexplainへ |
| プロンプト規模 | 総トークンのp50/p90/p99 | 自環境28日の初期分布 | p99テールを週1件分解 |
| 支配費目分解 | 費目構成比 | — | 構成比の変化=動いたレバーの裏付け |
| モデル構成比 | モデル別トークン比(`<synthetic>` 除外) | — | 引き下げ施策の事前・事後比較 |
| 枠消費率 | `/usage` の5時間枠・週次上限 | 週次上限に当たる回数0 | 段階運用の起点 |
## 3. 介入一覧(必須3列。文面は下へ)
| 介入 | 層 | 発火条件 |
|---|---|---|
| statusline | ambient | 常時 |
| cold cache警告 | just-in-time | TTL超間隔 + cache write 25,000トークン超 |
| 枠消費の段階警告 | just-in-time | `/usage` の枠消費率 50/80/100% |

- statusline: 「本日<トークン>・燃焼<レート>・失効HH:MM」/ conversion判定なし
- cold cache警告: 「再構築≈<量>。続きでなければ新セッションが安い」/ conversion=発火後の新セッション開始 / 抑制=セッション一回性
- 枠消費の段階警告: 「100%: 当番が翌日送りを確認(停止しない)」/ conversion=翌日送りの実施 / 抑制=段階ごと1回
## 4. 段階運用
- `/usage` の枠消費率で 50/80/100%。100%でも送信は止めない — 理由: 換算値と請求の乖離、誤爆時の信頼喪失
## 5. 施策台帳
| 施策 | 仮説 | 期待効果 | 判定日 | counter-metrics | verdict |
| 失効前通知 | 離席起因の再構築が減る | 週のcache write −25% | +2週 | プロンプト数減少なし | (判定日に記録) |
## 6. 計測ヘルスとROI
- 第2推定器: ローカルjq集計とOTelを±10%突合。欠報: 月曜朝チェック
- 撤退基準: 定常工数週30分超が1ヶ月 or 四半期ROI<1 → ステージ2へ縮退。初期構築SRE1人日は分母に一度算入
```

## この適用で変わったこと

- 経営への説明: 「わからない」→ 費目構成と分布(p50/p90/p99)で説明可能に
- 着手の速さ: 依頼当日にjq集計だけで支配費目(cache write)を特定。基盤構築の判断はその結果を見てから下せた(構築が先だったら1週間は何も分からないままだった)
- スパイクの検知: 月次請求書(最大30日遅れ)→ 当日のstatusline・段階警告
- 初月の結果: 離席起因の再構築が週41万→12万トークン(施策1本、判定日にwin記録)。週次上限に当たった回数が2回→0回。プロンプト総数は減らさず — 萎縮させずに削減する、という当初の狙いをcounter-metricで確認できた
- 「見たが行動が変わらない」の検出: cold cache警告のconversionが初週28%→文面改訂(再構築量を先頭へ)で41%に改善
