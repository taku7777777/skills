# 依頼設計の経済性(prompt-economy)スキル

Anthropic公式のClaude Codeベストプラクティス・コスト管理ガイダンスと、metsuke(Claude Code利用コストの全ログ実測に基づく行動変容システム)の知見を統合した、AIエージェントへの「1回で通す依頼」の設計と迷走の早期停止のプロセス。

領分の境界: プロダクト要件の発見・定義は `requirements-definition` の領分(本スキルが扱うのはエージェントへ渡す1回の依頼の設計)。CI・hooks・検証ゲートといった常設基盤の整備は `harness-engineering`(本スキルは1回の依頼に検証手段をどう同梱するか)。セッション・キャッシュ・compactの運用は `context-economy`、モデル選択とサブエージェント委任の構成は `delegation-economy`、依頼単位のコスト計測と帰属は `llm-cost-observability` の領分。これらは「計測 → 気づき → 行動 → 再計測」のループを構成し、本スキルは「依頼の仕方」という行動側を分担する。

定額プランでの読み替え: 定額購読レーンには「依頼1件の実請求額」という概念が無く、希少資源はドルではなく**セッション枠と週次上限の消費速度**になる(公式に「5時間ローリング窓+週次窓」と窓長が明記されているのはTeams/Enterpriseのシート許容量。Pro/Maxでは session limit / weekly limit として案内され窓長の記載はない。自分のレーンは `/status` で確認。レーン判定と換算値の扱いは `llm-cost-observability`)。本スキルが動かす対象 — 曖昧依頼が誘発する広域探索、手戻りで再送される履歴、サブエージェントの生成量 — はすべてトークンで測られるため、機構も打ち手も1つも変わらない(便益が請求減ではなく枠の節約として現れるだけ)。以降のドル建て表現は「枠の消費速度」へ読み替える。トークン建ての基準線の取り方は `references/evidence.md`。

## 大原則

1. **1プロンプト=その指示が引き起こす因果総コストで考える。** 依頼文の長さはコストの説明変数にならない(数十文字の指示が数ドルになる実測もあるが、その内訳はほぼ離席後のキャッシュ再構築であり、依頼設計では動かない — 条件つきの実測値は `references/evidence.md`、対処は `context-economy`)。依頼設計が動かせるのは指示が誘発する探索・生成・手戻り・サブエージェント費であり、そこが依頼の因果コストの本体になる。詳細なブリーフに使う数百トークンは、広域探索や手戻りを1回防げば桁で回収できる保険。
2. **検証手段の同梱が最大のレバー。** エージェントは「できたように見えた」ところで止まる。pass/failを機械判定できるチェック(テスト・入出力例・終了コード)を依頼に同梱すれば、検証ループはエージェント側で自動で閉じる。同梱しなければ人間が検証ループになり、全ミスが人間の発見待ち=もう1往復分の課金になる。
3. **曖昧さは広域スキャンとして課金される。** 「改善して」「直して」型の依頼は探索コストへの白紙委任。対象・完了定義・スコープ制約を明示した依頼は最小のファイル読みで済む。書かなかった要素は、エージェントの推測と探索で高く補われる。
4. **手戻りは複利で課金される。** 失敗アプローチはコンテキストに残り、以後の全ターンで再送・課金され、以後の出力も汚染する。同じ問題で2回訂正して直らなければ、/clearして学びを織り込んだ依頼で再開する方がほぼ常に勝る(公式ガイダンス)。数えるのは**訂正**(指示を誤読され、対象・スコープ・前提を差し戻した回数)であって、依頼どおり検証して外れた**棄却仮説**の数ではない(修正を指示して直らなかった回は、デバッグ中でも訂正として数える) — 棄却仮説は進捗であり、次のブリーフへ持ち越す資産(ステップ5)。「ここまでの文脈がもったいない」は、毎ターン課金される誤謬。
5. **中断は失敗ではなく、最も安い操作。** 誤方向に気づいた瞬間にEscで止める — コンテキストは保持されたまま軌道修正できる。誤った経路を丸ごと捨てるなら/rewindを優先する(/compact・/clearとの使い分けと相対コストの根拠は `context-economy`)。迷走を放置した分だけ、コスト分布のp99側に高額プロンプトが育つ。
6. **段取りの重さはタスクの不確実性に合わせる。** 期待するdiffを一文で言えるならplanモードを飛ばす(planにもオーバーヘッドがある)。大きめの機能は依頼の前にSPEC.mdを固め、実装はフレッシュセッションで行う。常時plan・常時spec先行は過剰プロセスで、常時直行は手戻りの複利払い。
7. **依頼設計自体を過剰最適化しない。** 目的は一発通過率と手戻りの削減であって、完璧なブリーフではない。counter-metricsとして依頼作成にかける人間の時間・着手までの遅延を併記する。1行修正にテンプレート一式を持ち出さない。依頼文のトークン節約も目的にしない(支配項は探索と手戻り)。

## ワークフロー

### ステップ1: 依頼の重さを分類する

| 状況 | 段取り |
|---|---|
| 期待するdiffを一文で説明できる | 直行。planモード不要。ブリーフは最小(対象+完了定義+検証コマンド) |
| 症状はあるが原因が不明 | 調査と修正を分ける。調査依頼には「仮説と根拠を報告して止まれ」という完了定義を与える |
| 変更が複数ファイル・複数工程に及ぶ | planモードで計画を確認してから実装に進ませる |
| 大きめの機能・仕様自体が未確定 | spec先行: エージェントに自分をインタビューさせてSPEC.mdを書かせ、実装はフレッシュセッションで |

- 無関係なタスクを同じ依頼・同じセッションに混載しない(kitchen sinkセッション)。セッション分割・/clearの実務は `context-economy`
- 迷うケースの判定は `references/brief-patterns.md` の「依頼の重さ判断表」に従う

### ステップ2: ブリーフを組み立てる(完全指定)

6要素で構成する。欠けた要素は探索と手戻りで払うことになる:

1. **完了定義**: 何ができたら終わりか一文で
2. **対象と場所**: 触るファイル・関数・ディレクトリ。参照すべき既存パターン(「◯◯と同じ作りで」)
3. **現況と再現手順**: 症状、再現条件、観測された事実。事実と推測を区別して書く
4. **受け入れ条件**: 機械的に判定できる形(入出力例・テスト・終了コード)
5. **検証コマンド**: エージェント自身が実行して確認できるコマンドと期待出力
6. **スコープ制約**: 触ってはいけない範囲・してはいけない操作・差分の上限

チェックリストと記入例は `references/brief-patterns.md`。

### ステップ3: 検証手段を同梱する

- 受け入れ条件は入出力例で書く(例: 「validateEmailを書け。user@example.com→true、user@.com→false。実装後にテストを実行」)。「正しく」「きれいに」という形容詞は受け入れ条件にならない
- **証拠を出させる**: 「テストを実行し、出力を貼って完了報告せよ」を依頼に含める。宣言だけの「完了しました」を受理しない
- 巨大出力は前処理する: 数万行のログ・テスト出力を本体セッションに生で読ませない。grep等で絞る指示を依頼に書くか、verbose解析はサブエージェントへ切り出す(委任構成は `delegation-economy`)
- 同じ検証指示を依頼のたびに書いていると気づいたら、hooks・CIへの常設化を検討する — その基盤整備は `harness-engineering` の領分

### ステップ4: 実行中の監視と早期中断

- 着手直後の挙動を見る。意図しない広域探索・想定外ファイルの編集が始まったら**即Escで止めて**軌道修正する(コンテキストは保持される)。「もう少し様子を見る」は様子見自体に課金される
- 訂正は具体的に、1回で伝える(「そこじゃない」ではなく「対象は src/X。YをZの後に呼ぶ順序が問題」)
- 誤った経路を丸ごと捨てるなら/rewind(判断表は `context-economy`。本スキルは「捨てる判断を先送りしない」ことだけを扱う)
- 依頼時に中断条件を仕込んでもよい: 「読む必要のあるファイルが10を超えたら、計画を報告して指示を待て」
- ただし**走査そのものが完了定義である依頼**(公開契約・APIシグネチャの変更影響、全利用箇所の洗い出し、要件の棚卸し)には件数上限を掛けない。途中で切ると見落としがそのまま下流の手戻りになる — 中断条件は「読了後に一覧を報告して止まれ」の形にする(レビューで読むべき範囲の基準は `impl-review`)

### ステップ5: 見切りと再依頼

- **同じ問題で2回訂正して直らなければ、3回目は打たない**。/clear(または新セッション)し、失敗から学んだことを織り込んだ改良ブリーフで再依頼する
- 再依頼の前に、誤修正の未コミット変更を破棄・退避し、作業ツリーを既知の状態へ戻す
- 失敗をブリーフ要素の欠落へ帰着させる: エージェントはどこを誤解したか → 6要素のどれが欠けていたか → 改良ブリーフに明記する
- **捨てるのはコンテキストであって、確定した事実ではない**。原因の目星・切り分け結果に加え、却下した案と棄却した仮説(「Xではないと確認済み」)を改良ブリーフへ書き写す — 何を否定済みかが次の探索空間を狭める(調査中の仮説ログの形式は `systematic-debugging`)
- 「ここまでの文脈がもったいない」は誤り。失敗アプローチを含むコンテキストは資産ではなく、毎ターン再送・課金される負債(大原則4)

### ステップ6: セルフチェックと計測への接続

- [ ] 受け入れ条件は第三者(エージェント自身)が機械的に判定できるか
- [ ] 触ってはいけない範囲を明示したか
- [ ] このタスクにこの段取りは重すぎないか(1行修正にブリーフテンプレートは不要)
- [ ] 一発通過率・訂正回数・中断の頻度を把握しているか — 依頼単位のコスト分布(平均でなくp50/p90/p99)と高額プロンプトの原因分析は `llm-cost-observability` で行い、結果を依頼設計の改善へ還流する

## 成果物フォーマット

依頼文の設計・改善を依頼された場合は、散文の助言で終えず書き直した依頼文そのものを出す:

```markdown
# タスクブリーフ: <完了定義を一文で>
## 対象と場所(触るファイル・参照パターン)
## 現況と再現手順(事実と推測を区別)
## 受け入れ条件(機械判定可能な入出力・テスト)
## 検証コマンド(実行し証拠を出す)
## スコープ制約・禁止事項
## 中断条件(該当時)
```

既存の依頼・セッションの診断では、ビフォー/アフターの依頼文と「どの要素の欠落が何の浪費を生んだか」の対応表を出す。

実例: `references/worked-example.md`
