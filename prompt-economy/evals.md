# prompt-economy 評価セット

スキルの効果を測定するための評価定義。運用方法は skill-improvement スキルの
references/eval-template.md を参照。

追加の実行可能なraw fixtureとhidden rubricは [task manifest](../quality/tasks/cases.jsonl) に登録済み。実行時は `scripts/eval_tasks.py prepare` で分離し、rubricをexecutorへ見せない。

## 検証シナリオ

### S1: 曖昧依頼のビフォーアフター設計(勤怠SaaSのCSVエクスポート)
- **タスク**: 「架空の勤怠管理SaaS。管理画面の月次CSVエクスポートが30秒以上かかりタイムアウトすることがある。担当者はClaude Codeに『エクスポートが遅いので速くして』と依頼しようとしている。この依頼を1回で通る形に設計してほしい。リポジトリはRails、エクスポート処理は `app/services/export/` 配下、既存テストは `spec/services/export/` にある。原因はまだ特定されていない」
- **スキルなしで予想される欠落**: 機械判定可能な受け入れ条件(目標時間と測定手順)、検証コマンドと証拠要求、スコープ制約(スキーマ・公開契約を触らない)、原因未特定タスクでの調査/修正の分離、中断条件。素のモデルは「もっと具体的に書きましょう」と一般論+文言の膨らましで終わる。
- **合格条件**:
  - [ ] 受け入れ条件が、対象データ量(件数・期間)と計測コマンドを伴う時間閾値、または遅延条件を再現してpass/failになる性能テストのいずれかで書かれている(「既存テストが全件パス」だけは不可)
  - [ ] 触ってはいけない範囲(DBスキーマ・公開APIのレスポンス形状等)と、制約外の変更が必要になった場合に変更せず報告して止まる手続きが明示される
  - [ ] 検証コマンドの実行と出力の貼付(証拠)を要求している
  - [ ] 原因未特定のため調査と修正を分け、調査依頼に中断条件(読むファイル数の上限・時間予算・仮説を報告して止まる指示)が具体的に付いている
  - [ ] ブリーフ作成自体の過剰最適化への注意(counter-metric)に言及している(人間判定)

### S2: 大きめ機能でのspec先行判断(請求書サービスの多通貨対応)
- **タスク**: 「個人開発の請求書サービスに多通貨対応(表示・換算・丸め・既存データの移行)を追加したい。Claude Codeに丸ごと任せたいが、どう依頼を組み立てるべきか。なおClaude CodeはMaxプラン(定額)で使っていてAPIの従量課金ではないので、節約の話をされてもピンとこない」
- **スキルなしで予想される欠落**: diff一文テストによる「直行しない」判断、インタビュー→SPEC.md→フレッシュセッション実装の段取り、分割後の各依頼への検証手段の同梱、常時spec先行への過剰プロセス警告、定額レーンでの読み替え。素のモデルは巨大な単一プロンプトの雛形か、planモードの一般的な推奨で終わる。定額と言われると「課金されないのでコストは気にしなくてよい」と流すか、逆にドル建ての目安をそのまま持ち込む。
- **合格条件**:
  - [ ] 段取りの重さを明示的な基準(期待するdiffを一文で言えるか、原因・仕様が確定しているか等)で判定し、その判定結果として分割・spec先行を選んでいる(「大きいから慎重に」ではない)
  - [ ] spec先行の段取り(エージェントへのインタビュー→SPEC.md→実装はフレッシュセッション)が提案される
  - [ ] 分割後の各依頼に機械判定可能な受け入れ条件(丸め・換算の入出力例など)を同梱する方針がある
  - [ ] データ移行部分にスコープ制約・検証(件数一致・ロールバック確認など)が付く
  - [ ] 定額レーンのため便益を請求額の削減ではなく**枠(セッション上限・週次上限)の消費速度**で述べ、ドル建ての目安をそのまま持ち込まない。かつ「定額だからコストは気にしなくてよい」で流さず、段取り自体は1つも変わらないことを示す
  - [ ] すべてのタスクにspec先行を課すのは過剰プロセスだという限定がある(人間判定)

### S3: 3回目の訂正への途中介入(検索バグ修正の相談)
- **タスク**: 別作業(ログ整形スクリプトの相談)の会話中に、ユーザーが「そういえば別セッションでエージェントに検索機能のバグ修正をやらせてるんだけど、2回直しを指示してもまだ変なんだよね。もう一回だけ具体的に指示すれば直りそう。どう書けばいいかな」と聞いてくる。
- **スキルなしで予想される欠落**: 2回訂正ルール(3回目を打たない)、失敗アプローチによるコンテキスト汚染と複利課金の指摘、/clear+学びを織り込んだ再依頼という代替行動、確定した事実(棄却仮説・却下案)の持ち越し。素のモデルは頼まれたとおり3回目の訂正文を添削してしまうか、「デバッグ中だから試行はまだ続けてよい」として見切りを回避する。
- **合格条件**:
  - [ ] 3回目の訂正文を作る前に、見切り(2回訂正ルール)を明確に提案する
  - [ ] 失敗アプローチがコンテキストに残り、以後のターンで再送・課金され出力も汚染することを根拠に挙げる
  - [ ] /clear(または新セッション)+2回の訂正から得た学びを織り込んだ改良依頼、という具体的な再開手順を示す
  - [ ] /clear前に、確定した事実 — 原因の目星・切り分け結果に加え、**却下した案と棄却した仮説(「Xではないと確認済み」)を理由つきで** — 改良ブリーフへ書き写すよう指示する(捨てるのはコンテキストであって確定した事実ではない)
  - [ ] 「修正を指示して直らなかった」2回を訂正2回として扱い、「デバッグ中だからまだ試してよい」として見切りを先送りしない
  - [ ] 介入が本題(ログ整形)への回答と分離され、3回目の訂正文の添削を先にしない(人間判定)
