## 依頼の重さ判断表

| 判定質問 | Yes | No |
|---|---|---|
| 期待するdiffを一文で言えるか | 直行(planなし)。ブリーフは対象+完了定義+検証コマンドの3点に圧縮 | 次の質問へ |
| 原因・修正箇所は特定済みか | 修正依頼として6要素ブリーフを書く | 調査と修正を分離。調査依頼の完了定義は「仮説と根拠の報告」であり修正ではない |
| 変更は単一モジュール内に収まるか | 通常ブリーフ | planモードで計画確認を挟む |
| 仕様・要件は確定しているか | 上記いずれか | spec先行: インタビュー→SPEC.md→フレッシュセッションで実装。要件自体の発見は `requirements-definition` へ |

補助判定:

- 同じ種類の依頼を3回以上繰り返している → テンプレート化する(本ファイルをベースに自分の定型を作る)
- 依頼の中に「ついでに」が入っている → 分割する。「ついで」は広域スキャンとスコープ逸脱の誘発剤
- 依頼を書くのに完了定義が書けない → 依頼の問題ではなく要件の問題。先に要件を固める

## ブリーフ6要素チェックリスト

| # | 要素 | 確認質問 | 欠けたときに起きること |
|---|---|---|---|
| 1 | 完了定義 | 「何ができたら終わり」を一文で書いたか | エージェントが自分で終了条件を推測し、過剰実装または早すぎる完了宣言 |
| 2 | 対象と場所 | ファイル・関数・ディレクトリを名指ししたか。参照すべき既存パターンを指したか | 広域スキャン。既存機構と重複する新規実装 |
| 3 | 現況と再現手順 | 事実(観測)と推測を区別して書いたか | 推測を事実と誤読して誤った箇所を修正 |
| 4 | 受け入れ条件 | 機械判定できる形か(下記パターン集) | 「できたように見えた」ところで停止。人間が検証ループ化 |
| 5 | 検証コマンド | 実行コマンドと期待出力を書いたか。「証拠を貼れ」と書いたか | 宣言だけの完了報告。ミスの発見が次ターンに先送り |
| 6 | スコープ制約 | 触ってはいけない範囲・禁止操作・差分上限を書いたか | 「ついで」の書き換え。関係ないファイルの整形・リネーム |

## 受け入れ条件パターン集

機械判定できる形への落とし方。上ほど強い:

| パターン | 書き方の例 | 向くタスク |
|---|---|---|
| テスト指定型 | 「`tests/queue/retry.spec.ts` のskipを外し、パスさせる。既存テストは全件パスのまま」 | バグ修正・仕様変更 |
| 入出力例型 | 「`parse("2026-07-30")` → `Date(2026,7,30)`、`parse("")` → `null`、`parse("30/07")` → 例外」 | 関数・API追加 |
| 終了コード型 | 「`npm run build && npm run lint` が終了コード0」 | リファクタ・依存更新 |
| 差分計測型 | 「変更前後で `npm run bench` のp95が20%以上短縮。悪化したベンチがゼロ」 | 性能改善 |
| 状態観測型 | 「マイグレーション後に `SELECT count(*)` が変更前と一致。ロールバックで元に戻る」 | データ移行 |
| スクリーンショット型 | 「変更後の画面キャプチャを添付し、ズレの有無を報告」 | UI変更(機械判定の下限。可能ならビジュアルリグレッションへ) |

禁止形: 「正しく動く」「きれいにする」「いい感じに」「壊さないように」— すべて判定不能。判定不能な条件は、エージェントの自己申告を受け入れると宣言しているのと同じ。

## スコープ制約の書き方

- **触らないリスト**: 「`db/schema.rb`・公開APIのレスポンス形状・設定ファイルは変更しない」
- **禁止操作**: 「テストの削除・skip・期待値の書き換えは禁止。テストが間違っていると考えた場合は変更せず報告」
- **差分上限**: 「差分が10ファイルを超える見込みになったら、着手せず分割案を出せ」
- **逸脱時の手続き**: 「制約の外を変更する必要が出たら、変更せず理由を報告して止まれ」— 禁止だけでなく逸脱時の正しい行動を与える
- **件数上限を掛けない例外**: 走査そのものが完了定義である依頼(公開契約・APIシグネチャの変更影響、全利用箇所の洗い出し、要件の棚卸し)では、上限で切ると見落としがそのまま下流の手戻りになる。件数上限ではなく「読了後に一覧を報告して止まれ」という形の中断条件へ置き換える(レビューで読むべき範囲の基準は `impl-review`)
- 恒常的に守らせたい制約(毎回書いている制約)はhooks・CI・権限設定へ常設化する → `harness-engineering`

## 中断・再依頼の判断表

| 状況 | 操作 | 理由 |
|---|---|---|
| 方向違いに気づいた(実行中) | Escで即停止 → 具体的に軌道修正 | コンテキスト保持のまま最安で修正。様子見は様子見自体に課金される |
| 直近の経路を丸ごと捨てたい | /rewind | 誤った経路を以後のターンの課金対象から外す。/compact・/clearとの使い分けは `context-economy` |
| 訂正1回目 | 具体的な訂正を1回(場所・原因・期待を明示) | 曖昧な訂正(「違う」)は2回目の迷走を誘発する |
| 訂正2回目で直らない | 3回目を打たずに /clear +改良ブリーフ | 失敗アプローチがコンテキストを汚染。継続はほぼ常に負け(公式ガイダンス) |
| 依頼どおり検証した仮説が外れた | 訂正回数に数えない。次の仮説へ進む | 棄却は進捗。ただし「何を否定済みか」をその場でブリーフ側に書き足す |
| 再依頼の前 | 未コミットの誤修正を破棄・退避 | 汚れた作業ツリーの上の再依頼は誤修正を前提に積み上がる |
| 再依頼のブリーフ | 「前回の誤解」を明記(「Xではない。原因はY系統にある」) | 同じ誤解の再演を防ぐ。学びを織り込まない/clearはただのリトライ |

「訂正2回」の数え方: 数えるのは**こちらの指示が誤読され、対象・スコープ・前提を差し戻した回数**である。「この仮説を検証して結果を報告せよ」と依頼して外れた回は訂正ではなく進捗なので、この2回に数えない(連続する棄却はデバッグの正常な進み方であり、仮説が続けて外れたときに疑うべきは前提のほう — その判断は `systematic-debugging`)。逆に、**修正を指示して直らなかった回は、デバッグ中であっても訂正として数える**。見る場所の取り違え・スコープ逸脱・既存機構の見落としが2回続いたなら、題材がバグ調査であっても通常どおり見切りの対象になる。

sunk costの扱い: 「ここまでの探索がもったいない」と感じたら、この探索で確定した事実を改良ブリーフに書き写す — 原因の目星・切り分け結果に加え、**却下した案と棄却した仮説(「Xではないと確認済み。理由は◯◯」)を含める**。棄却仮説は探索空間を狭める資産であり、落とすと再依頼先が同じ袋小路を辿り直す(調査中の仮説ログの形式は `systematic-debugging`)。書き写さないのは失敗した経路の生の試行錯誤(誤った差分・誤読された指示・その上に積んだ説明)だけである。コンテキストではなくテキストとして持ち越すのが最安の再利用。

## 巨大出力の前処理パターン

| 状況 | パターン |
|---|---|
| テスト・ビルドの大量出力 | 全出力をファイルへ落とさせたうえで「失敗したテストの名前とエラー行だけを報告」と依頼に書く。恒常化するならhookでfailのみ返す(→ `harness-engineering`) |
| 長大なログの解析 | 原文をファイルに残したまま、grep・tail等で絞る指示を依頼に含める(「ERROR行と前後3行のみ」)。生ログをコンテキストへ貼らない |
| verboseな調査(依存関係・全文検索) | サブエージェントへ切り出し、本体には要約だけ返させる(構成は `delegation-economy`) |
| 大きな成果物の生成(長文ドキュメント等) | 目次→承認→本文の2段依頼にし、方向違いの長文生成を防ぐ |

**原文の保全と、コンテキストへの提示を分ける。** 「要約させる」はコンテキストに載せる量の話であって、原文を捨てる指示ではない。スタックトレース・エラーログを要約で置き換えると調査の一次証拠が失われる(症状は原文のまま記録するのが `systematic-debugging` の規律)。依頼にはこの形で書く:

> `npm test > /tmp/test-full.log 2>&1` で全出力をファイルへ落とし、報告には失敗したテスト名とエラー行だけを載せよ。スタックトレース全文が必要になったら `/tmp/test-full.log` の該当箇所だけを読め。

原文は永続化されたまま残り、毎ターン再送されるのは要約だけになる。両立しないのは「要約して原文を捨てる」ときだけである。

## ビフォー→アフター短例集

worked-exampleより小さい例。パターンだけ掴む:

**例1(バグ修正)**
- Before: 「ログインがたまに失敗するので直して」
- After: 「`auth/session.ts` のセッション更新で、有効期限ちょうどのとき401になる(再現: `tests/auth/expiry.spec.ts` に追加したfailingテスト)。このテストをパスさせろ。既存テストは全件パスのまま。`auth/` の外は変更しない。`npm test -- auth` の出力を貼って完了報告」

**例2(小改修)**
- Before: 「CSVエクスポートに部署列も出るようにして」
- After: 「`export/csv.ts` の列定義に `department` を追加(`memberName` 列と同じ実装パターン)。ヘッダ行は `部署`。`tests/export/csv.spec.ts` の期待値を新列込みに更新してパスさせろ。列の並び順は末尾」

**例3(調査のみ)**
- Before: 「なんでビルドが遅いのか調べて」
- After: 「ビルド時間の内訳を計測し、上位3工程と短縮の仮説を報告して止まれ。コードは変更するな。読むファイルが20を超えそうなら計画を先に出せ」

## アンチパターン表

| アンチパターン | 何が起きるか | 修正 |
|---|---|---|
| 「改善して」「直して」の白紙委任 | 広域スキャン+推測修正。因果コストがp99入り | 6要素ブリーフ(最低でも対象+完了定義+検証) |
| 受け入れ条件なしの依頼 | 「できたように見えた」で停止、人間が検証ループ化 | テスト・入出力例・終了コードを同梱 |
| 訂正3回目 | 汚染コンテキストへの追加課金。以後の出力も劣化 | 2回で見切り、/clear+学び織り込み |
| 「もったいない」でEscをためらう | 誤方向の生成に課金し続ける | 中断は最も安い操作。即Esc |
| 全タスクplanモード・全タスクspec先行 | 段取りのオーバーヘッドが本体を超える | diff一文テストで直行を選ぶ |
| 依頼文のトークン節約 | 節約した文脈を探索で高く買い戻す | 削るのは冗長さであって情報ではない |
| 「ついでに◯◯も」 | スコープ逸脱と差分肥大 | 依頼を分割。ついでは次の依頼へ |
| 完璧なブリーフ作りに20分 | 依頼設計自体の過剰最適化 | counter-metric: 作成時間・着手遅延。軽いタスクは3点圧縮版で出す |
