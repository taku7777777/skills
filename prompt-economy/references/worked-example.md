# prompt-economy 適用例

## 題材

架空のECバックエンド「カートワークス」。決済プロバイダへの支払いリクエストが失敗した際のリトライ処理に不具合があり、開発者が「決済リトライのバグ直して」という依頼でClaude Codeに投げた結果、3往復して未解決のまま高コストで終わった。このセッションを振り返り、1回で通るブリーフに書き直す。

## 入力

- 失敗セッションの記録:
  - 依頼原文: 「決済リトライのバグ直して」
  - ターン1: エージェントは決済関連の30ファイル超を探索し、リトライ回数の設定値を変更した(原因はそこではなかった)
  - 訂正1: 「回数じゃなくて、失敗した決済が二重に請求されることがあるのが問題」→ 冪等キーの仕組みを `billing/` 配下に新規実装(既存の冪等機構と重複)
  - 訂正2: 「既存の IdempotencyKey クラスがあるからそれを使って」→ 使ったが、リトライ間隔の指数バックオフも「ついでに」書き換えた。ここでセッションを閉じた
  - 因果コスト実測: このセッションの3プロンプトで$12.40(当該週のp99)。同種タスクの中央値は$1台
- 手元にあるもの: 障害チケットPAY-812(二重請求は決済プロバイダのタイムアウト後のリトライ時に集中、直近30日で7件)、`payments/retry.py`、既存の `payments/idempotency.py`(IdempotencyKey クラス)、`tests/payments/` のテストスイート(3分で完走)

## 各ステップでの判断

**ステップ1(重さの分類)**: 症状はあるが原因は未確定 → 調査と修正を分離する。ただし障害チケットで「タイムアウト後リトライ時の二重請求」まで絞れているため、調査依頼は「`payments/retry.py` とその呼び出し経路に限定して原因仮説を報告して止まれ」という完了定義つきの小さな依頼にした(大原則3)。planモードは使わない — 調査が終われば修正はdiffを一文で言える見込みのため(大原則6)。

**ステップ2(ブリーフ)**: 6要素で書き直した(成果物参照)。特に「対象と場所」へ既存の IdempotencyKey クラスを参照パターンとして明記した。訂正1(重複実装)の原因は、既存機構の存在を書かなかったことにあると帰着したため。

**ステップ3(検証手段)**: 受け入れ条件を「タイムアウト→リトライを再現するテストで請求記録がちょうど1件」という機械判定に落とし、`pytest tests/payments/ -k retry` の実行と出力の貼付を要求した。「二重請求が直ること」という判定不能な条件を排除した(大原則2)。

**ステップ4(実行中の監視)**: 依頼に中断条件「`payments/` の外を変更する必要が出たら、変更せず理由を報告して止まれ」を仕込んだ。前セッションの「ついで」の書き換え(指数バックオフ)の再発防止(大原則5、スコープ制約の逸脱時手続き)。

**ステップ5(見切りの帰着)**: 前セッションの3往復を6要素の欠落へ帰着した — 症状の限定なし(→30ファイル超の広域探索)、既存パターンの参照なし(→重複実装)、スコープ制約なし(→ついでの書き換え)。本来は訂正2回目で直らなかった時点で/clearすべきだった。継続していれば、汚染されたコンテキストへの課金がさらに積み上がっていた(大原則4)。再依頼の前に、前セッションの未コミット変更(リトライ回数・重複した冪等実装・バックオフ変更)をすべて破棄した。

**ステップ6(計測への接続)**: このタスクは週次コストレビューでp99の高額プロンプトとして検出されたもの。書き直し後の再実行は1往復で完了し、同種タスクの中央値レンジに収まった。高額プロンプトの検出・帰属の仕組み自体は `llm-cost-observability` の領分。

## 成果物(抜粋)

```markdown
# タスクブリーフ: タイムアウト後リトライでの二重請求をなくす
## 対象と場所
- 変更対象: payments/retry.py(必要なら payments/client.py まで)
- 参照パターン: payments/idempotency.py の IdempotencyKey を使う。新規の冪等機構を作らない
## 現況と再現手順(事実と推測を区別)
- 事実: 二重請求7件/直近30日。全件が決済プロバイダのタイムアウト→リトライ後に発生(チケットPAY-812)
- 推測: リトライ時に冪等キーが再生成されている(未確認。修正前にコードで確認し、仮説を一度報告する)
## 受け入れ条件
- タイムアウト→リトライを再現するテストを追加し、請求記録がちょうど1件になることを検証してパスさせる
- 既存の tests/payments/ が全件パスする
## 検証コマンド
- pytest tests/payments/ -k retry を実行し、出力を貼って完了報告する
## スコープ制約・禁止事項
- リトライ回数・バックオフ間隔は変更しない(別チケット)
- payments/ の外は変更しない。テストの削除・skipは禁止
## 中断条件
- payments/ の外を変更する必要が出たら、変更せず理由を報告して止まる
- 読むファイルが15を超えたら、計画を報告して指示を待つ
```

## この適用で変わったこと

- 往復: 3往復・未解決 → 1往復で完了
- 因果コスト: $12.40(週のp99)→ 同種タスクの中央値レンジ($1台)
- 副作用: 「ついで」の書き換えゼロ — スコープ制約と中断条件で構造的に抑止
- 再発防止: 「6要素の欠落 → 生じた浪費」の対応表をチームのブリーフテンプレートに反映した
