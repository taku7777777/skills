# Claude Code 利用ログ診断 — Palet バックエンド開発者1名・1週間

ログの数字だけで原因を特定できるところまで詰めました。ファイル・設定の変更は一切していません。以下はすべて提案です。

---

## 結論(3行)

1. **無駄の主因は「1日1セッション・8時間・コンテキストを畳まない」運用**です。リクエスト数(週214件)は多くありません。1リクエストあたりが重いのが原因です。
2. **チームSlackの仮説(CLAUDE.md を半分に削る)は的を外しています。** CLAUDE.md は 480 tok、プレフィックス全体の 1.2%。半分にしても週の削減額は 3 セントほどです。同じ場所にある **MCPツール定義 34,000 tok が CLAUDE.md の約 71 倍**を占めています。
3 週内のキャッシュミス12件は、**セッション開始5件 / 休憩によるTTL失効6件 / 水曜の `/model` 切り替え1件** に完全に分解できました。原因不明の穴はありません。

## 0. 数字の読み方について(先に前提)

ログに出ているのは **入力側のキャッシュ分だけ**です。出力トークンと非キャッシュ入力の記録がないため、請求額そのものは再現できません。以下の「%」は明示しない限りすべて **キャッシュ分入力コストに対する比率**です。

適用した単価(sonnet-4.6 = $3.00/MTok 入力、opus-5 = $5.00/MTok 入力):

| | sonnet-4.6 | opus-5 |
|---|---|---|
| キャッシュ書き込み(5分TTL, 1.25×) | $3.75/MTok | $6.25/MTok |
| キャッシュ書き込み(1時間TTL, 2×) | $6.00/MTok | $10.00/MTok |
| キャッシュ読み出し(0.1×) | $0.30/MTok | $0.50/MTok |

**ここで1点、直感に反する事実があります。** opus-5 は sonnet-4.6 の 1.67 倍(入力 $5 対 $3、出力 $25 対 $15)です。世代の古い Opus のような数倍差ではありません。つまり水曜のモデル切り替えの損失は「レートが跳ねたこと」ではなく「キャッシュを丸ごと捨てたこと」が主です(後述 P3)。

## 2. 「使い方は変えていない」のに1.7倍になった仕組み

キャッシュ読み出しコストは **リクエスト数 × 平均コンテキスト長** で決まります。同じペースで作業しても、セッションが2倍長引けば両方の項が増えるので、コストは約4倍になります。線形ではありません。

これは今回のログの中で実測できています。

| | 曜日 | 稼働時間 | リクエスト | 読み出し1件平均 | 読み出しコスト |
|---|---|---|---|---|---|
| S1 | 月 | 4時間18分 | 38 | **81,000 tok** | $0.90 |
| S2 | 火 | 8時間35分 | 52 | **222,000 tok** | $3.32 |
| S3 | 水 | 8時間05分 | 46 | 198,000 tok | (混在) |
| S4 | 木 | 7時間50分 | 44 | 183,000 tok | $2.26 |
| S5 | 金 | 6時間35分 | 34 | 105,000 tok | $0.98 |

S1 と S2 は**同じ作業(API改修)の初日と2日目**です。稼働時間は 2.0 倍、リクエストは 1.37 倍。それに対して読み出しコストは **3.7 倍**になっています。1リクエストあたりでは $0.036 → $0.111 で 3 倍です。

つまり「使い方は変えていない」と「請求が1.7倍」は矛盾しません。**同じ習慣のまま作業時間が伸びると、コストは超線形に増えます。** 加えて MCP サーバが9台でプレフィックスが 41,200 tok まで膨らんでいること、水曜午後に opus-5 を使ったことが乗っています。

## 3. キャッシュミス12件の原因分解

既定のキャッシュTTLは5分です。6件のギャップ(8分〜124分)はすべて5分TTL失効で説明できます。

| 日時 | 直前間隔 | 書き込み | 原因 | 回避可能か |
|---|---|---|---|---|
| 月 09:12 / 火 09:05 / 水 10:00 / 木 09:30 / 金 09:40 | — | 各 42,000 | セッション初回 | 不可(構造上必要) |
| 火 13:10 | 68分 | 268,000 | 昼休みでTTL失効 | **可** |
| 水 12:48 | 41分 | 151,000 | 昼休みでTTL失効 | **可** |
| 木 11:26 | 22分 | 88,000 | 中断でTTL失効 | **可** |
| 木 15:04 | 124分 | 246,000 | 長時間離席でTTL失効 | **可** |
| 金 14:35 | 92分 | 221,000 | 離席 + `/compact` | 一部(圧縮自体は有益) |
| 金 15:02 | 8分 | 57,000 | 短い中断でTTL失効 | **可** |
| **水 15:21** | **2分** | **274,000** | **`/model` によるモデル切り替え** | **可** |

**水 15:21 が診断の決め手です。** 間隔が2分しかないのでTTL失効ではありえません。15:20 に `/model` を実行しているので、原因はモデル切り替え一択です。プロンプトキャッシュはモデル単位に紐づくため、切り替えるとツール定義・システム・会話履歴のすべてが無効化されます。

**この12件が完全に説明できたことから、副次的な結論が1つ出ます。** 週内に CLAUDE.md が3回編集されていますが、「間隔が短く、モデル変更もないのにミスした」リクエストは1件も存在しません。**つまり CLAUDE.md の編集は測定可能なコストを一切発生させていません。** Slackの仮説はサイズの面でも編集回数の面でも空振りです。

一方で、**42,000 tok のセッション初回書き込みのうち 34,000 tok(81%)は MCP ツール定義**です。ここは削れます。

## 4. 行動変更の提案(優先度順)

---

### P1(最優先・効果最大)コンテキストを溜めない ─ セッションを切る / 畳む

**根拠:** キャッシュ読み出し 33.4M tok の 75%(25.1M tok)は蓄積した会話です。週内で `/clear` は0回、`/compact` は1回のみ。1リクエスト平均 165,000 tok。

**すでに本人のログの中に効果の実証があります。** 金曜 14:35 の `/compact` 直前のコンテキストは 221,000 tok。圧縮後、15:02 の書き直しは **57,000 tok** でした。**74%減**です。これは推定値ではなく実測値で、しかも本人のセッションで偶然観測されたものです(15:02 の8分ギャップがなければ見えませんでした)。

**やること — トリガーを3つ決めてください:**

| トリガー | 操作 | 理由 |
|---|---|---|
| タスクの区切り(バグ修正1件終わり→次へ) | `/clear` | 要約コストゼロ。前の文脈が不要なら最安 |
| 5分以上離席する前 | セッション終了 or `/compact` | 戻った時の書き直しが 250,000 tok ではなく 42,000〜60,000 tok になる |
| コンテキストが 100,000 tok を超えた | `/compact` | 以降のすべてのリクエストの読み出し単価が下がる |

**目標値は S1 のプロファイルに戻すことです。** 同じ作業を S1 は 81,000 tok/件で回していました。S2〜S4 は 183,000〜222,000 tok/件。恣意的な目標ではなく、同一データセット内の実績です。

**期待効果:** 読み出し 33.4M → 約18M(-45%)、加えて休憩時の書き直しも半減。合計で **キャッシュ分入力コストの25〜35%削減**(週 $5.5〜7.5 相当)。

**補足2点:**
- `/compact` は引数なしで実行されていました。**フォーカス指示を渡す**と(例: 「検索クエリのビルダー実装と失敗中のテストだけ残す」)要約が絞られ、圧縮後のコンテキストがさらに小さくなります。
- `/rewind` が0回です。モデルの誤った出力を対話で修正し続けると、そのやり取りの分だけコンテキストが増えます。誤った1ターンは巻き戻したほうが安く済みます。

**副作用:** `/clear` は文脈を捨てるので、再ブリーフィングの手間が発生します。タスク境界でのみ使い、作業の途中では `/compact` を使ってください。

---

### P2(即実行推奨・所要5分)未使用のMCPサーバ7台を外す

**根拠 — 推定不要の事実が2つ:**
- MCPツール定義 34,000 tok は、セッション初回プレフィックス 41,200 tok の **82.5%**
- 週合計のツール呼び出しは **github 41回 / postgres 12回 / 残り7サーバ 0回**

7台は1週間で一度も呼ばれていません。それでも全リクエストのプレフィックスに定義が乗り続けています(deferred ではなく全定義が載っている状態)。

**削減量の推定:** 9台で 34,000 tok なので単純平均 3,778 tok/台。7台分で **約 20,000〜26,000 tok** と見ています。ただし github MCP はツール数が多く単体で大きく、postgres は小さいので、実際の幅はこれより広い可能性があります。**正確な値は測れます** — 7台を無効化して `/context` を再実行し、差分を取ってください。それが実数です。

**期待効果(20,000 tok削減の保守的な仮定で):** 読み出し 4.04M tok 減、書き込み 240,000 tok 減 → **キャッシュ分入力コストの10〜13%削減**(週 $2.3〜3.0)。副次効果として、候補ツールが減るぶんツール選択の精度も上がります。

**重要な実施タイミング:** ツール定義はプレフィックスの先頭(position 0)にあります。変更するとツール・システム・会話のすべてのキャッシュ層が無効化されるため、**セッション中ではなく、1日の終わりか翌朝の開始前に変更してください。**

**7台を残す必要がある場合:** ツール定義の遅延読み込み(tool search / deferred tools)を有効にすると、名前のみがプレフィックスに載り、必要になった時点で定義が取得されます。これでも同等の効果が得られます。

**P1との関係:** P1 が効くとプレフィックスの相対的な重みが上がるので、**P2 の価値は P1 の後で増えます。** 平均コンテキストが 81,000 tok になれば、41,200 tok のプレフィックスは各読み出しの51%、MCP定義だけで42%を占めることになります。だから P2 を先にやってください(行動変更が不要な唯一の項目です)。

---

### P3 モデル切り替えはセッションの頭で行う

**根拠:** 水 15:21 に 274,000 tok の全書き直しが発生。opus-5 レートで **約 $1.7**、キャッシュ分入力コストの8%が1リクエストで消えました。

**誤解を先に解いておきます。** 「opus は高いから使うな」ではありません。opus-5 は sonnet-4.6 の 1.67 倍で、数倍差ではありません。難しい探索タスクでターン数が減るなら、opus を使ったほうが総額で安くなることもあります。**問題はレートではなく、274,000 tok まで育ったコンテキストの上でモデルを切り替えたことです。**

**やること:**
- モデルは**セッション開始時に決める**(起動時の `--model` 指定、または `/model` 実行直後に `/clear`)
- 途中でモデルを上げたくなったら、**`/clear` して新しいセッションで上げる**。42,000 tok の書き直しなら 274,000 tok の 15% です

**期待効果:** 無駄な書き直し分 **約8%削減**(週 $1.7 相当)。

**もう1点、根本原因の可能性:** 水曜 15:20 にモデルを上げたのは、おそらく 250,000 tok 規模のコンテキストで sonnet の応答品質が落ちたからではないでしょうか。もしそうなら、**その症状に対する正しい対処はモデルの引き上げではなく `/clear` + 論点の再提示**です。膨れたコンテキストの上でモデルだけ上げても、劣化の原因(コンテキスト長)は残ります。ここは P1 と同じ問題の別の顔です。

---

### P4 セッション初回の 42,000 tok について

5回のセッション開始書き込み(合計 210,000 tok、約 $0.8)は**構造上必要**です。誰かが最初にキャッシュを書かないと読めません。ここは削減対象ではありません。

ただし P2 を実施すると 42,000 → 約 20,000 tok になります。**P4 は独立した施策ではなく、P2 の副産物です。**

なお、事前ウォームアップ(`max_tokens: 0` でプレフィックスだけ書く)という手はありますが、**これはレイテンシ対策でコスト対策ではありません。** 書き込み料金を先払いするだけで総額は下がりません。今回は初回リクエストの待ち時間が問題になっていないので、推奨しません。

## 5. 検討して見送った案(理由つき)

### 見送り1: 1時間TTLへの変更 ─ 計算すると赤字になります

「休憩でキャッシュが切れるなら TTL を延ばせばいい」は自然な発想ですが、この開発者のギャップ分布では成立しません。

観測されたギャップ: **68分 / 41分 / 22分 / 124分 / 92分 / 8分**。**6件のうち3件が60分を超えています。**

計算(**1時間TTLが週の全書き込みに適用されるという前提**です。この前提が結論を決めます):

| | 書き込み量 | 単価 | コスト |
|---|---|---|---|
| 現状(5分TTL) | 2,704,000 | $3.75/MTok | **$10.14** |
| 1時間TTL(救済されるのは41分・22分・8分の3件、296,000 tok) | 2,408,000 | $6.00/MTok | **$14.45** |

**週 $4.3(+42%)の悪化**です。読み出しは TTL によらず 0.1× なので動きません。

さらに、**仮に6件すべてが救済されたとしても** 1,673,000 × $6.00 = $10.04 で、現状の $10.14 とほぼ同額 — ベストケースでも損益分岐点です。書き込み単価が 1.25× → 2.0×(+60%)になる負担が、救済分を食い切ります。

**結論:** お使いのバージョンに1時間TTLのオプションがあっても、この使用パターンでは有効化しないでください。正しい対処は TTL を延ばすことではなく、**休憩時に書き直される量そのものを減らすこと**(P1)です。休憩を全部なくすことはできませんが、休憩時に 250,000 tok を抱えていない状態にはできます。

### 見送り2: CLAUDE.md を半分に削る(チーム提案)

| | 現状 | 半減後 | 差分 |
|---|---|---|---|
| サイズ | 480 tok | 240 tok | −240 tok |
| プレフィックス内比率 | 1.17% | 0.59% | — |
| 週の読み出し(202件) | 96,960 tok | 48,480 tok | −48,480 tok |
| 週のコスト | **$0.054** | **$0.027** | **−$0.027** |

**削減額は週 3 セント。キャッシュ分入力コストの 0.12% です。**

同じプレフィックス内の MCP ツール定義は **$3.8/週** で、**CLAUDE.md の約71倍**(34,000 ÷ 480 = 70.8倍)。手を入れる場所が1桁半ずれています。

加えて §3 で示したとおり、**週3回の CLAUDE.md 編集は測定可能なコストを発生させていません。** 12件のキャッシュミスはすべて他の原因で説明済みで、編集に起因する穴はありません。

**そして CLAUDE.md を削ると副作用のほうが大きいリスクがあります。** プロジェクト規約が薄くなればモデルの手戻りが増え、手戻りはターンを増やし、ターンはコンテキストを増やします。**3セント節約するために、P1で削ろうとしている 25.1M tok の側を悪化させる可能性があります。**

「毎リクエスト送られている」という観察自体は正しいです。ただ**送られているものの内訳を見ると 82.5% が MCP、1.2% が CLAUDE.md** でした。仮説の方向は合っていて、対象を間違えているケースです。

## 6. 無駄が出ていない箇所(触らないでください)

診断としては「どこを見なくてよいか」も重要なので明示します。

- **リクエスト数(週214件・1日平均43件)** — 開発者1名としては多くありません。回数を減らす施策は不要です。コストは回数ではなく1件あたりの重さで決まっています。
- **202件の増分書き込み(1,189,000 tok、平均 5,886 tok/件)** — 各ターンで追加された分の通常の追記です。異常値ではありません。ただし固定量ではなく、1ターンで context に入る新規内容(ファイル読み込み量など)に比例します。
- **CLAUDE.md がリポジトリ直下1ファイルのみ** — 構成として適切です。
- **permission mode / プラグイン構成が週内で無変更** — 良いことです。これらを変えればキャッシュが飛びます。

**請求額全体に対する効果について。** 上記はキャッシュ分入力($22/週)に対する比率です。請求額全体には出力トークンと非キャッシュ入力も含まれますが、ログに記録がないため確定できません。**仮に**出力側が週 $8 前後だとすると、キャッシュ分入力は請求額の約73%を占め、その45〜50%削減は**請求額全体で33〜37%の削減**に相当します。この場合、1.7倍だった請求額は先月比 1.1 倍前後まで戻る計算です。ただしこれは出力側の規模を仮定した数字なので、実際の請求内訳で検算してください。

**確実に言えるのは順序です。** P1 が最大で、P2 が最も安く、P3 が最も単発的です。P2 → P1 → P3 の順で着手してください。
