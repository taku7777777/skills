# Claude Code 利用ログ診断(1週間・開発者1名)

## 結論(先に3行)

1. **請求の主因はリクエスト数ではなく「1リクエストあたりのコンテキスト量」です。** 全214リクエストの平均コンテキストは約165,000トークン。セッションを丸1日つなぎっぱなしにしていることが、キャッシュ読み込み費とキャッシュ再作成費の両方を押し上げています。
2. **214件中わずか12件のリクエストが、週の cache creation の56%(1,515,000 / 2,704,000 トークン)を占めています。** うち7件は削減可能です。
3. **チームの仮説「毎リクエストCLAUDE.mdが送られている」は、金額的にはほぼ無関係です。** CLAUDE.md は初回プレフィックスの1.2%(480/41,200)。半分に削っても週あたり数円しか変わりません。一方、同じプレフィックスの82.5%を占めるMCPツール定義(34,000トークン)は、9サーバ中7サーバが週を通じて**呼び出し回数0**です。

## 前提(金額の読み方)

以下の金額は **Sonnet 4.6 の公開レート($3 / 1M input)を全期間に適用した概算**です。

- キャッシュ読み込み = 入力の約0.1倍 → $0.30 / 1M
- キャッシュ書き込み(既定の5分TTL)= 入力の約1.25倍 → $3.75 / 1M

実際には水曜15:20以降が opus-5($5 / $25)で動いているため、その区間は上振れします(後述)。また**出力トークンはログに含まれていない**ため、ここで算出しているのは請求全体ではなく「入力・キャッシュ側」のコストです。相対比較のための数字として読んでください。

| 項目 | トークン | 概算コスト |
|---|---:|---:|
| cache creation(キャッシュミス12件) | 1,515,000 | $5.68 |
| cache creation(残り202件の増分書き込み) | 1,189,000 | $4.46 |
| cache read | 33,400,000 | $10.02 |
| **入力・キャッシュ側 合計** | | **約 $20** |

注目すべきは、**2.7Mトークンの書き込みが、33.4Mトークンの読み込みとほぼ同額**という点です。書き込みは読み込みの12.5倍単価なので、「読み込み量が多い」以上に「書き込みが発生している」ことが効いています。

## 無駄の所在:4つの発見

### 発見1 — キャッシュミス12件が creation の56%を占める

12件の内訳を分類すると、原因はきれいに3つに分かれます。

| 分類 | 件数 | cache creation | creation全体比 | 概算 | 削減可否 |
|---|---:|---:|---:|---:|---|
| セッション初回(前日からの持ち越し不可) | 5 | 210,000 | 7.8% | $0.79 | 不可避 |
| **5分TTL切れ(休憩・会議での中断)** | 6 | 1,031,000 | 38.1% | $3.87 | **削減可** |
| **モデル切り替え(水 15:20 の `/model`)** | 1 | 274,000 | 10.1% | $1.03※ | **回避可** |
| 合計 | 12 | 1,515,000 | 56.0% | $5.68 | |

※この1件は切り替え後の opus-5 レート($6.25/1M)で書き込まれるため、実際は約 $1.71 です。

**リクエスト数では5.6%、コストでは56%。** 「どこが効いているのか分からない」の答えの半分はここにあります。

キャッシュの既定TTLは5分です。表の6件の間隔は 8分 / 22分 / 41分 / 68分 / 92分 / 124分 — すべて5分を超えています。つまり**昼休みと会議のたびにコンテキスト全体が作り直されている**。これは「使い方を変えていない」のに費用が伸びる典型的な形です。

### 発見2 — 同じ失敗が4.3倍のコスト差を生んでいる(最重要)

ログの中で最も示唆的なのがこの2件です。どちらも**原因は同じTTL切れ**なのに、コストが4.3倍違います。

| 日時 | 間隔 | cache creation | 差の理由 |
|---|---:|---:|---|
| 木 15:04 | 124分 | **246,000** | コンテキストが肥大したまま中断 |
| 金 15:02 | 8分 | **57,000** | 直前(14:35)の `/compact` でコンテキストが縮んでいた |

さらに、その `/compact` 自体の効果も同じセッション内で観測できます。

| 金曜 | cache creation | |
|---|---:|---|
| 14:35(`/compact` 実行時) | 221,000 | 圧縮前のコンテキストを読み切っている |
| 15:02(圧縮後の最初のミス) | **57,000** | **74%減** |

つまり、**キャッシュミスの回数を減らすより、ミスしたときの単価を下げるほうが確実で効果が大きい**。中断は人間の働き方であって撲滅できませんが、中断時のコンテキスト量はコントロールできます。

そして `/compact` は週にこの1回だけ、`/clear` と `/rewind` は**週内0回**です。

### 発見3 — コンテキストが肥大する構造そのもの

セッションごとの「1リクエストあたり平均コンテキスト」を出すと、肥大のプロセスが見えます。

| セッション | 曜日 | 稼働時間 | リクエスト数 | 平均コンテキスト |
|---|---|---|---:|---:|
| S1 | 月 | 4h18m | 38 | 約 79,000 |
| S2 | 火 | 8h35m | 52 | 約 213,000 |
| S3 | 水 | 8h05m | 46 | 約 185,000 |
| S4 | 木 | 7h50m | 44 | 約 171,000 |
| S5 | 金 | 6h35m | 34 | 約 96,000 |

※この列は cache read をリクエスト**総数**で割った値です(冒頭の全体平均165,000は読み込みが発生した202件で割っています)。分母にキャッシュミス分を含むため、実際の読み込み時コンテキストはやや大きくなります(S2なら213,000ではなく約222,000)。過小評価の側なので、以下の議論は安全側です。

月曜(S1)と火曜(S2)は**同じ「API改修」の作業**です。稼働時間が2倍になった結果、平均コンテキストは2.7倍になりました。1日1セッション・`/clear` なしなので、コンテキストは単調増加します。午後には200,000トークン超になり、そこで昼休みや会議が入ると発見1の高額ミスになります。

> ⚠️ **ここから「リクエストを減らそう」と読まないでください。** S2は52件で11.08M読み、S5は34件で3.27M読みですが、差の主因は件数(1.5倍)ではなく1件あたりの重さ(2.2倍)です。**減らすべきは仕事量ではなく、持ち歩いているコンテキストの量**です。

### 発見4 — MCPツール定義が初回プレフィックスの82.5%、その大半が未使用

`/context` の実測内訳(5セッションとも同値):

| 構成要素 | トークン | 割合 |
|---|---:|---:|
| **MCPツール定義(9サーバ全定義)** | **34,000** | **82.5%** |
| システムプロンプト | 6,000 | 14.6% |
| プロジェクト情報等 | 720 | 1.7% |
| CLAUDE.md | 480 | 1.2% |
| 合計 | 41,200 | 100% |

一方、週の実際のツール呼び出しは **github 41回 / postgres 12回 / 残り7サーバ 0回**。

この34,000トークンはプレフィックスの先頭にあるため、**キャッシュミスのたびに全額を書き直し、ヒット時も毎回読み込みます。**

| | トークン | 概算コスト |
|---|---:|---:|
| 書き込み(12回 × 34,000) | 408,000 | $1.53 |
| 読み込み(202回 × 34,000) | 6,868,000 | $2.06 |
| **MCPツール定義の週間保持コスト** | | **約 $3.6** |
| うち未使用7サーバ分(推定 26,400 tok) | | **約 $2.8** |

ログに「ツール定義は名前のみのdeferredではなく全定義がプレフィックスに載っている」とある通り、定義を名前のみに遅延ロードする選択肢もありますが、**呼び出し0回のサーバを外すほうが単純で、副作用もありません。** 副次効果として、使わないツールが多いとツール選択の精度も下がります。

### 発見5 — 1ターンあたりの「書き足し量」が月曜だけ3分の1

残る cache creation 1,189,000 トークン(全体の44%)は、中断とは無関係に毎ターン発生する増分書き込みです。これは一見「固定費」ですが、**ログを分解すると固定ではありません。**

各セッションの creation 合計から、そのセッションのミス分を引くと増分が出ます。

| セッション | creation | − ミス分 | = 増分 | 読み込みリクエスト | **増分/ターン** |
|---|---:|---:|---:|---:|---:|
| S1 月 | 120,000 | 42,000 | 78,000 | 37 | **2,108** |
| S2 火 | 658,000 | 310,000 | 348,000 | 50 | 6,960 |
| S3 水 | 755,000 | 467,000 | 288,000 | 43 | 6,698 |
| S4 木 | 634,000 | 376,000 | 258,000 | 41 | 6,293 |
| S5 金 | 537,000 | 320,000 | 217,000 | 31 | 7,000 |
| 合計 | 2,704,000 | 1,515,000 | **1,189,000** | 202 | |

増分の合計はログの 1,189,000 と一致するので、この分解は妥当です。そして **月曜は1ターンあたり2,108トークン、火〜金は平均6,700トークン — 約3.2倍の差**があります。しかも月曜と火曜は同じ「API改修」の作業です。これはリクエスト数で割った値なので、**件数の差ではなく1ターンの重さの差**です。

**ただしログは、この増分の中身(ツール出力 / アシスタント応答 / ユーザー入力)を分解していません。** したがってこれは削減額の主張ではなく、**計測すべき項目**です。エージェント型のコーディングでは通常ツール出力が支配的になります(ファイル全体の読み込み、範囲の広いgrep、テスト出力の全文)。もし月曜だけ狙った読み方をしていたのなら、それは再現可能な行動です。

## チームの仮説への回答

> 「毎リクエストCLAUDE.mdが送られてるのが効いてるんじゃない? 半分に削るところから始めよう」

**着眼点は正しく、対象も正しく、理由だけが間違っています。**

| | トークン | 週間コスト概算 |
|---|---:|---:|
| CLAUDE.md(480 tok) | 480 | **約 $0.05** |
| MCPツール定義(34,000 tok) | 34,000 | 約 $3.6 |

差は約71倍です。CLAUDE.md を半分にしても週あたり $0.03 程度しか変わりません。そもそも CLAUDE.md はキャッシュされたプレフィックスの中にあり、読み込み単価は0.1倍です。「毎回送られている」のは事実ですが、それはCLAUDE.mdだけでなくプレフィックス全体に言えることで、問題は480トークンの側ではなく34,000トークンの側にあります。

**ただし CLAUDE.md には別の注意点があります。** 週内に3回編集されています。CLAUDE.md はキャッシュ対象プレフィックスの一部なので、**セッション中に編集すると、その時点から後ろのキャッシュが全部無効になります。** 今回のログでは12件のミスがすべてセッション初回・TTL切れ・モデル切替で説明できるため、編集起因の追加ミスは確認できません(セッション境界で編集されたと思われます)。金額は付けられませんが、機構としては実在します。

→ 正しい行動は「CLAUDE.mdを小さくする」ではなく、**「CLAUDE.mdの編集をセッション中に散発的にやらず、セッション終了時にまとめる」** です。

## 優先度つき・行動変更の提案

効果と手間の2軸で並べています。**P1は今日30分でできて効果が確定しているもの、P2は効果が最大だが習慣の変更が要るもの**です。

> 各項目の金額は「その施策を単独で打った場合」の目安です。**P2とP3はどちらもコンテキスト量を下げる施策なので効果が重複します。単純に足し算しないでください。** 全部を打った場合の合計は末尾の試算表(約 $20 → 約 $11)を参照してください。

### P1 — 未使用MCPサーバ7つを外す(設定変更・1回・恒久)

- **効果:** 週 約 $2.8(入力側の約14%)。今後すべてのキャッシュ再作成の「底値」が下がるため、効果は他の改善と乗算されます。
- **手間:** 設定1回。**リスクは実質ゼロ**(週を通じて呼び出し0回のため)。
- **やること:** github と postgres 以外の7サーバを無効化。将来また必要になったら都度戻す。棚卸しを月1で回すのが望ましい形です。
- 全定義を載せ続けたい事情があるなら、代替として名前のみのdeferredロード(tool search)への切り替えを検討してください。

### P2 — セッションを「1日1本」から「タスク1本」に切る(最大の効果)

- **効果:** 平均コンテキストを半減できれば、読み込み・ミス単価の両方が下がり、**入力側で 約 $6〜7(30%以上)**。
- **手間:** 習慣の変更が必要。ここが一番大きく、一番続きにくい部分です。
- **やること:**
  - タスクの区切り(API改修 → 検索機能 のような切り替え時)で `/clear`
  - 目安として、コンテキストが 100,000トークンを超えたら区切りを探す(`/context` で確認)
  - **作業の途中なら `/clear` ではなく `/compact` を使ってください。** タスク半ばで消すと文脈が失われ、結局ファイルを読み直して同じ量を払い直すことになります。`/clear` は「そのタスクが本当に終わったとき」だけです。
  - 火曜のように「月曜の続き」を丸1日やる場合こそ、午前で1本・午後で1本に分ける価値があります
- **重要:** これは作業を減らす提案ではありません。同じ仕事を、必要な文脈だけ持って進める提案です。

### P3 — 中断の前に `/compact` か `/clear` を打つ

- **効果:** 週 約 $2〜3。金曜のデータが実証済み(221,000 → 57,000、74%減)。
- **手間:** 小。習慣の一部にできれば自動化不要です。
- **やること:** 昼休み・会議・退席の**前**に、いま作業中でなければ `/compact`(文脈を残したい場合)か `/clear`(タスクが終わっている場合)。木曜15:04の246,000トークンは、これだけで1/4以下になっていたはずです。
- 引数なしの `/compact` でも十分効果が出ています(金曜の実績)。残したい論点があるときだけ引数を付けてください。

### P3.5 — 1ターンあたりの投入量を絞る(まず計測)

- **効果:** 金額未算定。ただし改善後の残コストの**最大項目**(後述の試算で $4.46 / $11.19 = 40%)がここです。
- **手間:** 小〜中。ツールの使い方の癖の問題で、設定変更は不要。
- **やること:** 発見5の通り、月曜だけ1ターンあたりの書き足しが3分の1です。まず**月曜と火曜で何が違ったかを本人が振り返る**のが最短です。一般的な着眼点は3つ:
  - ファイル全体を読むのではなく、必要な範囲を指定して読む
  - grep の範囲を絞る(リポジトリ全体ではなくディレクトリ単位)
  - テスト出力を全文渡すのではなく、失敗部分だけ渡す
- 削減額を約束できる段階ではありません。**「44%は固定費」という前提を疑うべき、というのがこの項目の主張です。**

### P4 — モデルはセッション開始時に決める(`/model` の中断使用を避ける)

- **効果:** 週 約 $1.7 + opus区間の上乗せ分。
- **手間:** ほぼゼロ。判断のタイミングを変えるだけ。
- **理由:** プロンプトキャッシュは**モデル単位**です。水曜15:21のミス(274,000トークン)は、直前リクエストからわずか2分でTTL切れではあり得ず、15:20の `/model` が唯一の説明になります。しかも再作成は**切り替え後のopusレート**で課金されます。
- **やること:** 難しい問題に opus を使いたい場合は、セッション途中で切り替えるのではなく、**その用途で新しいセッションを開始**する。加えて、切り替え後は読み込み・出力もすべて opus レートになるため、水曜15:20〜18:05の全区間が本当に opus を必要としていたかを一度振り返る価値があります。

### P5 — CLAUDE.md の編集はセッション終了時にまとめる

- **効果:** 金額は不明(今回のログでは検出されず)。予防的措置。
- **手間:** ゼロ。
- **やること:** 気づいたtypoをその場で直すのではなくメモしておき、セッションを閉じるときにまとめて反映する。**サイズを削る必要はありません。**

## やらないほうがよいこと:1時間TTLへの切り替え

「休憩でキャッシュが切れるなら、TTLを長くすればいい」は自然な発想ですが、**このログの使い方では逆効果になる可能性が高い**です。理由は2つあります。

1. **週の cache creation 2,704,000 トークンのうち 1,189,000(44%)は、中断とは無関係に毎ターン発生する増分書き込みです。** TTLを延ばしてもこの44%は1件も減らず、書き込み単価だけが 1.25倍 → 2倍(60%増)になります。
2. **休憩の半分は1時間でも足りません。** 6件のギャップは 8 / 22 / 41 / 68 / 92 / 124分。1時間TTLで救えるのは 8・22・41分の3件(296,000トークン)だけです。

粗い試算では、削減 296,000 トークンに対して残り 2,408,000 トークンが1.6倍になるため、**差し引きで週 約 $4 の増加**になります。P2でコンテキストを半減させた後でも、増分書き込みが支配的である以上、符号は変わりません。

> 補足:この試算は「1時間TTLがプレフィックスだけでなく毎ターンの増分書き込みにも適用される」という前提に立っています。TTLの適用範囲を静的プレフィックスだけに限定できる設定があるなら結論は変わり得ます。ただし**「増分書き込みが creation の44%を占め、それは中断とは無関係に発生する」という事実は前提に依存しません**。まずP1〜P3(コンテキストそのものを小さくする施策)を先に打つべき、という結論も変わりません。

## 改善後の見込み(前提つきの試算)

**前提:** MCPを2サーバに絞りプレフィックスを 41,200 → 約 14,800 に、`/clear` により会話部分の平均を半減、`/model` の中断使用を回避。

| | 現状 | 改善後 |
|---|---:|---:|
| cache read | $10.02 | $4.65 |
| cache creation(ミス分) | $5.68 | $2.08 |
| cache creation(増分) | $4.46 | $4.46 |
| **入力・キャッシュ側 合計** | **約 $20** | **約 $11** |

**約45%減。** これは「会話部分を半減できる」という私が置いた仮定に依存する参考値です。実測値ではありません。

なお、改善後に**据え置きの $4.46(増分書き込み)が最大項目になり、全体の40%を占めます。** これはP1〜P4の施策では減らないという意味で据え置いていますが、**下限ではありません**(発見5・P3.5)。次に手を付けるべき場所はここです。

参考までに、仮にこの削減率が請求全体に及ぶなら 1.7倍 × 0.55 ≒ 0.94倍 となり、先月並みに戻る計算になります。ただし出力トークンはこの施策では減らないため、実際の請求全体の削減率は45%より小さくなります(出力が請求の2割なら全体で約36%減)。あくまで規模感の目安としてください。

## 併せて確認していただきたいこと

ログは今週分のみで、先月との比較材料がありません。「使い方は変えていないつもり」なのに1.7倍になった理由は、このログだけでは特定できません。仮説として最も有力で、かつ確認コストが低いのは次の1点です。

> **9つのMCPサーバのうち、呼び出し0回の7つは、いつ追加されたか。**

もし先月以降に追加されていれば、「使い方を変えていない」のに全リクエストのプレフィックスが恒久的に膨らんだことになり、月次の増加とP1の効果の両方が一度に説明できます。週内のMCP構成変更は0件なので、変更があったとすればこの週より前です。
