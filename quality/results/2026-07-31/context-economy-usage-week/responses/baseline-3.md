# Claude Code 利用ログ診断 — 1週間分

## 結論(先に3行)

1. **無駄の本体は「キャッシュが切れた瞬間の書き直し」です。** 214リクエスト中わずか12件(5.6%)が、週の入力コストの **28%** を占めています。
2. **チームの仮説(CLAUDE.md を半分に)は、効果が週あたり約0.13%です。** 金額にして週2.5セント。ここに時間を使うのは損です。
3. **本命は3つ:水曜のモデル切替(1回で約8.5%)、離席によるキャッシュ失効(約19%)、未使用のMCPサーバ定義(約18%)。** 上2つは設定変更なしで今日から直せます。

---

## 0. 前提 — このログから何がどこまで言えるか

診断の土台になる価格構造を先に固定します。

| トークン種別 | 素の入力トークンに対する倍率 |
|---|---|
| cache read(キャッシュヒット) | **0.1倍** |
| cache creation(キャッシュ書き込み、5分TTL) | **1.25倍** |
| cache creation(1時間TTL) | 2倍 |

以下では、素の入力トークン1個分を「1」として全部を足し合わせた値を **換算入力トークン** と呼びます(cache read は ×0.1、cache creation は ×1.25)。これでリクエスト間・日付間の比較ができます。

**重要な倍率:cache creation ÷ cache read = 1.25 ÷ 0.1 = 12.5倍。**
まったく同じ内容でも、キャッシュが生きているときに触るか、切れた後に触るかで **12.5倍** 値段が変わります。今回の診断はほぼこの一点に集約されます。

### このログで分かることの限界(先に明示します)

- ログには **出力トークンが一切含まれていません**。出力単価は入力の5倍なので、週の請求総額はこのログからは復元できません。以下の「週コスト比」はすべて **入力側のみ** の比率です。金額を出しているのは、比較として効く2箇所だけに絞っています。
- リクエストごとのモデル判別ができません(水曜15:20以降が opus-5 という記載のみ)。換算値は基本 sonnet-4.6 基準で、Opus区間には別途1.67倍の単価差があることを都度注記します。
- 認証が `ANTHROPIC_API_KEY`(従量課金)で、キャッシュ関連設定は既定のまま — つまり **キャッシュTTLは5分** です。この1点が、以下の失効パターンをすべて説明します。

## 1. 週コストの構造 — 書き込みと読み込みがほぼ同額

| 種別 | 実トークン | 換算入力トークン | 入力コスト比 |
|---|---:|---:|---:|
| cache creation | 2,704,000 | 3,380,000 | **50.3%** |
| cache read | 33,400,000 | 3,340,000 | **49.7%** |
| 合計 | 36,104,000 | **6,720,000** | 100% |

**cache creation は全トークン量の7.5%しかないのに、コストでは半分を占めています。** 1.25倍と0.1倍の差がそのまま効いた結果です。

ここが最初の重要な示唆です。「読み込みが33Mもある」ことに目が行きがちですが、**削るべきは270万の書き込み側**です。cache creation を半分にできれば、週の入力コストは約25%下がります。読み込みを半分にしても同じ25%ですが、そちらは会話量そのものを半減させる必要があり、はるかに難しい。

## 2. 「使い方は変えていない」は、ほぼ正しい

本人の証言と請求1.7倍が矛盾して見える理由が、セッション別に正規化すると出てきます。

| セッション | 曜日 | 作業 | 稼働 | req | 換算入力トークン | **1req当たり** |
|---|---|---|---|---:|---:|---:|
| S1 | 月 | API改修 | 4h18m | 38 | 450,000 | **11,842** |
| S2 | 火 | API改修の続き | 8h35m | 52 | 1,930,500 | **37,125** |
| S3 | 水 | 検索機能 | 8h05m | 46 | 1,796,750 | **39,060** ※ |
| S4 | 木 | バグ修正 | 7h50m | 44 | 1,544,500 | **35,102** |
| S5 | 金 | リファクタリング | 6h35m | 34 | 998,250 | **29,360** |
| 合計 | | | | 214 | 6,720,000 | 31,402 |

※ S3は約1/3が opus-5(単価1.67倍)なので、実コストはこの値より上振れします。

### 月曜が対照群になっています

**火曜は月曜と同じ作業(「API改修の続き」)、同じモデル、同じ本人で、1リクエスト当たり3.1倍のコストがかかっています。**

月曜だけ何が違ったか:
- セッションが4時間18分と短い(他は6.5〜8.5時間)
- **セッション途中のキャッシュ失効がゼロ**(初回42,000のみ)
- 平均 cache read が81,000/req(週平均165,000)= 会話が80k程度で収まった
- 1ターンあたりの追加書き込みが約2,100トークン(週平均5,886)

つまり本人の感覚は正しく、**操作は変えていません。変わったのはセッションの長さです。** そして、

> **キャッシュ失効1回の値段は、その時点の会話サイズに比例する。会話サイズはセッションの長さに比例する。**

長時間セッションは、それ自体が高いのではなく、**「失効事故が起きたときの被害額」を押し上げます。** 同じ習慣のまま作業時間が伸びただけで、コストは非線形に増えます。これが「どこが効いているのか分からない」の答えです。

## 3. 無駄の内訳 — 12件で28%

cache read = 0 の12件は、その時点の会話全体を丸ごと書き直しています。合計 1,515,000トークン(週の cache creation 2,704,000 の **56%**)。原因別に分けます。

| 原因 | 件数 | cache creation | 換算入力トークン | 入力コスト比 | 削減可能性 |
|---|---:|---:|---:|---:|---|
| A. その日の初回 | 5 | 210,000 | 262,500 | 3.9% | 構造的に下限。ただし前置き縮小で下がる |
| B. 離席によるTTL失効 | 6 | 1,031,000 | 1,288,750 | **19.2%** | **ほぼ全部削れる** |
| C. モデル切替 | 1 | 274,000 | 570,833 ※ | **8.5%** ※ | **全部削れる** |
| 小計 | 12 | 1,515,000 | — | 約31% | |

※ 水15:21は `/model` 実行の直後、つまり opus-5 の書き込み単価で課金されています。sonnet換算で 274,000 × 1.25 × (5/3) ≈ 570,833。分母(6,720,000)自体がsonnet基準なので、実際の比率はこれよりわずかに小さいですが、8%台であることは動きません。

### C. モデル切替 — 1回のキーストロークで約8.5%

水15:21のリクエストは **直前リクエストからわずか2分** なのに cache read = 0 です。TTL(5分)は切れていません。原因は15:20の `/model` 実行です。

**プロンプトキャッシュはモデル単位で保持されます。** モデルを切り替えた瞬間、それまでのキャッシュは全部無効になり、274,000トークンの会話をゼロから書き直します。しかも新しい方(opus-5)の単価で。

さらにこの後、18:05までの残り全リクエストが opus-5 単価(入力$5 / 出力$25 per MTok、sonnet-4.6の1.67倍)で走っています。水曜が1req当たり最も高い(39,060)のはこの二重の負担です。

### B. 離席によるTTL失効 — 約19%、これが最大の単一要因

| 日時 | 間隔 | cache creation | 状況 |
|---|---:|---:|---|
| 火 13:10 | 68分 | 268,000 | 昼休み |
| 水 12:48 | 41分 | 151,000 | 昼休み |
| 木 11:26 | 22分 | 88,000 | 短い中断 |
| 木 15:04 | 124分 | 246,000 | 長時間離席 |
| 金 14:35 | 92分 | 221,000 | 昼休み+`/compact` |
| 金 15:02 | 8分 | 57,000 | **8分の休憩でも失効** |

TTLは5分です。**コーヒーを淹れに8分離席しただけで、57,000トークンの書き直しが発生しています。**

そして cache creation の値は、その瞬間の会話サイズをそのまま教えてくれます。**火〜金の会話は日常的に220,000〜275,000トークンまで膨らんでいます。** この状態で離席すると、戻ってきた最初の1リクエストが25万トークンぶんの書き込み料金を払います。

## 4. 金曜のログが、答えを自分で示しています

金曜だけ `/compact` が実行されています。その前後の数字:

- **14:35(`/compact` 実行時):cache creation 221,000**
- **15:02(その27分後):cache creation 57,000**

`/compact` は会話を221,000 → 57,000 に、**74%削減** しました。CLAUDE.mdを半分にして削れる240トークンの、およそ680倍です。

そして金曜は、火〜木より1req当たり16〜25%安く済んでいます(29,360 vs 35,102〜39,060)。効果は数字に出ています。

### ただし、実行のタイミングが間違っていました

14:35の `/compact` は、**92分の離席から戻った後** に実行されています。だから221,000トークンぶんの書き込み(1.25倍)を払っています。

もし離席する直前(13:03頃、キャッシュがまだ生きているうち)に実行していれば、同じ221,000トークンは **cache read(0.1倍)** で処理されました。

> **同じ `/compact` が、休憩の前なら0.1倍、休憩の後なら1.25倍 — 12.5倍の価格差です。**

内容は1バイトも変わりません。順番だけの問題です。この1件だけで、換算で約205,000トークン(週の約3%)の差が出ています。

## 5. チームの仮説の検証:CLAUDE.md半減は効きません

Slackの「毎リクエストCLAUDE.mdが送られてるのが効いてるんじゃない?」— **前半は事実ですが、量が桁違いです。**

セッション前置き41,200トークンの内訳:

| 項目 | トークン | 前置き比 | 週の入力コスト比 |
|---|---:|---:|---:|
| MCPツール定義 | 34,000 | **82.5%** | **17.8%** |
| システムプロンプト | 6,000 | 14.6% | 3.1% |
| プロジェクト情報等 | 720 | 1.7% | 0.38% |
| **CLAUDE.md** | **480** | **1.2%** | **0.25%** |

**CLAUDE.md を半分(240トークン)にした場合の削減効果:週の入力コストの 0.126%。**

金額にすると **週あたり約2.5セント**(sonnet単価 $3/MTok で計算)。年間でも1.3ドル程度です。一方、同じ前置きの中にある MCPツール定義は **週あたり約3.6ドル分** — CLAUDE.md の **71倍** です。

補足すると、週内に3回編集されている件も実質ゼロコストです。TTLが5分である以上、そもそも日をまたいだキャッシュ再利用は起きていないので、編集による無効化は失うものがありません。

**CLAUDE.md は削るべき対象ではありません。** 480トークンで開発の文脈が共有できているなら、それはむしろ費用対効果が非常に良い投資です。削るとチームの生産性だけが下がります。

## 6. 提案(優先度順)

### 【P0-1】セッション途中でモデルを切り替えない — 設定変更不要・即日

**根拠:** 水15:21、間隔2分でのキャッシュ全損 274,000トークン。約8.5%。

- モデルはセッション開始時に決める。
- 途中で opus が必要になったら、**その用途だけ新しいセッションを立てる。** 前置き41,200トークンを1回払うだけで済み、25万トークンの書き直しは発生しません。
- 難所を opus で解いたら、元のセッションに戻って続ける。

**効果:** 書き直し分(約8.5%)に加え、不要に opus 単価で走った区間(水15:21〜18:05)の1.67倍差も消えます。

### 【P0-2】5分以上席を立つ前に、セッションを整理する — 設定変更不要・即日

**根拠:** 上記の12.5倍の価格差。離席失効だけで約19.2%。

具体的には:

- **昼休み・会議の前に `/compact`(または区切りがつくなら `/clear`)を実行してから離席する。** 戻ってからではなく、離席前。
- 独立したタスク(特に木曜の「バグ修正」のような、互いに無関係な作業の連続)は `/clear` で区切る。1件目のバグの文脈を、5件目のバグを直す間ずっと読み続ける理由はありません。
- 長時間離席が確定しているなら、セッションを終了してしまうのが最も安い。

**効果:** 休憩前に会話を60,000トークン程度(金曜の実績は57,000)まで畳めていれば、B群6件の書き直しは 1,031,000 → 約385,000 に減ります。削減 **約646,000トークン、週の入力コストの約12%**。加えて、`/compact` 自体をキャッシュが生きているうちに実行することで、その処理自体も0.1倍で済みます。

なお、週内の `/clear` と `/rewind` の実行は0件でした。214リクエストを5つの長大セッションで走らせている状態です。

### 【P1】MCPサーバの棚卸し — 設定判断が必要

**根拠:** MCPツール定義34,000トークンが前置きの82.5%を占め、週の入力コストの17.8%。そして **9サーバ中7サーバが週を通じて呼び出し0回**(github 41回 / postgres 12回 / 残り7サーバ 0回)。

- 使われた2サーバ以外の7サーバを、いったん接続から外す。
- 外した後に `/context` を実行して、前置きが実際に何トークンになったか測る。サーバごとの定義量は均等ではないので、推定せず実測してください。
- ツール定義が「名前のみのdeferred」ではなく全定義で載っている、という記載があります。**deferred(遅延読み込み)がこの環境で利用可能かどうかを確認する価値があります。** 使えるなら、サーバを外さずに前置きだけ縮められます。

**換算の目安:** 現在の利用パターンでは、**前置きから1,000トークン削るごとに、週の入力コストが約0.52%下がります**(202回の読み込み×0.1 + 12回の書き込み×1.25 = 35.2換算トークン/1トークン)。7サーバぶんが仮に20,000トークンなら、約10%の削減になります。

**この項目だけは、人間の継続的な規律に依存しません。** 一度外せば効果が永続する唯一の施策なので、P0より下でも着手する価値があります。

**注意:** MCP構成の変更は **セッションとセッションの間に** 行ってください。セッション途中でツール構成を変えると、ツール定義・システム・会話のキャッシュがすべて無効化され、丸ごと書き直しになります(週内のMCP構成変更0件は、この点では正しい運用でした)。

### 【P2】計測の穴を埋める

現状のログでは、以下が分からないため請求額の完全な分解ができません。

- **出力トークン数**(単価は入力の5倍。最も高い要素が欠けています)
- キャッシュされていない生の入力トークン(`input_tokens`)
- リクエストごとのモデル

`/cost` や利用状況の集計で、最低限 **入力(生・書込・読込)/出力/モデル** の5項目をリクエスト単位で取れるようにすると、次回以降は推定でなく実測で判断できます。

### 【P3】1ターンあたりの文脈増加量を見直す

cache read > 0 の202リクエストは、1リクエストあたり平均 **5,886トークン** を新たにキャッシュに書き込んでいます(月曜だけは約2,100)。これはツール結果・ファイル読み込みの取り込み量です。

- ファイル全体ではなく、必要な範囲を指定して読む。
- 広い grep の結果をそのまま流し込まない。

**効果は二重です。** 直接的に1.25倍の書き込みが減るのに加え、**会話の成長速度が落ちるので、将来のあらゆる失効事故の被害額が小さくなります。** ここを半減できれば書き込み側で約11%、さらに失効時の書き直しも連動して縮みます。

## 7. やらないほうがよいこと

### ❌ CLAUDE.md を半分にする

削減効果 **0.126%**(週2.5セント)。前置きの1.2%しかありません。作業時間のほうが高くつきますし、失うもの(チームの文脈共有)のほうが大きい。

### ❌ キャッシュTTLを1時間に延ばす

一見すると離席問題の直接的な解に見えますが、**この利用パターンでは逆効果です。**

1時間TTLは書き込み単価が1.25倍 → **2倍** になります。

- **救われる失効:** 60分以内の3件(水12:48の41分、木11:26の22分、金15:02の8分)。回避できる書き込みは約278,000トークン(通常のターン書き込み分を除く)→ 換算347,875トークンの節約。
- **増えるコスト:** 残り約2,425,700トークンの書き込みすべてに +0.75倍 → 換算1,819,275トークンの増加。
- **差引:換算で約+147万トークン、週の入力コスト +21〜22%の増加。**

理由は明快で、書き込み量の大半(1,189,000トークン)は通常ターンの逐次書き込みだからです。3件の失効を救うために、その全部に5割増しの税金をかけることになります。しかも68分・92分・124分の3件は1時間TTLでも救えません。

(なお、この環境に利用者が触れる1時間TTLの切替が存在するかは、ログからは確認できません。「検討するなら」という前提での試算です。)

**正しい対処は、TTLを延ばすことではなく、失効時に書き直す量そのものを減らすこと**(P0-2とP3)です。

## 8. 請求1.7倍の説明について

正直に書きます。**特定した要因は、1.7倍を説明するのに十分すぎるほどです。逆に言えば、要因ごとの厳密な按分はこのログだけではできません。**

- 先月が月曜のような使い方(11,842換算トークン/req)で、今月が火〜木の平均(約37,000)なら、1リクエスト当たり約3倍です。これは1.7倍を **超えて** います。
- つまり、リクエスト単価の悪化だけでなく、リクエスト数や稼働日数の違いも絡んでいるはずですが、先月のセッション別内訳がないため切り分けられません。

言えるのは以下です。

1. 水曜のモデル切替(約8.5% + Opus単価差)は **今月新しく発生した** 変化で、先月には無かった要素です。
2. 離席失効(約19%)とMCP定義(約18%)は先月も存在した構造ですが、**セッションが長くなるほど被害額が増える性質** を持っています。長時間化がそのまま増額に直結します。
3. この3つを潰せば、**使い方を変えずに入力コストの3割前後**が消える計算になります。ただし三者は独立ではなく、前置き41,200トークンはすべての書き直しに含まれるため(MCP定義34,000トークンぶんは離席失効・モデル切替の数字の内側にも入っています)、実際の削減幅は各項目の単純合算より小さくなります。前置きを削れば残る失効1件あたりの単価が下がり、失効を減らせば前置きを払う回数が減る — 両方効きますが、二重には効きません。

先月分の同じ粒度の集計が取れれば、P2の計測整備と合わせて確定できます。

| cache creation 単価(5分TTL) | 素の入力の 1.25倍 |
| **書き込み ÷ 読み込み** | **12.5倍** |
| sonnet-4.6 単価 | $3.00 / $15.00 per MTok |
| opus-5 単価 | $5.00 / $25.00 per MTok(sonnet比 1.67倍) |

**キャッシュが無効化される条件**(この診断の根拠):

- モデルの切り替え → ツール定義・システム・会話の **全キャッシュが無効**
- ツール定義(MCPサーバ)の追加・削除・順序変更 → **全キャッシュが無効**
- 前置き内容の変更 → その位置より後ろがすべて無効(キャッシュは前方一致)
- TTL経過(既定5分) → 失効
