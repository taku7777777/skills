# セッション運用診断書(Palet バックエンド / 1週間ログ)

結論を先に3行で。

- 効いているのは CLAUDE.md ではない。CLAUDE.md を半分に削っても週の請求は **0.13%** しか動かない。
- 効いているのは「日次1セッションを一日中閉じない運用」で、離席と `/model` がそこに乗って増幅している。
- 打ち手は3つ。(1) MCPツール定義の削減、(2) セッション途中の `/model` 禁止、(3) 育ったセッションから離れるときは区切る。合計で週のキャッシュ対象入力費の **35〜45%** オーダー。

---

## 0. 前提と単位(以下の比率がかかっている土台)

**単位**: cache write を基本入力単価の ×1.25(5分TTL)、cache read を ×0.10 として正規化した「入力トークン相当」で比較する。

| 費目 | 実トークン | 入力トークン相当 |
|---|---|---|
| cache creation | 2,704,000 | 3,380,000 |
| cache read | 33,400,000 | 3,340,000 |
| **合計** | 36,104,000 | **6,720,000** |

以降の「%」はすべてこの 6,720,000 に対するシェアである。**モデル別の単価差・出力トークン・非キャッシュ入力は本ログに無いため含まない**。したがって「請求額 1.7 倍」の分母とは一致しない(§6)。

**TTLレーンの確定(これを取り違えると閾値ごと間違う)**: 認証は `ANTHROPIC_API_KEY`、キャッシュ関連設定は既定 → **TTL は 5 分**レーン。ログ内で検証できる。

- 8分・22分のギャップで cache read = 0。1時間レーンならヒットしていたはずで、5分レーンであることの直接証拠。
- 逆に5分未満で read = 0 は水 15:21 の1件だけ。これは直前 15:20 の `/model` による全面失効で説明が付く。
- 結果、read = 0 の12件は**すべて**「日初回 / 5分超のギャップ / モデル切替」で説明でき、未説明の異常はない。

「1時間離れなければ大丈夫」はこのレーンでは成立しない。昼休みでも会議でも再構築が走る。

**整合性チェック**(3点、いずれも一致): 日初回の creation 42,000 ≒ 起動固定費 41,200 / 金 15:02 の 57,000 ≒ 41,200 + 圧縮後会話 ≒16,000 / 通常202件の増分 5,886 tok/件 ≒ S2 から逆算した会話成長率 ≒6,500 tok/件。

## 2. 支配要因

### **会話の肥大(閉じない日次セッション)。**

シェアで最大であり、かつ他の費目の乗数になっている。

| 費目 | 入力換算 | シェア |
|---|---|---|
| cache read — 会話部分 | 2,507,760 | **37.3%** |
| cache write — 通常202件の増分(健全) | 1,486,250 | 22.1% |
| cache write — 離席起因の再構築6件 | 1,288,750 | **19.2%** |
| cache read — 起動固定費部分(202×41,200) | 832,240 | 12.4% |
| cache write — モデル切替1件 | 342,500 | 5.1% |
| cache write — 日初回5件 | 262,500 | 3.9% |

**「肥大」が「再構築」の上流にある根拠**: 起動固定費は5セッションとも 41,200 で同一なのに、再構築1回の creation は 57,000〜274,000 と約6倍ばらついている。この差は**その時点の会話サイズ**しか説明しない。つまり離席そのものが高いのではなく、**育ったセッションから離席することが高い**。日初回の 42,000 に対し、火 13:10 の再構築は 268,000(6.4倍)である。同じ 1 回の中断が、朝なら 42,000、夕方なら 268,000 になる。

第2要因は離席起因の再構築(19.2%)。これは施策の優先度ゲートを明確に超えている — **全 cache write に対する離席起因の比率は 1,031,000 / 2,704,000 = 38.1%** で、「10% 未満なら離席施策を優先しない」という目安の 4 倍近い。離席管理は本件では正当に優先すべき対象である。

第3要因はモデル切替1件(5.1%)。**単一操作としては週最大**で、124分離席の再構築(246,000)より水 15:21 の切替(274,000)の方が大きい。sonnet-4.6 は旧トークナイザ、opus-5 は新トークナイザで同一テキストが約3割多くトークン化されるため、モデル切替は「同じ履歴をもう一度書く」ではなく「膨らんだ履歴を高い単価で書き直す」操作になる。同一モデルでの再構築より構造的に高くつく。

**本人の「使い方は変えていない」について**: 主観的にはそうでも、請求構造上は変わっている。週内に `/model`(水)と `/compact`(金)という新しい操作が入っており、いずれも失効イベントとして記録されている。

**チームの仮説(CLAUDE.md 半減)は数値で否定される** — §4 に置く。

## 3. 行動変更表

優先度は「シェア × 確実性 ÷ 行動コスト」で並べた。**一度に1つずつ**入れて再計測する。

支配要因(会話の肥大)に直接対応するのは #3 だが、実施順は #1 → #2 → #3 とする。#1・#2 は設定とルールだけで文脈を一切捨てないため counter-metric のリスクが無く、先に入れておけば #3 の効果を清潔に測れる。シェアが大きい施策から着手するのではなく、**測定を汚さない施策から着手する**。

| # | 場面 | いまの行動 | 変える行動 | 期待効果の桁 |
|---|---|---|---|---|
| **1** | MCP 9サーバ・全定義ロード(未使用7サーバは週0回) | 34,000 tok が毎リクエストのプレフィックスに常駐 | ①ツール定義を既定の deferred(名前のみ)へ戻す ②それでも残るなら未使用7サーバを無効化 ③github は `gh` CLI へ(定義コスト0) | **−5〜17%**(点推定 −13.8%)。設定のみ・文脈損失ゼロ・恒久 |
| **2** | 途中でモデルを変えたくなった | セッション途中で `/model`(水 15:20) | 冒頭で決めて固定。変えるなら `/clear` を挟んで新セッションで opus-5 を開き、要点を再指定する | **−5.1%**(確定分)+ 切替後2h45m 分の巨大プレフィックスを opus 単価で読み続けた分(§6 待ち)。ルール1本・行動コストほぼ0 |
| **3** | 育ったセッションから離れる(火13:10・水12:48・木15:04・金14:35) | 開いたまま離席 → 復帰初手が全面再書込 | 離れる前に要点(決定事項・未解決TODO・次の一手・関連ファイルパス)を書き出させてセッションを区切る。戻ったら新セッション+要点再指定 | creation 側 **−13.4%** + read 側 **−10〜18%**(区切りが会話部分をリセットする副作用)= 合計 **−23〜31%** |
| **4** | 離席の判断そのもの | 分数で迷う(そもそも意識していない) | **分数ではなく再構築費で決める**: 再構築費が日初回起動(42,000)の3倍(≒125,000 tok)を超えていたら区切る。下回るなら何もしない。実務の目安は「稼働2時間半を超えたセッションから離れるとき」 | 木11:26(88,000)・金15:02(57,000)は**対象外**になる。1件あたり効果 0.3〜0.9% で行動コストに負ける(過剰最適化の回避) |

| **5** | 休止から戻った直後 | 92分の離席明けに引数なし `/compact`(金 14:35) | 休止明けの `/compact` は打たない。新セッション+要点再指定に置き換える | トークン効果は #3 に含む。追加価値は判断構造(却下案・フェーズ前提)の保全 |
| **6** | 同一タスクで文脈が肥大したとき | auto-compact 任せ / 引数なし `/compact` | 切れ目で「決定事項・未解決TODO・却下案と理由を残せ」と**指示付き** `/compact` | 手戻り側の効果(§5 の counter-metric で観測) |
| **7** | 失敗アプローチを捨てるとき | 訂正を重ねて同一セッション続行 | 経路の破棄は `/rewind`(キャッシュ済みプレフィックスへの切り戻しで compact より安い)。同じ問題で2回訂正したら `/clear` + 依頼の書き直し | 週内 `/rewind` 0件 = この選択肢が使われていない |

### #1 の効果幅の出どころ

プレフィックスから1トークン削ったときの週次効果は、read 側 202 件 ×0.10 + write 側 12 件 ×1.25 = **35.2 入力トークン相当/週**。これに削減量を掛ければ即座に評価できる。

- deferred 復帰(9サーバ維持・名前のみ常駐、−約32,000 tok)→ 約 1,126,000 → **−16.8%**
- 未使用7サーバ無効化のみ(定義サイズが均等と仮定、−26,400 tok)→ 929,000 → **−13.8%**
- 保守側(未使用7サーバが定義の3割、−10,200 tok)→ 359,000 → **−5.3%**

サーバ別の定義トークン数(§6)が取れれば1点に絞れる。**postgres は残す**(週12回使用)。

### #3 の効果の出どころ

**creation 側**: 会話が育った4件(火13:10=268,000 / 水12:48=151,000 / 木15:04=246,000 / 金14:35=221,000、計 886,000)を「区切って新セッション」に置き換えると 4×42,000 = 168,000 に落ちる。差 718,000 ×1.25 = 897,500 → **−13.4%**。

**read 側(副作用として自動的についてくる)**: 区切ると以降のリクエストが背負うプレフィックスもリセットされる。木曜1件で見ると、15:04 以降の約13リクエストは 246,000→330,000(平均 ≒288,000)を読み続けたが、新セッションなら 42,000→126,000(平均 ≒84,000)で済み、read 約 2,652,000 tok = **約3〜4%** の差になる。S2〜S5 の会話部分 read 合計 23,602,000 を各1回の区切りで概ね半減させると 1,180,000 → **−17.6%**。控えめに見て **−10〜18%**。

この read 側の数字は**木曜の単一ケースも含めてすべて**、成長モデル(1リクエストあたり会話 +約6,500 tok、リクエスト数はセッション内で均等分布と仮定)からの推定であり、確定値ではない。ログには離席時点の creation しかなく、離席以降のリクエスト数と read の内訳が無いためである(§6)。ただし**前提はログにあるもの(実際に起きた4回の長時間離席)だけで、追加の仮定を必要としない**点が #8 との違いである。

### #8(条件付き・検証が先)

タスク境界での `/clear` を離席とは独立に入れれば read 側はさらに下がる。ただし**本ログには1日の中に無関係なタスクが混在していた証拠がない** — S1→S2 は明示的に同一タスクの継続で、S3・S4・S5 も各1タスクとして記録されている。したがって「日次セッションを機械的に半分に割る」は現時点で推奨できない。**先に検証すること**: 各日の作業に実際に切り離せる単位(別チケット・別レイヤ・調査と実装)が含まれていたか。含まれていたなら境界ごとに `/clear`。含まれていないなら #3 の区切りで十分で、それ以上刻むのは §4 の過剰最適化に入る。

### 合計

施策 #1〜#3 は再構築費の項で一部重複する(#1 を先に入れると #3 の creation 側は 13.4%→11.4% に縮む)。重複を引いて **週のキャッシュ対象入力費に対して概ね −35〜45% のオーダー**。出力トークンとモデル別単価差を含む請求総額への効果は、本ログからは算定できない(§6)。

## 4. やらないこと

### (a) CLAUDE.md の削減 — チームの提案は却下

480 tok は起動固定費の 1.2%、平均プレフィックス(165,347)の **0.29%**。上記の 35.2 tok/週 の係数で評価すると:

- 半分に削る(−240 tok)→ 8,448 → **0.126%**
- **全部消しても**(−480 tok)→ 16,896 → **0.25%**

週の請求は動かない。「毎リクエスト送られている」は事実だが、送られている 165,347 tok のうち 480 tok の話である。ここに着手すると、効く施策(#1 の MCP 34,000 tok = 同じ場所の **71倍**)が後回しになる分だけ有害。

CLAUDE.md を小さく保つ理由はコストではなく**指示の埋没防止**であり、内容・体系の設計はコスト診断の領分ではない。

**別件の正しさの指摘**(コストとは無関係): 週内3回のセッション中編集は、キャッシュを壊さないが**反映もされていない**。CLAUDE.md の変更は次の `/clear`・`/compact`・再起動から効く。「直したのに効かない」場面があったなら原因はこれで、即時に効かせたい指示はプロンプトで直接渡す。

### (b) 1時間TTLへのオプトイン(`ENABLE_PROMPT_CACHING_1H=1`)— この環境では**逆に高くなる**

5分レーンだと分かったので反射的に打ちたくなるが、計算すると損である。

書込単価が ×1.25 → ×2.00 に上がるため、損益分岐は「回避できる書込量 S が全書込量 W の 37.5% を超えること」:

> 2.00 × (W − S) < 1.25 × W  ⇔  0.75W < 2S  ⇔  **S > 0.375W**

実績は:

- 1時間TTLが救えるのは60分未満のギャップだけ → 8分(57,000)+ 22分(88,000)+ 41分(151,000)= **S = 296,000**
- W = 2,704,000 → **S/W = 10.9%**(37.5% に遠く届かない)
- 施策 #1 でプレフィックスを縮めた後でも S/W = 9.1% で、結論は変わらない

実額では、creation は 2,704,000 − 296,000 + 増分約19,500 = 約2,427,500 になるが単価が2倍で 4,855,000。現行 3,380,000 に対し **+約1,500,000 = 週の入力費 +22%** の悪化。

さらに重要なのは、**離席被害 1,031,000 のうちレーン固有なのは 296,000(29%)だけ**で、68分・92分・124分のギャップは1時間レーンでも同じく全面再書込になるという点。**残り71%はレーンを変えても消えない。** 打つべきは設定変更ではなく #3 の行動変更である。

### (c) 節約目的の細切れ `/clear`(1時間ごと等)

連続作業中の202件の増分書込は平均 5,886 tok/件で既に健全。ここに削る余地はない。刻みすぎると再説明・同一ファイルの再読・手戻りが増え、節約額を上回る。ヘッドルームは使い切ってよい予算である。

### (d) 日初回の起動書込(5件 = 210,000 = 3.9%)

構造的に避けられない(一晩空けば TTL は必ず切れる)。#1 で自動的に縮むので、単独では追いかけない。

### (e) opus-5 の利用そのものの禁止

単価は高いが必要な場面はある。問題は**モデル選択ではなくタイミング**(セッション途中での切替)だけ。#2 は「opus を使うな」ではなく「切替を `/clear` 境界に寄せろ」である。

## 5. counter-metrics と見直し条件

施策 #3・#8 は文脈を捨てる方向なので、単独では評価しない。**必ず以下と対で見る。**

| counter-metric | 測り方 | 悪化のサイン | 対応 |
|---|---|---|---|
| 再説明の往復回数 | 区切り後の新セッションで、前提の説明し直しに費やしたユーザー発話数 | 週3回超 | 手放しの書き出し粒度を上げる(決定事項・却下案・関連ファイルパスを明示)。それでも減らなければ区切り閾値を 125,000 → 200,000 tok へ緩める |
| 同一ファイルの再読量 | 新セッション冒頭で読み直したファイルのトークン量 | 区切りごとに大量読み込みが再発 | 要点書き出しに**ファイルパスと結論**を含める |
| 手戻り率 | 圧縮/区切り後に、既に却下した案が再提案された回数 | 1回でも出たら | `/compact` 指示に「却下案と理由を残せ」を追加(#6) |

### 見直し条件

- **施策は1つずつ。** #1(設定のみ・文脈損失ゼロ)→ #2(ルール1本)→ #3(習慣)の順。#1・#2 は counter-metric のリスクが無いので先に入れて、#3 の効果を清潔に測れる状態を作る。
- **2週間後に再計測**: read = 0 のリクエスト一覧と creation の時系列。#3 が効いていれば 100,000 tok 超の再構築スパイクが消える。
- **deprioritize 基準**: 離席起因の再構築が全 cache write の 10% 未満に下がったら、以降の離席施策はやめる。現状 38.1% なので今は対象。ここを割ったら「打つべき施策がない」を結論にしてよい。
- **1時間TTLの再判定条件**: S/W が 37.5% を超えたときだけ。#1・#3 の後も 9〜11% 圏なので、当面は再判定不要。
- **#8 は検証が済むまで着手しない。** 各日の作業に切り離せる単位があったかを確認してから。
