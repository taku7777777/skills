# セッション運用診断書(Palet バックエンド / 1週間ログ)

依頼どおり、ファイル変更・設定変更は一切行っていない。以下はすべて提案である。

**前提(コストモデル)**
ログにあるのは cache creation / cache read のトークン数だけなので、**入力等価単位**(基本入力トークン1個 = 1単位)で比較する。APIキー運用・既定設定のため書込は5分TTL(×1.25)、読取は×0.10(`references/evidence.md`、Anthropic Pricing 2026-07-30参照)。

- 週の書込: 2,704,000 tok × 1.25 = **3,380,000 単位**(50.3%)
- 週の読取: 33,400,000 tok × 0.10 = **3,340,000 単位**(49.7%)
- 合計 **6,720,000 単位** = 214リクエスト平均 31,402 単位/req

出力トークンと非キャッシュ入力(compactの要約読み込み等)はログに無いため本モデルの外にある。したがって以下の金額シェアは**下限**であり、特に水曜15:21以降はOpus-5単価(Sonnet-4.6の数倍。加えて新トークナイザで同一テキストが約3割多くトークン化される)なので、水曜分の実際の金額シェアはトークンシェアより大きく出る。

## 1. 現況サマリ

### 起動固定費(毎リクエストのプレフィックスに乗る恒常費)

| 内訳 | tok | 起動固定費内シェア |
|---|---|---|
| MCPツール定義(9サーバ・全定義ロード) | 34,000 | **82.5%** |
| システムプロンプト | 6,000 | 14.6% |
| プロジェクト情報等 | 720 | 1.7% |
| CLAUDE.md | 480 | **1.2%** |
| 合計 | 41,200 | 100% |

Claude Code の既定はMCPツール定義が **deferred(名前のみ常駐)** である。34,000tok が丸ごと載っているのは既定から外れた構成の結果であり、削減余地がここに集中している。MCPツール呼び出しは週合計53回(github 41 / postgres 12)で、**残り7サーバは0回**。

### cache creation の構造:12リクエスト(全体の5.6%)が週の創出量の56%

| 分類 | 件数 | cache creation | 週creationに占める割合 |
|---|---|---|---|
| セッション初回(不可避の起動費) | 5 | 210,000 | 7.8% |
| **中断によるTTL失効後の再構築** | 6 | **1,031,000** | **38.1%** |
| `/model` 切替による全面失効 | 1 | 274,000 | 10.1% |
| キャッシュヒットした増分書込(202件) | 202 | 1,189,000 | 44.0% |
| 合計 | 214 | 2,704,000 | 100% |

### TTLレーンの確定:このレーンは5分であり、1時間ではない

環境仕様から直接決まる。認証は `ANTHROPIC_API_KEY`(従量課金)で、キャッシュ関連の環境変数・設定は既定のまま。APIキー/Bedrock/Vertex 系のTTLは既定 **5分**で、1時間はサブスクリプションの自動適用か `ENABLE_PROMPT_CACHING_1H=1` によるオプトインでしか得られない(`references/evidence.md`)。**このレーンは5分である。**

ログ側の裏付け:**8分の中断(金15:02)で cache read が 0 に落ちている**。この時刻に `/model`・MCP着脱・permission mode変更はいずれも無い(操作ログで確認)ので、TTL失効以外に説明が付かない。22分(木11:26)、41分(水12:48)も同方向。

したがって **「1時間離れなければ大丈夫」はこのレーンでは成立しない**。この1点を取り違えると、以降の閾値がすべてずれる。

### `/model` は離席と切り分けて特定できる

水15:21 のリクエストは**直前から2分**しか経っていないのに cache read = 0、creation 274,000。2分はTTL内なので離席では説明できない。15:20 の `/model`(sonnet-4.6 → opus-5)によるキャッシュキー変更が原因と一意に特定できる。**キー1回の打鍵で 274,000 tok**、これは水曜のcreation 755,000 の36%である。

### キャッシュが効いていた202リクエストは既に健全 — 削る余地はない

cache read > 0 の202リクエストの増分書込は 5,886 tok/req、平均プレフィックス 165,347 tok に対して**実効再書込率 3.6%**。metsuke実測の「5分未満=2.6% / 5〜60分=2.7%」と同じ桁で、普段の作業中の挙動に問題はない。この比率は creation ÷ プレフィックスから直接出ており、リクエスト間隔の推定を一切必要としない。本人の「使い方は変えていないつもり」という自己認識は**正しい**。

### 変わったのは使い方ではなくセッションの持ち越し時間

| セッション | 稼働時間 | 平均プレフィックス | 単位/req |
|---|---|---|---|
| S1(月) | 4h18m | 81,081 | **11,842** |
| S5(金) | 6h35m | 105,484 | 29,360 |
| S4(木) | 7h50m | 183,415 | 35,102 |
| S3(水) | 8h05m | 198,372 | 39,060 |
| S2(火) | 8h35m | 221,600 | 37,125 |

S1とS2は**同じ作業(API改修とその続き)**である。にもかかわらず S2 は 1リクエストあたり S1 の **3.1倍**かかっている。差を作っているのはタスクの性質ではなく、1本のセッションを何時間持ち越したか。全セッションが S1 の効率で回っていれば週合計は 2,534,000 単位、つまり**現状の38%**で済んだ計算になる。

ただしこの「38%」は上限側の見積もりとして扱うこと。S1は半日で終わっており、**セッション長とその日の作業量が交絡している**(軽い日だったから安かった可能性を排除できない)。S1/S2 が同一タスクである点は交絡をかなり弱めるが、証明ではない。確度が高いのは「平均プレフィックスがセッション時間に単調に連動している」という関係の存在であって、38%という水準そのものではない。

### 同じ中断でも、遅い時間ほど高い

木曜の同一セッション内:11:26(22分中断・セッション序盤)= 88,000 に対し、15:04(124分中断・セッション終盤)= 246,000。**2.8倍**。再構築費は中断の長さではなく、そのとき抱えている会話の大きさで決まる。

### 金曜の `/compact` は禁じ手が2つ重なっている

金14:35 は「92分の休止明け」かつ「引数なし `/compact`」。(a) 休止明けなのでキャッシュが冷えており、要約リクエストが圧縮前の会話全体を高い単価で読む(この非キャッシュ読み込みはログの221,000には含まれていないので、実費はこれより大きい)。(b) 引数なしなので決定事項・却下案・未解決TODOを選んで残せない。なお圧縮自体は効いており、直後15:02の再構築は 57,000 まで落ちている(221,000 → 57,000)。つまり「会話が大きすぎた」という認識自体は正しく、**手段の選択だけが間違っている**。

### CLAUDE.md 編集3回について

セッション中の CLAUDE.md 編集はキャッシュを壊さない(この3回は無害)。ただし**反映もされない** — 次の `/clear`・`/compact`・再起動から有効になる。週内に `/clear` が0件なので、編集は翌日のセッション開始時(と金曜の`/compact`時)に初めて効いていた。「直したのに効かない」と感じていたならこれが正体である。

## 2. 支配要因

**中断によるTTL失効後の全プレフィックス再構築。週の cache creation の 38.1%(1,031,000 tok)、モデル全体の 19.2%(1,288,750 単位)を占める、単一最大の「手を打てる」要因。**

「支配要因」は**削減可能な**要因の中の最大という意味で使っている。単純なシェアでは増分書込(22.1%)の方が大きいが、これは実効再書込率3.6%で既に健全域にあり、削る余地が構造的に無い(§1)。シェア順ではなく「シェア × 削減可能性」で選んでいる。

要因別シェア(6,720,000 単位に対して):

| 要因 | 単位 | シェア | 削減可能性 |
|---|---|---|---|
| 読取(cache read)合計 | 3,340,000 | 49.7% | 部分的(会話サイズ次第) |
| └ うちMCPツール定義由来(202×34,000) | 686,800 | 10.2% | **高(構成変更のみ)** |
| └ うちCLAUDE.md由来(202×480) | 9,696 | 0.14% | 実質ゼロ |
| 増分書込(202件) | 1,486,250 | 22.1% | **なし(3.6%で健全。手を出さない)** |
| **TTL失効後の再構築** | **1,288,750** | **19.2%** | **高(セッション境界の設計)** |
| `/model` 切替 | 342,500 | 5.1% | **高(行動コストゼロ)** |
| セッション初回 | 262,500 | 3.9% | 起動固定費の削減分だけ |

補足として、この支配要因は**2つの乗数**で膨らんでいる。

1. **TTL 5分レーン**:昼休みも打ち合わせも全部TTLを超える。中断の回数そのものは制御できない。
2. **会話サイズ**:再構築費は会話サイズに比例する。木曜の 88,000 vs 246,000 がその証拠。

制御可能なのは (2) だけである。したがって打ち手は「離席を減らす」ではなく「**離席時に抱えている会話を小さく保つ**」になる。

なお、**単体で最も大きい削減可能な項目は MCPツール定義**である。読取10.2% + 全面再構築12回への同梱7.6% = **17.8%(1,196,800 単位)**が、9サーバ中7サーバが1度も呼ばれないまま毎リクエスト計上されている。支配要因(19.2%)にほぼ並ぶ規模でありながら、行動変更を一切要さない。

**チームのSlackの仮説について**:「毎リクエストCLAUDE.mdが送られている」という観察は正しいが、規模を2桁取り違えている。同じプレフィックスの中で MCP定義 34,000tok は CLAUDE.md 480tok の **71倍**である。CLAUDE.md を半分に削っても週の請求は **0.13% しか動かない**(§4に計算)。正しい標的は同じ場所にある別のものである。

## 3. 行動変更表(優先度つき)

優先度は「削減効果 ÷ 行動コスト」で並べた。P1〜P3は行動を変えずに設定・タイミングだけで効く。

| 優先度 | 場面 | いまの行動 | 変える行動 | 期待効果の桁 |
|---|---|---|---|---|
| **P1** | MCP常駐(9サーバ・全定義34,000tok・うち7サーバは週0回) | 全定義がプレフィックスに常駐 | ①まず既定の deferred(名前のみ常駐)へ戻せるか確認 → ②未使用7サーバを無効化 → ③github を `gh` CLI へ(ツール定義コストゼロ)。すべて**タスク境界で**実施(ツール定義変更は全面失効を招くため) | 起動固定費 41,200 → 8,000〜14,000tok。**週 700,000〜1,050,000 単位減(全体の11〜16%)** |
| **P2** | 昼休み・長い打ち合わせの前(火13:10・水12:48・木15:04・金14:35 の4件) | 開いたまま離席し、戻って続行 | 離席前に「決定事項・未解決TODO・次の一手・関連ファイルパス」を書き出させてセッションを終了。戻ったら新セッション+その要点で再開 | 再構築 268k/151k/246k/221k → 各 ~50k。**creation 686,000tok減 = 857,500単位(全体の12.8%)** + 下流リクエストのプレフィックス縮小による読取減 |
| **P3** | モデルを変えたくなったとき(水15:20) | セッション途中で `/model` | セッション冒頭に決めて固定。変えるなら `/clear` か新セッションを挟む。残作業が小さいなら**切り替えずに今のモデルで終える** | **274,000tok = 342,500単位(5.1%)の全損を根絶**。金額ベースではOpus-5単価分さらに大きい。行動コストはゼロ |
| **P4** | 1日1セッションを終業まで持ち越す(火〜金) | 8時間前後を1本で通す | 半日、または明確なサブタスクの切れ目で `/clear`。**目標は月曜の形**(4時間強・平均プレフィックス80k前後) | 読取が全体の49.7%。平均プレフィックスを 165k → 100k にできれば **約1,300,000単位(19%)減**。ただしP5とcounter-metricsで監視すること |
| **P5** | 会話が膨らんだと感じたとき(金14:35) | 休止明けに引数なし `/compact` | 休止明けの `/compact` は禁止(新セッション+要点再指定へ)。同一タスクを続けるなら**中断前の切れ目で**「決定事項・未解決TODO・却下案とその理由を残せ」と指示を付けて打つ | 圧縮前会話をフル単価で読む分の回避 + 判断構造の保全(手戻り防止) |
| P6 | 失敗したアプローチを捨てるとき | 該当操作なし(週内 `/rewind` 0件) | 経路を捨てるだけなら `/rewind`(キャッシュ済みプレフィックスへの切り戻しで `/compact` より安い)。同じ問題で2回訂正したら `/clear` + 依頼の書き直し | 迷走時の `/compact` 誤用の予防 |

**効果は足し算にならない。** 各行の数値は**すべて現状(6,720,000単位)を基準に単独で測った値**であり、直前の施策を適用した後の残高に対する値ではない。特に **P2 と P4 は同じ行動を粒度違いで書いたもの**で、加算できない — 火13:10・水12:48 の昼休み前にセッションを畳めば、それがそのまま半日分割になる。単純合計(約50%)は正しくないので、意思決定には「P1 + (P2かP4のいずれか) + P3」の組み合わせで見積もり直すこと。

**実施順序の注意**:P1はツール定義の変更なので、実行した瞬間に全面失効が起きる。週の終わりか、`/clear` 直後の何も走っていないタイミングで一度だけ行うこと。

**起動固定費の換算式(今週の形での再利用可)**:プレフィックスから X トークン削ると、`202 × X × 0.10 + 12 × X × 1.25 = 35.2X` 単位が週あたり浮く。X=26,000(未使用7サーバ相当と仮定)なら 915,200単位。X=480(CLAUDE.md全削除)なら 16,896単位。この係数35.2倍が、起動固定費だけが全セッションに効く理由である。

**P1はP2の効果を増やさない**(直感に反するので明示しておく)。P2の削減量は「再構築費 − 新規開始費」= `(起動固定費 + 会話) − (起動固定費 + 引き継ぎメモ)` で、**起動固定費の項が打ち消し合う**。火13:10 の削減は起動固定費が41,200でも10,000でも約218,000で変わらない。P1の利得はP1の行に既に計上済みであり、二重に数えないこと。

## 4. やらないこと

### 4-1. CLAUDE.md の削減(チーム提案。効果は誤差)

- 現状 480tok = 起動固定費の1.2%、平均プレフィックス165,347tok の **0.29%**
- 週を通した実効コストは 16,896 単位 = 全体の **0.251%**
- 半分に削った場合の削減は **8,448 単位 = 全体の 0.126%**
- 請求は 1.700倍 → **1.698倍** にしかならない。P1(11〜16%)との効果差は **約108倍**
- 週内3回の編集もキャッシュを壊していないので、コスト観点で気にする必要はない

削らない理由はもう一つある。CLAUDE.md を小さく保つ本来の目的は指示の埋没防止であって、コストではない。内容が肥大していて指示が埋もれているなら、それはコスト施策ではなくドキュメント設計の課題として別建てで扱うべきである(`docs-for-ai` の領分)。**「コストのために削る」を出発点にすると、消してはいけない指示を消す**。

### 4-2. 1時間TTLへのオプトイン(この構成では逆効果)

一見すると 22分・41分・8分の中断を吸収できて有利に見えるが、書込単価が ×1.25 → ×2.00 に上がるため、**この週の形では赤字**になる。

- 1時間TTLで救えるのは60分未満のギャップ3件のみ:57,000 + 88,000 + 151,000 = **296,000 tok**(週creationの 10.95%)
- 68分・92分・124分の3件は1時間TTLでも救えない
- 損益分岐:`(W − A) × 2.00 ≤ W × 1.25` より **A ≥ 0.375W = 1,014,000 tok** が必要。実際は 296,000 で **3.4倍足りない**
- 試算:書込 (2,704,000 − 296,000) × 2.00 = 4,816,000 単位(現状 3,380,000)。読取微増を含め週合計 6,720,000 → **約 8,186,000 単位(+21.8%)**

この開発者の中断は「長すぎて1時間TTLでも救えない」側に偏っており、一方で書込総量が大きいため単価上昇のペナルティを全量で受ける。**P2(セッションを畳む)を先に打つべきで、TTLオプトインはその後に再評価する**(再評価条件は §5)。

**この結論が依存している仮定**:`ENABLE_PROMPT_CACHING_1H=1` が全書込に一律 ×2.00 を適用するものとして計算している。もしブレークポイント単位でTTLを混在させられる(長寿命の起動固定費だけ1時間、変動の大きい会話末尾は5分)なら損益は変わりうる。通常と逆の「やらない」結論を出しているので、実施前にこの1点だけは自環境で確認すること。

### 4-3. 連続作業中の細切れ `/clear`・こまめな節約

202リクエストの実効再書込率は 3.6% で、metsuke実測の健全域と同じ桁。ここを削っても取れる量は無く、文脈を捨てすぎて再説明・再読・手戻りが増える方が高くつく。**ヘッドルームは使い切ってよい予算**であり、コンテキスト残量の節約自体は目的ではない。

### 4-4. 中断そのものを減らす努力

5分TTLレーンでは昼休みも打ち合わせも全部TTLを超える。中断回数を行動で管理するのは行動コストが節約額を上回る。制御すべきは中断の有無ではなく、**中断時に抱えている会話のサイズ**(P2・P4)である。

### 4-5. 「1.7倍」の原因を今週のログだけで断定すること

先月同時期のログが手元に無いため、増加の因果は**確定できない**。今週の構造から説明できる候補は (a) 火〜金の1セッション長時間化、(b) 水曜のOpus-5切替、(c) MCP 9サーバ常駐、の3つだが、どれが「先月から変わった点」かは不明である。本人が「使い方は変えていない」と述べており、かつ連続作業中の挙動が健全であることを踏まえると、**行動ではなく構成(MCPサーバの増加)か稼働時間の増加を疑うのが筋**。§5に確認手順を置いた。

## 5. counter-metrics と見直し条件

### 施策は一度に1つ

P1(構成変更・行動コストゼロ)→ P3(タイミングのみ)→ P2(行動変更あり)→ P4(行動変更あり・副作用リスク大)の順で、1つずつ入れて前後比較する。P2とP4を同時に入れると、効果も副作用も切り分けられなくなる。

### counter-metrics(悪化したら緩める)

| counter-metric | 悪化のサイン | 対応 | 主に監視すべき施策 |
|---|---|---|---|
| 再説明の往復回数 | セッションを畳んだ後、前提の説明し直しが**週3回**を超える | 手放しの書き出し粒度を上げる(結論とファイルパスを必ず含める)。それでも改善しなければ切る頻度を下げる | P2・P4 |
| 同一ファイルの再読量 | 新セッションのたびに同じ大量読み込みが走る | 要点書き出しに「読んだファイルと結論」を含める | P2・P4 |
| 手戻り率 | 圧縮・分割後に却下済みの案が再提案される | `/compact` 指示に「却下案と理由を残せ」を明示。P4の分割粒度を粗くする | P4・P5 |
| 平均プレフィックス | 100k を下回っても再説明が増えない | 分割が効いている。それ以上は削らない(過剰最適化) | P4 |
