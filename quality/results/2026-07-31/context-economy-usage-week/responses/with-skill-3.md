ファイル変更・設定変更は行っていません。以下はすべて提案です。

## 0. 読み方(集計の単位)

金額はログから復元できないため(理由は §1 の「答えられないこと」)、以下では**コスト加重トークン**で比較します。

- コスト加重値 = cache creation × 1.25 + cache read × 0.10
- キャッシュ書込は入力単価の×1.25(5分TTL)、読取は×0.10([Anthropic Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md) 2026-07-30参照)
- 単価はsonnet-4.6を1とした相対量。水15:20以降のopus-5区間は単価が違うため、この区間は**過小評価**になっています(§2で補正)

週合計 = 2,704,000 × 1.25 + 33,400,000 × 0.10 = **6,720,000 コスト加重tok**。以下の「シェア」はすべてこの分母に対する比率です。

## 1. 現況サマリ

### 1-6. このログでは答えられないこと

**「請求1.7倍」の内訳はこのログからは分解できません。** 欠けているのは4つ。

4. 先月同期間の同じ集計(比較の基準がない)

その上で、**最初に検証すべき仮説を1つ**挙げます。

> **仮説: MCPツール定義の「全定義ロード」設定が今月入った。**
> これは非既定の状態です(既定はdeferred)。この設定変更は9サーバ分34,000tokをプレフィックス床に足すため、**214リクエスト全部の読取と、12件の全面再書込の両方**を同時に押し上げます。全体を一律に持ち上げるタイプの変化で、「使い方は変えていないのに全体が高い」という症状に最も整合します。

先月分の同じ集計表(特にセッション初回リクエストの `/context` 内訳)と突き合わせれば、これは1回のクエリで白黒がつきます。計測項目の整備は `llm-cost-observability` の領分です。

## 2. 支配要因

> **冷えたプレフィックスの全面再書込。**
> 214リクエスト中12件(5.6%)が cache read = 0 で、そこに cache creation の **56.0%**(1,515,000 tok)、コスト加重で **28.2%** が集中している。

内訳は 離席後の復帰6件 19.2% / `/model` 途中切替1件 5.1%(opus単価のため下限)/ セッション初回5件 3.9%。連続作業中の202件は再書込率3.4%で既に健全なので、**削れる余地は事実上この12件にしかありません。**

**MCPツール定義34,000tokは、独立した要因ではなく上の12件すべてを膨らませる乗数です。**

- warm読取側: 202 × 34,000 = 6,868,000 tok(全cache readの20.6%)
- 冷えた書込側: 12 × 34,000 = 408,000 tok(全cache creationの15.1%)
- 合計 1,196,800 コスト加重tok = **全体の17.8%**

つまり毎リクエスト運ばれ、かつ冷えるたびに書き直されているものの正体が、この34,000tokです。

補足2点。

- **`/model` の274,000tokはopus-5でトークン化された値**です。Claude 4.7以降のモデルは新トークナイザで同一テキストが約30%多くトークン化されるため([Anthropic Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md) 2026-07-30参照)、sonnet-4.6でトークン化された他行と直接は比べられません。金額はopus-5とsonnet-4.6の入力単価比を r とすると **274,000 × 1.25 × r コスト加重tok相当**。r が大きければこの1リクエストが週の単一項目として最大になります。
- **支配要因(コストの大きさ)と最優先施策(コスト ÷ 実行コスト)は別物です。** §3ではMCPを先頭に置いていますが、これは離席より安いからではなく、**設定を戻すだけで行動を1つも変えずに済むから**です。行動変更を要する施策は、それ自体が費用(思い出すコスト・再説明の往復)を持つので後ろに回します。

なお `/usage` や `/context` の水位ではなく、**opus-5を使うべき作業だったかどうか**の判断は `delegation-economy` の領分です。本診断は「どのモデルでもいいから冒頭で決めて固定せよ」までしか言いません。

## 4. やらないこと

### 4-1. CLAUDE.mdを半分に削る(チームSlackの提案)

**やめてください。効果は全体の0.13%で、請求は動きません。**

| | tok | コスト加重tok | 全体シェア |
|---|---|---|---|
| CLAUDE.md 480tok(read 202回 + write 12回) | 102,720 | 16,896 | **0.25%** |
| これを半減した場合の節約 | 51,360 | 8,448 | **0.13%** |
| 参考: MCPツール定義 34,000tok | 7,276,000 | 1,196,800 | **17.8%** |

Slackの直感「毎リクエストCLAUDE.mdが送られている」は**事実として正しい**。間違っているのは対象です。

- 毎リクエスト送られているのは事実だが、キャッシュヒット時の単価は入力単価の**0.10倍**で、平均プレフィックス165,000tokに対して480tokは**0.29%**
- 同じ「毎リクエスト送られているもの」の中に、**71倍大きい34,000tokのMCPツール定義**が座っている
- 削るなら480tokではなく34,000tokのほう。しかもMCP側は削るのではなく**既定のdeferredに戻すだけ**で済み、9サーバの機能はどれも失われない

CLAUDE.mdを小さく保つ理由はコストではなく指示の埋没防止です。480tokは200行未満の目安に対して十分小さく、削る理由がありません。

### 4-2. 1時間TTLへのオプトインを最初に打つ

**やらないのではなく、順序を後にします。** 期待できる上限が離席分の3割しかないためです。

離席6件を、1時間TTLで救えるものと救えないもので分けると:

| 間隔 | cache creation | 1時間TTLで救えるか |
|---|---|---|
| 8分(金15:02) | 57,000 | ○ |
| 22分(木11:26) | 88,000 | ○ |
| 41分(水12:48) | 151,000 | ○ |
| **小計** | **296,000** | **離席分の29%** |
| 68分(火13:10) | 268,000 | × |
| 92分(金14:35) | 221,000 | × |
| 124分(木15:04) | 246,000 | × |
| **小計** | **735,000** | **離席分の71%・どのTTL設定でも救えない** |

オプトインの効果の上限は 296,000 × 1.25 = 370,000 コスト加重tok = **全体の5.5%**。一方、離席前の手放し(P1)は残り71%の735,000tokに効きます。**大きいほうから潰すのが順序です。**

なお1時間TTLは書込単価が×1.25→×2.00に上がるため、オプトインは無条件に得ではありません。損益分岐は「救える再書込 × 1.25 > 単価が上がる書込量 × 0.75」。この式に自環境の実測値を入れて判定してください — ただし判定するのはP1実施後の再計測データで、いまの数字ではありません。

### 4-3. 節約目的の細切れ `/clear`

連続作業中202件の再書込率は**3.4%**で、実測ベンチマーク(2.6〜2.7%)と同水準です。ここを短く切っても節約できる量は誤差で、代わりに再説明の往復・同一ファイルの再読・手戻りが増えます。ヘッドルームは使い切ってよい予算です。`/clear` はタスクの切れ目と「同じ問題で2回訂正したとき」に打つもので、節約のために打つものではありません。

### 4-4. 8分・22分の中断への行動介入

22分の会議延長や8分の割り込みは事前に予測できません。予測できない中断に手放し手順を強いると、行動コストが節約額(2件で145,000tok = 全体の2.7%)を上回ります。この帯域は §4-2 の設定側で吸収するか判定するもので、規律で解くものではありません。

### 4-5. 金額ベースのdeprioritize判定(いまは適用不能)

このログには出力トークンとリクエストごとのモデルタグがないため、「TTL失効の再構築費が1日$5未満なら離席施策を優先しない」という金額基準は**適用できません**。代わりにトークン基準を使います。

> 離席起因の再構築 1,031,000 tok = 全cache creationの **38.1%**。目安の10%を大きく超えるため、**deprioritizeしません。**

先月比較と請求明細が揃った時点で、金額基準でも再判定してください。

## 5. counter-metricsと見直し条件

### 5-1. 施策の投入順序

**一度に1つずつ**入れます。同時に入れると、どれが効いたかが分からなくなります。

1. 週1(P0): MCPをdeferredへ + 未使用7サーバ無効化。**行動を変えないので、これ単独で1週間分の効果が測れます**(先週比でcache readが約20%落ちれば想定どおり)
2. 週2(P0): モデル固定ルール。イベント数を数えるだけで検証可能(セッション途中の `/model` が0件か)
3. 週3〜4(P1): 離席前の手放し + 休止明けの新セッション + 指示付き `/compact`

### 5-2. counter-metrics(悪化したら緩める)

| counter-metric | 測り方 | 悪化のサイン | 対応 |
|---|---|---|---|
| 再説明の往復回数 | 新セッション開始後、前セッションの前提を説明し直したターン数 | **週3回超** | 手放しの書き出し粒度を上げる(決定事項・却下案・ファイルパスを必須項目にする)。それでも減らなければセッションを切る頻度を下げる |
| 同一ファイルの再読量 | 新セッション冒頭で読み込むファイルの合計トークン | 手放し1回あたり **50,000tok超** | 要点書き出しに「読んだファイルのパスと、そこから得た結論」を含めさせ、再読自体を不要にする |
| 手戻り率 | 圧縮・セッション切替の後に、却下済みの案が再提案された回数 | **1件でも発生** | `/compact` 指示に「却下案と理由を残せ」を明示。金曜の引数なし `/compact` 以降に発生していないか、まず遡って確認する |

### 5-3. 再計測と見直し条件

**2週間後に同じ集計を取り直す**(同じ集計ツール、同じ表形式)。見るのは3つ。

1. **起動固定費**: 41,200 → 15,000tok以下になっているか。なっていなければMCP設定が反映されていない
2. **cache read = 0 のリクエスト件数**: 12件 → 5件(セッション初回のみ)に近づいているか。セッション初回以外が残っていれば、どのイベントに紐づくかを個別に見る
3. **離席起因のcache creationのシェア**: 38.1% → 何%か

見直し条件:

- 離席起因が**全cache writeの10%未満**まで落ちたら、離席施策は維持コストのほうが大きくなる。以降はdeprioritizeし、「長時間離席の前の手放し」だけルールとして残す
- 逆に10%以上残っていたら、残っているギャップの長さ分布を見て §4-2 の損益分岐式を再評価する
- counter-metricsのいずれかが上表の閾値を超えたら、**その施策だけを緩める**(全部やめない)
- 起動固定費は**月1回**再計測する。MCPサーバは増えるものなので、放置すると34,000tokの状態に戻ります

### 5-4. 施策を入れずに済む場合
