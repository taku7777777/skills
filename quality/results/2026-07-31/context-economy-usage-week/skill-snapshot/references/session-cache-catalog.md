## 1. 診断表: 支配要因の特定(ステップ1)

| 症状(ログの見え方) | 支配要因 | 打ち手 |
|---|---|---|
| cache creationのスパイクが離席・休止直後の初回リクエストに一致 | TTL失効後の再構築 | 離席前の手放し / 長TTLオプトイン / 新セッション再開 |
| /model・/effort・MCP着脱イベントの直後にスパイク | キャッシュキー変更による全面失効 | 変更をセッション冒頭・/clear直後へ寄せる |
| creationが毎ターン高止まり | プレフィックスが壊れている(設定の揺れ・ツール定義の変化) | 直近の設定変更を巻き戻して切り分ける |
| cache readが単調増加しプロンプト単価を押し上げる | 会話の肥大(kitchen sink) | タスク境界で/clear、切れ目で指示付き/compact |
| セッション初回リクエストが常に大きい | 起動固定費(MCP定義・大型スキル) | 棚卸しチェックリスト(本書5節)へ |
| どれにも該当しない・内訳が取れない | 計測不備 | 分析より先に計測を直す(`llm-cost-observability`) |

## 2. 判断表: /clear・/compact・/rewind(ステップ2)

| 状況 | 操作 | 理由 |
|---|---|---|
| 別のタスク・案件へ移る | /clear | コストゼロで新規開始。compactの要約費用も不要な文脈も持ち越さない |
| 同一タスクを続けるが文脈が肥大 | 切れ目で指示付き/compact | 残す情報(決定事項・TODO・却下案)を自分で選ぶ。auto-compactはタスク途中で発火し選べない |
| 失敗したアプローチの経路を捨てる | /rewind | キャッシュ済みプレフィックスへの切り戻しで、要約リクエストが要るcompactより安い |
| 同じ問題で2回訂正した | /clear+依頼の書き直し | 文脈が失敗アプローチに汚染されている。依頼の再設計は `prompt-economy` |
| TTL超の休止から戻った直後 | 新セッション or サマリ再開 | 休止後のcompactは要約のため全履歴をフル単価で読む最悪手 |

## 3. 判断表: キャッシュを壊す操作・壊さない操作(ステップ4)

プレフィックスは tools → system(プロジェクトコンテキスト含む)→ messages の3層で、上位を触ると下位が全部落ちる。「全面失効」と「一部の層の作り直し」を混ぜない。

全面失効 = tools層以下がすべて落ちる(次の1ターンが全履歴の再書込になる)。能動的な操作ではこの2系統だけ:

- キャッシュキーの変更: /model でのモデル切替(planモードの出入りでモデルが変わる設定を含む)・effort/思考予算の変更・fast mode などリクエストヘッダを変える機能のオン/オフ
- ツール定義の変化: MCPサーバの接続/切断(定義がプレフィックスにロードされる構成のとき。既定のdeferredなら無傷)・プラグイン着脱・ツール丸ごとのdenyルール追加

一部の層だけ作り直す(全面失効とは別扱い):

- エージェント本体のアップグレード → システムプロンプトが変わるので system 層以下。巨大セッションへの復帰は最も高い1ターンになる
- /compact → 会話層のみ。システムプロンプト層は再利用され、プロジェクトコンテキストはディスクから再読込(未変更ならヒット)。ただし要約リクエスト自体が圧縮前の会話全体を読むため、会話が大きい・キャッシュが冷えているほど高い

壊さない(誤解されがちなもの):

- リポジトリのファイル編集(履歴末尾への追記のみ)
- CLAUDE.mdのセッション中編集 — 壊さないが**反映もされない**(次の/clear・/compact・再起動から有効)
- permission modeの切替(planモードの出入りでモデルが変わる設定は例外 — 上記「キャッシュキーの変更」に該当)、スキル・コマンドの起動、サブエージェント起動
- /rewind(キャッシュ済みプレフィックスへ戻るだけ)

途中で切り替えたくなったときの判断(問題は切替の是非ではなくタイミング):

- 残作業が小さい → **切り替えずに今のモデル・設定のまま終える**。再書込費が残作業での単価差の節約を上回る
- 残作業が大きい → /clear か新セッションを挟んでから切り替える。そのまま切り替えると全損+新キーで再書込の二重払い
- 安いモデル・低effortの活用自体は否定しない。冒頭で決めて固定するのが最も安い

補足: キャッシュは実質マシン+作業ディレクトリ単位。worktree・別マシンは別キャッシュ。操作一覧の最新版と例外は `evidence.md` 記載の公式ドキュメントで確認する。

## 4. チェックリスト: 離席前・再開時(ステップ3)

前提(1回だけ): 自分のレーンのTTLを確定する。認証方式で5分〜1時間と12倍違い、これを取り違えると閾値ごと間違える。短TTLレーンで中断が多いなら、離席運用より先に長TTLへのオプトインを打つ(書込単価が上がるため、TTL内に2回以上読まれる使い方が損益分岐)。

離席前(自問は1つ: 「これからTTL以上離れるか」):

- [ ] TTL内に戻る見込み → 何もしない(過剰最適化しない)
- [ ] TTL超の見込み → 進捗の要点(決定事項・未解決TODO・次の一手・関連ファイルパス)を書き出させ、セッションを区切る
- [ ] 判断がつかない(会議が延びるかもしれない)→ 書き出しだけして開いたままにする。戻れれば続行、戻れなければ書き出しが新セッションの種になる

再開時:

- [ ] TTL内 → そのまま続行
- [ ] TTL超+セッションが小さい → 続行してよい(再構築費が小さい)
- [ ] TTL超+セッションが大きい → 新セッション+要点再指定、またはサマリからの再開。そのままの続行と休止後compactを避ける
- [ ] エージェントをアップグレードした直後 → 巨大セッションへの復帰が最も高い1ターンになると見込み、新セッションを優先する

## 5. チェックリスト: 起動固定費の棚卸し(ステップ5)

効果の大きい順に確認する:

1. [ ] MCPサーバ: 直近2週間で使っていないサーバを無効化する。ツール定義がdeferred(名前のみ常駐)か全定義ロードかを確認する
2. [ ] CLI代替: gh・aws・gcloud等、同等CLIがあるMCPはCLIへ置き換える(ツール定義コストゼロ)
3. [ ] 大型スキル: 常駐サイズではなく呼び出し頻度を見る — 1回のロードが常駐の桁違いになりうる
4. [ ] 巨大出力の前処理: テスト・ログの生読みはhookで絞る(依頼側の設計は `prompt-economy`)
5. [ ] CLAUDE.md: コスト理由では削らない(常駐は平均プレフィックスの1%未満)。指示の埋没が問題なら `docs-for-ai` で内容を再設計する

## 6. テンプレート: セッション運用ルール(チーム向け)

```markdown
# セッション運用ルール

## 切る
- タスク・案件の切替時は /clear(履歴の持ち越し禁止)
- 同じ問題で2回訂正したら /clear + 依頼の書き直し

## 離れる
- TTL以上離れるときは要点を書き出して区切る。TTL内なら何もしない

## 戻る
- 休止明けの巨大セッションは新セッション+要点再指定。休止後の /compact は禁止

## 固定する
- モデル・effort・MCP構成はセッション冒頭に決める。変更は /clear 後

## 見直す
- counter-metricsが悪化したらルールを緩める。月1回、起動固定費を再計測する
```

## 7. counter-metricsとdeprioritize基準(ステップ6)

| counter-metric | 悪化のサイン | 対応 |
|---|---|---|
| 再説明の往復回数 | /clear・手放しの後に前提の説明し直しが頻発 | 手放しの書き出し粒度を上げる / 切る頻度を下げる |
| 同一ファイルの再読量 | 新セッションのたびに同じ大量読み込みが走る | 要点書き出しにファイルパスと結論を含める |
| 手戻り率 | 圧縮後に却下済みの案が再提案される | compact指示に「却下案と理由を残せ」を追加する |

deprioritize基準: 対象の損失(再構築費)が利用費全体に対して十分小さいなら、施策自体をやめる。「打つべき施策がない」は正当な結論(目安の数値は `evidence.md`)。
