# context-economy 適用例

## 題材(架空シナリオ)

フリーランスのバックエンド開発者。EC事業者の改修案件(案件A)と自社CLIツールの開発(案件B)を並行し、Claude Codeを朝9時から夜まで開きっぱなしにしている。APIキー運用(従量課金)。打ち合わせ・昼休み・保育園の送迎で1日3〜5回の中断がある。今月の利用費が先月の約2倍になり、「CLAUDE.mdを削るべきか」と相談してきた。

## 入力(依頼と手元にあるもの)

「Claude Codeの使い方は変えていないのに費用が倍になった。セッションの使い方を見直したい。CLAUDE.mdのダイエットも効くなら教えて」。手元には直近3日分のトランスクリプト(トークン内訳つき)と、打ち合わせ・離席の時間帯メモ。MCPは全定義ロード(名前のみのdeferredではなく、接続8サーバ分のツール定義がプレフィックスに載っている)。

## 各ステップでの判断

- **ステップ1(現況とキャッシュ健全性)**: 3日分のcache creationを時系列に並べると、スパイク9回中8回が「20分以上の中断のあとの最初のリクエスト」に一致(最大296,000tok)。連続作業中の再書込率は3%未満で健全。起動固定費は約33,000tokで、内訳はシステムプロンプト等6,150tok、MCPツール定義26,500tok(接続8サーバ、実際に使うのはgithub 3,700tokとpostgres 2,900tokの2つだけ)、CLAUDE.md 350tok。支配要因を「離席起因のキャッシュ再構築」と特定(大原則2)
- **ステップ2(セッション境界)**: 案件Aと案件Bを同一セッションで交互に扱っていた(kitchen sink)。案件切替時の /clear を必須化。auto-compact任せをやめ、コンテキスト警告が出たら切れ目で「決定事項と未解決TODOと却下案を残せ」と指示付き /compact に変更(大原則5)
- **ステップ3(離席と再開)**: APIキー運用のため既定TTLは5分で、20分の中断でも再構築が走っていた(レーン別の現行値は `evidence.md`)。「1時間離れなければ大丈夫」が成り立たないレーンだと確定させ、まず1時間TTLへオプトインして20〜60分の中断を吸収する。その上で昼休み・送迎(1時間超)の前は進捗の要点をNOTES.mdへ書き出させて区切る。オプトイン後の30分程度の離席は何もしない(大原則6 — 過剰最適化しない)
- **ステップ4(壊す操作の排除)**: 「軽い作業になったら/modelで下位モデルへ」という夕方の習慣が、切替のたびに全損再書込を起こしていた(大原則4)。モデルはセッション冒頭に決め、途中で変えたくなったら /clear 後に切り替えるルールへ
- **ステップ5(起動固定費)**: 未使用の6 MCPサーバを無効化してツール定義を26,500→6,600tokへ、さらにGitHub操作を `gh` CLIへ移してgithubサーバも外し、常駐MCPをpostgres 2,900tokだけにした。起動固定費は33,000→9,400tok。CLAUDE.md 350tokは削らない — 常駐コストは平均プレフィックスの0.2%程度で誤差(大原則3)。「ダイエットしても請求は動かない」と数値で回答し、内容の整理は別件として `docs-for-ai` の領分へ
- **ステップ6(効果確認)**: 施策は「離席前の手放し」から1つずつ。counter-metricは「再開後に前セッションの内容を再説明した往復回数」。2週間後にcache creationの時系列で再計測し、スパイクが消えていれば以降の離席施策はdeprioritize

## 成果物(抜粋)

```markdown
# セッション運用診断書(3日分ログより)

## 1. 現況サマリ
- 起動固定費 約33,000tok(システムプロンプト等6,150 / MCP定義26,500 / CLAUDE.md 350)
- cache creationスパイク9回中8回が20分以上の中断後の初回リクエスト(最大296,000tok)
- APIキー運用でキャッシュTTLは既定5分。20分の中断でも全面再書込が起きている
- 連続作業中の再書込率3%未満 — 普段の使い方は既に効率的

## 2. 支配要因
離席起因のキャッシュ再構築。ただし境界は「1時間」ではなくこのレーンのTTL(5分)。会話の長さ・CLAUDE.mdは主要因ではない。

## 3. 行動変更表
| 場面 | いまの行動 | 変える行動 | 期待効果の桁 |
|---|---|---|---|
| 20〜60分の中断 | 毎回再構築 | 1時間TTLへオプトイン | 中断あたり再構築1回分の解消 |
| 1時間超の離席前 | 開いたまま離席 | 要点書き出し→セッションを区切る | 再構築スパイク1回分/離席 |
| 案件の切替 | 同一セッション続行 | /clear | 不要な履歴再送の停止 |
| モデル変更 | 途中で/model | 冒頭に決定。変更は/clear後 | 全損再書込の根絶 |
| コンテキスト警告 | auto-compact任せ | 切れ目で指示付き/compact | 判断構造の保全 |
| MCP | 8サーバ常時接続 | postgres 1本+gh CLI | 起動固定費 33,000→9,400tok(約7割減) |

## 4. やらないこと
- CLAUDE.mdの削減(350tok=平均プレフィックスの約0.2%。効果は誤差)
- 離席の全廃(行動コストが節約額を上回る。オプトイン後の1時間以内の中断は対象外)

## 5. counter-metricsと見直し条件
- 再開後の再説明往復が週3回を超えたら「手放し」の書き出し粒度を上げる
- 2週間後にスパイクを再計測。再構築費が十分小さければ以降の離席施策はdeprioritize
```

## この適用で変わったこと

- cache creationスパイク: 3日で8回 → 2週間後の同条件3日で1回(送迎が急に延びた1件のみ。20〜60分の中断分は1時間TTLオプトインで消えた)
- 起動固定費: 約33,000tok → 約9,400tok(MCP棚卸しとCLI代替。内訳はシステムプロンプト等6,150+postgres 2,900+CLAUDE.md 350)
- 月次費用はおよそ4割減。CLAUDE.mdには触れておらず、削減の大半は離席運用とMCP棚卸しで説明できた
- 再説明往復は週1回に収まり、counter-metric上の手戻り増なし
