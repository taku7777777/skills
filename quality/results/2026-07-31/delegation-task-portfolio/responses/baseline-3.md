# ヤドリギ バックエンドチーム — タスク別モデル/実行形態の割当設計

ファイルの変更はしていません。以下は設計案と運用の取り決め案です。

---

## 0. 結論

月$2,400 → **基本ケース $814 / 悲観ケース 約$1,090** で目標の$1,200以内に収まります。設計相談(#6)とレビュー(#5)は**モデル階層を下げずに**目標達成できます。

削減の主因は「安いモデルに替えること」ではなく、次の3つです。

1. **effortが全タスクmax固定** — 定型作業に最上位の推論深度を払っている
2. **全タスクをメインセッションで実行** — 直前の作業の文脈が次の作業の入力トークンに乗り続ける。40万行のログを読んだ直後のセッションでPRレビューをすれば、そのログ代を再度払う
3. **決定的なツールで済む処理をモデルにやらせている** — デッドコード検出、リネーム、ログの一次絞り込み、flakyの再現試行

したがって割当表は「モデル階層」だけでなく **effort** と **実行形態(コンテキスト隔離)** を同格の列として扱います。この3つ目の列が今回いちばん効きます。

### 各割当の根拠

**#1(Sonnet 5 / medium / headless)**
「既存エンドポイントの構成をそのまま踏襲」+「CIがOpenAPIスキーマとの整合を検査」。仕様が既存コードに書かれており、正解が機械判定できる。この2条件が揃っているタスクは中位階層+中程度のeffortで足ります。誤りのコストが「CIが赤くなる」で止まるので、フロンティア階層で予防する必要がない。headlessにするのは、9件/月それぞれが互いに無関係で、文脈を共有する価値がないため。

**#2(Haiku 4.5 / headless / スケジュール起動)**
毎週月曜・3リポジトリという定型スケジュール実行で、8分のテストスイートが正解判定を担う。lockfileのバージョン更新は実質的に分類タスクで、最小階層で足りる。ただしCHANGELOGに破壊的変更が書かれている場合は判断が要るので、そこだけSonnet 5に昇格させます。Haiku 4.5は`effort`パラメータ非対応なので指定しないこと(指定するとエラーになります)。レイテンシ非依存なのでBatch APIで更に半額にできます。

> **Haiku 4.5のコンテキスト上限に注意(#2/#4共通)**: 他の階層が1Mコンテキストなのに対し、**Haiku 4.5は200K / 最大出力64K**です。#2は1リポジトリずつ実行すれば収まりますが、3リポジトリ分の差分を1セッションにまとめると溢れます。#4も複数ファイルにまたがるリネームと型チェック/テスト出力全文を同時に載せると危険です。したがって**「200Kに収まらない見込み」自体をSonnet 5への昇格条件に加えます**(破壊的変更ノートの有無と並ぶ第2の昇格トリガー)。ここを曖昧にすると、上限超過による再実行がそのまま§6-1で計測したい「手戻り」として現れ、単価$2.5の見積りが崩れます。

**#3(前処理 + サブエージェント隔離)**
これは推論の問題ではなく**コンテキスト量の問題**です。設計の要点は2つ。

- 40万行はripgrep/jq/集約スクリプトで「エラー種別ごとの件数・時刻分布・代表スタックトレース」まで落とす。ここはモデルを一切使わない
- 絞り込んだ数百行はサブエージェントに渡し、**ログ本文をメインセッションのコンテキストに入れない**。返ってくるのは所見だけ。これで「1回のログ調査が、その後のセッション全体の入力トークンを膨らませる」現象が止まる

統合・仮説の絞り込みだけOpus 5/highに載せます。フロンティア最上位が要る作業ではありません。

**#4(静的解析 + Haiku)**
デッドコード検出は静的解析ツールの仕事で、モデルの仕事ではない。リネームもLSPのリファクタ機能で決定的に実行できる。モデルに残るのは「この検出結果は本当に消してよいか」の判断だけで、しかも型チェックとテストが後段で検証する。$18/件はこの内容に対して過大です。

**#5(階層据え置き、effortとコンテキストのみ削る)** — ここが設計の要点
「質を落としたくない」という制約を文字通り守り、**モデル階層は変えません**。削るレバーは2つだけ。

- **max → xhigh**: xhigh はコーディング/エージェント用途で推奨される設定で、max は過剰思考に陥りやすく投入トークンに対して逓減しやすい、とされています。つまりこの変更は「質を下げてコストを下げる」ではなく「レビュー用途に合った設定にする」変更です。とはいえ主張は検証で裏を取るべきなので、§5に判定手順を置きます
- **1PR = 1 headlessセッション**: 現状はメインセッションで日6件を連続処理しているため、6件目は1〜5件目の差分・議論を全部入力に載せています。PRごとに独立実行すれば、この重複が消えます。レビュー基準とアーキテクチャ資料はプロンプトキャッシュに載せる(Opus 5系は512トークン以上でキャッシュ可、キャッシュ読みは約0.1倍)

最終判断はリードが実施する体制は維持します。これが実質的な人間の検証ゲートで、モデル側を薄くする根拠になっています。

**#6(完全据え置き)**
料金計算・在庫引当のトレードオフ判断は、間違えたときのコストが最も高く、機械的な検証手段がありません。月2件で$50、新予算の6%です。**ここを削る合理性はゼロ**なので、Fable 5 / max / メインセッションのまま触りません。

実行形態についても意図的にメインセッションのままにします。他の行ではコンテキストの蓄積が「無駄な重複入力」ですが、設計相談では蓄積そのものが成果物です。前段で却下した案、その却下理由、既存実装の制約といった議論の積み上がりが次の判断の質を決めるので、headless化やサブエージェント隔離は**支払っている価値そのものを捨てる**変更になります。#5とは削減レバーの向きが逆である点に注意してください。

**#7(Haiku 4.5 / Batch API)**
コミット履歴からの要約という、最も単純な生成タスク。一次ドラフトは`git log`で機械的に作れます。週1回でレイテンシ要件がないのでBatch API(50%引き)が使えます。

**#8(スクリプト + Opus 5 / xhigh)**
「再現手順が不明なことが多い」= 探索が必要ということなので、**ここを安易に安くしません**。「テストなんだから軽いはず」という直感は誤りです。ただし削れる部分はある: 「テストを200回回して失敗パターンを収集する」という反復はスクリプトの仕事で、モデルのトークンを使うべきではありません。モデルは収集済みのデータから仮説を立てる部分に集中させ、反復回数に上限を設けて暴走を防ぎます。

## 5. 品質不可侵ラインの明文化

制約として与えられた#5/#6について、運用ルールとして固定します。

**不可侵**

- #6(設計相談): モデル階層・effort・実行形態のいずれもコスト理由で変更しない
- #5(PRレビュー): **モデル階層をコスト理由で引き下げることを禁止**。効率化はコンテキスト設計・キャッシュ・CIへの機械的指摘の移譲のみで行う

**#5のeffort変更(max → xhigh)の検証手順**

これは唯一「質に触りうる」変更なので、思い込みで入れず、判定してから入れます。

1. 直近のマージ済みPR 30件を、max と xhigh の両方でレビューさせる
2. リードが両方の出力を、どちらがどちらか分からない状態で読む
3. 判定基準: **xhighで漏れた指摘のうち、リードが「マージ前に指摘されるべきだった」と判断するものが0件**であること
4. 1件でも該当すればmaxに戻し、#5の削減は「セッション分割+キャッシュ」だけで実施する(この場合#5は約$5.0/件・$630/月、合計約$1,028で、それでも目標内)

つまり **effort変更が却下されても目標は達成できる**設計になっています。ここは安全側に倒せます。

## 6. 運用の取り決め

### 6-1. 計測 — 最優先で埋める穴

現状「差し戻し・手戻りの計測はしていない」ため、**上記の割当はすべて検証不能な仮説です**。安い階層に落としたタスクが2回差し戻されれば、置き換えたはずのフロンティア1回より高くつきます。計測なしに割当表を運用するのは、コストが下がったかどうかを判断できないまま品質を賭けることです。

**記録する項目(1実行 = 1レコード)**

| 項目 | 内容 |
|---|---|
| タスク種別 | #1〜#8 または「未分類」 |
| モデル / effort / 実行形態 | 実際に使われた値 |
| コスト | API換算額 |
| 差し戻し回数 | CIが落ちた回数 + 人間が指示し直した回数 |
| 完了までの総コスト | 初回 + 全再実行の合計 |
| 品質への不満(自己申告) | 差し戻しには至らなかったが、出力が不十分で人間が黙って手直し・補完したか(有無のみ) |

**最後の行が計測設計上の要点です。** CIの失敗と明示的な指示し直しだけを数えると、「モデルの出力が微妙だったので実行者が黙って自分で直した」ケースが完全に見えません。これは階層を下げたときに最初に現れる劣化の形で、しかも数字上は「差し戻し0回」として成功に計上されます。有無のフラグ1つでよいので、週次の入力欄に含めてください。ここが抜けていると、主指標は**降格のコストを構造的に過小評価します**。

**主指標は「初回コスト」ではなく「成功1件あたりの実効コスト = 完了までの総コスト ÷ 成功件数」** とします。初回コストだけを見ると、安い階層に落として差し戻しが増えた場合に改善したように見えてしまいます。

**ベースライン取得**: 割当を変更する前の2週間、現行構成(Fable 5 / max / メインセッション)で上記を記録します。比較対象がなければ後の判定ができません。

### 6-2. ロールバックトリガー

| 対象 | 条件 | アクション |
|---|---|---|
| 全行共通 | 差し戻し率がベースライン+10ポイントを **2週連続** 超過 | その行のモデル階層またはeffortを1段戻す |
| 全行共通 | 実効コストが移行前を上回った | その行を移行前の構成に戻し、原因を分析してから再挑戦 |
| #5 | モデルが見落とした指摘が原因の本番障害が **1件** 発生 | 即座にmax effortへ復帰。以降の変更はリード承認制 |
| #5 | リードが追加する重大指摘の件数が、ベースラインの1.5倍を2週連続超過 | effortをmaxに戻す |
| #3 | 一次調査から原因特定までのリードタイムが悪化 | 前処理の絞り込み条件を見直す(モデル階層は先に触らない) |

「2週連続」を条件にしているのは、単週のばらつきで振り回されないためです。逆に#5の本番障害は1件で即トリガーにします。

### 6-3. 昇格・降格ルール

- **昇格(その場での判断)**: 安い階層で2回失敗したら、その実行は1段上に上げる。判断は実行者の裁量でよく、事後承認も不要
- **初回から昇格**: 実行者が「これは定型ではない」と判断した場合、初回からフロンティア階層を使ってよい。定型と非定型の見分けは人間の判断が最も安い
- **降格(定期的な見直しのみ)**: 実効コストと差し戻し率の実測データがある行のみ、月次レビューで降格を検討する。データのない行は降格しない

「安いほうを試して失敗したら上げる」を摩擦なくできるようにしておくことが、割当表が守られるかどうかを決めます。上げるのに承認が要ると、実行者は最初から最上位を使います(それが現状です)。

### 6-4. 既定値の管理

- チーム標準の既定値は **Claude Opus 5 / effort high / メインセッション** とする(現状のFable 5 / max から変更)
- 既定値はリポジトリの設定ファイルに記述してバージョン管理下に置く。**設定ファイルの変更は本設計の合意後、別途実施する**(今回のファイル変更は行っていません)
- 各タスク種別の割当は、スラッシュコマンドまたは定型スクリプトとして固定し、実行者が毎回モデルとeffortを選ばなくてよい状態にする。**手動で選ばせる運用は必ず既定値に戻ります**(直近4週で誰も切り替えなかった実績がその証拠です)

### 6-5. コンテキスト衛生の規約

- headless実行はタスクごとに新規セッション。使い回さない
- 大量出力を生む処理(ログ、大きなdiff、テスト出力全文)はサブエージェント経由にし、メインセッションには結論のみ返す
- メインセッションを1日中使い回さない。タスクの切れ目でセッションを切る
- プロンプトキャッシュの規約: レビュー基準・アーキテクチャ資料などの安定した内容を先頭に固定し、**日付・PR番号・実行IDを先頭に入れない**(接頭辞が1バイト変わるとそれ以降のキャッシュが無効化されます)。キャッシュヒットは`cache_read_input_tokens`で毎回確認する

### 6-6. ログの取り扱い(#3)

予約プラットフォームの障害ログには氏名・連絡先・予約情報が含まれ得ます。

- ログをモデルに渡す前に、前処理スクリプトでPIIをマスクする。これは前処理をスクリプト化する副次的な利点でもあります
- Fable 5はゼロデータ保持(ZDR)環境では利用できず、30日のデータ保持設定が必要です。組織のデータ保持方針とログの取り扱いが両立するか、導入前に確認してください

### 6-7. レビューサイクル

| 頻度 | 内容 | オーナー |
|---|---|---|
| 週次 | 差し戻し率とコストのダッシュボード確認。ロールバックトリガー該当の有無 | 当番制(週替わり) |
| 月次 | 割当表の見直し。降格候補の検討、未分類タスクの分類 | リード |
| 四半期 | モデルラインナップと価格の変更を反映した割当表の再設計 | リード |

- **未分類タスクの扱い**: 既定値(Opus 5 / high / メインセッション)で開始し、月次レビューで#1〜#8のいずれかに分類するか、新しい行を追加する
- **オーナーを決めておくこと**: 「チームで見る」は誰も見ないことになります

## 8. 残るリスクと未確定事項

正直に書いておきます。

1. **単価の推定はすべて未実測**: 観測値は3件(#4/#2/#7)のみで、金額の7割を占める#5と#3の単価は頻度からの逆算です。§6-1の計測が入るまで、$814という数字の精度は「桁が合っている」程度に見てください
2. **Sonnet 5の導入価格が2026-08-31で終了**: 現在は$2/$10の導入価格、その後$3/$15になります。Sonnet 5を使う#1と#3(抽出サブエージェント部分)で **+$50前後/月**。目標内に収まりますが、9月以降の予算表は更新が必要です
3. **#5の件数が伸びると余裕が消える**: 現在126件/月で$416。人数増や開発速度向上で200件/月になれば$660で、目標余裕の大半を使います。コスト目標を「月額」ではなく「PR1件あたり」で持つほうが、チーム規模の変化に対して頑健です
4. **effort変更の効果は用途依存**: max → xhigh の削減率0.7〜0.8倍は一般論で、レビューという用途での実測ではありません。§5の検証でコストも同時に測ってください
5. **サブエージェント/headlessの学習コスト**: 直近4週で誰も使っていない機能です。移行初期は試行錯誤で一時的にコストが上がる可能性があります。週1–2のベースライン期間に、1人が代表して手順を固めてから展開するのが安全です
6. **「安い階層で回す」文化が定着するかは設定の固定にかかっている**: 既定値をFable 5 / maxにしたまま「必要に応じて切り替えて」と伝えても、直近4週の実績どおり誰も切り替えません。§6-4のスラッシュコマンド化・既定値変更は、この設計の中で最も地味で最も重要な項目です
