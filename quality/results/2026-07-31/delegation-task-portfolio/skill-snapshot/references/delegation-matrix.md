# 委任マトリクス設計カタログ(判断表・チェックリスト・テンプレート)

SKILL.md ステップ1〜5の詳細展開。本カタログは委任マトリクスを実際に書き下ろすときの作業手引きであり、SKILL.md と乖離したら SKILL.md の原則を正とする。単価・倍率・製品挙動の具体値は本カタログに書かない(`evidence.md` を正とする)。

## 目次

- タスク棚卸しテンプレート
- モデル階層の判断表
- effort・thinkingの判断
- 実行形態の判断表
- 二重払い診断チェックリスト
- counter-metricsテンプレート
- 委任マトリクス完全テンプレート

## 1. タスク棚卸しテンプレート(ステップ1)

| タスク | 頻度 | 検証可能性(機械判定できるか) | 判断の新規性 | 出力量 | 現状の実行形態 | 現状のモデル・effort |
|---|---|---|---|---|---|---|

記入の規律:

- **検証可能性**: テスト・lint・型・CI・スキーマ検証など、人間の目なしで合否が出るか。「レビューすれば分かる」は機械検証ではない
- **判断の新規性**: 前例のないトレードオフ判断を含むか。既存パターンの踏襲・定型変更は低
- **出力量**: 生成するコード・文書の物量。出力単価は入力の5倍という桁関係のため、大量生成タスクほど階層差が金額に直結する
- 頻度が高いものから埋める。月1未満・低リスク・短時間のタスクは割当設計の投資対象にしない(設計コストが節約を上回る)
- 棚卸しと同時にモデル別コスト構成比(`/usage` 等)を取り、「どのタスクが最上位モデルを消費しているか」を対応づける

## 2. モデル階層の判断表(ステップ2)

3問を順に通す:

1. **失敗を機械が検出できるか?** No → 上位階層+人間レビューを残す。Yes → 次へ
2. **判断の新規性は高いか?**(前例のない設計トレードオフ・多段推論)Yes → 上位。No → 次へ
3. **出力量が大きいか?** Yes → 最安階層で試す価値が最大(階層差が物量に乗算される)

| タスク特性 | 階層 | 必須の添え物 |
|---|---|---|
| 機械的・検証可能(リネーム、依存更新、フォーマット、定型追加、デッドコード削除) | 最安(Haiku級) | テスト・lint・型・CI green を通過条件に |
| 標準的な実装・バグ修正 | 中位(Sonnet級) | 再現テスト先置き+green |
| 設計判断・多段推論・レビューの最終判断 | 上位(Opus/Fable級) | 人間の承認(ゲート設計は `harness-engineering`) |
| 探索・調査(結果は要約だけ使う) | 最安〜中位+サブエージェント | 出力契約(§二重払い診断) |

運用の規律:

- **迷ったら一段安い側で試し、counter-metricsで戻す。** 高い側から始めると下げる動機が生まれない。ただし顧客影響が直接出るタスク・不可逆操作を含むタスクは一段高い側から始める
- 割当は「階層+検証手段」のペアが1単位。検証手段の欄が空の割当は書かない
- 同一タスク種別でも「生成は安価モデル・判定は上位モデル(または人間)」の分業は正当(Writer/Reviewer分離)
- 単価比の現在値・改定予定・トークナイザ差(モデル間で同一テキストのトークン数が変わる)は `evidence.md` を確認してから金額比較する

## 3. effort・thinkingの判断(ステップ2)

| 状況 | 設定 |
|---|---|
| 機械的タスク・定型変更 | effort最低・thinking off(thinkingは出力単価で課金される) |
| 標準的な実装 | effort既定 |
| 設計判断・難デバッグ | effort高・thinking on |

- **モデル・effortの切替はセッション冒頭か `/clear` 直後に限定する。** 途中切替はキャッシュ全損(メカニズムは `context-economy`)
- 「effortを上げれば品質が上がる」はタスク依存。機械的タスクでは思考トークンが増える割に成果物はほぼ変わらない(変わるなら検証手段が拾う)

## 4. 実行形態の判断表(ステップ3)

| 形態 | 使う条件 | コスト特性 | やめる・避ける条件 |
|---|---|---|---|
| メインセッション直 | 数往復で終わる/文脈の引き継ぎが必要 | 本体キャッシュが効く | 大量読み込みで本体コンテキストが溢れる |
| サブエージェント | 検索・ログ・大量ファイル読みの外部化 | 独立コンテキスト=初回キャッシュゼロ・TTL短側固定(`evidence.md`) | 数往復で終わる小タスク(起動費>分離の便益) |
| headlessファンアウト | 同型変更の多数展開(移行・一括修正) | 並列・使い捨てコンテキスト | 2〜3件の磨き工程でプロンプトが安定しない |
| Batch API | リアルタイム不要な分類・要約・一括評価 | 半額・キャッシュ割引と重畳 | 対話的な修正・即時性が必要 |
| agent teams | 真に並行な役割分担が必要 | トークン倍率が大きい(`evidence.md`) | 1セッションで直列にできる作業 |

- サブエージェントには `model:` を明示指定する。組み込みサブエージェントの既定モデルは製品バージョンで変わる(`evidence.md`)— 「前は安いモデルだったはず」を信用しない
- headlessの磨き工程: 2〜3件実行 → 失敗を分類 → プロンプト改良 → 10件で確認 → 全量。改良なしの全量再実行は失敗を全量に複製する
- 外部エージェント(Codex等)への委譲を形態に含める場合、委譲先の実行コストと規約ファイル(AGENTS.md等)の有無を確認し、総コスト比較に含める

## 5. 二重払い診断チェックリスト(ステップ4)

- [ ] サブエージェントの報告受領後、本体で同じファイル群をReadしていないか(トランスクリプト・セッション記録で確認)
- [ ] サブエージェント込みの指示単価を、本体単独でやった場合の見積りと比較したか
- [ ] サブエージェント費をspawn元の指示に合算して評価しているか(時間帯の重なりでなく、spawn連鎖=因果で帰属する)
- [ ] 委任の出力契約は「本体が再読せず次の行動へ進める」形か(結論+根拠のファイルパス・行番号+検証結果)
- [ ] 複数のサブエージェントが同じ調査を重複実行していないか(役割の重複)
- [ ] 数往復で終わるタスクをspawnしていないか(メインセッション直の方が安い)
- [ ] 外部エージェント委譲分のコストを総コストに含めたか

対策の優先順: 出力契約の構造化 → 役割重複の統合 → 小タスクのspawn廃止。**fan-out数の一律制限は最後の手段**(委任自体は正当であり、上限は二重払いを直さない)。

## 6. counter-metricsテンプレート(ステップ5)

| 指標 | 定義 | データソース | 悪化時の行動 |
|---|---|---|---|
| 差し戻し率 | 安価モデルの成果物を上位モデル・人間がやり直した割合(タスク種別ごと) | PRレビュー記録・再依頼の記録 | 該当種別のみ一段上へ。2週間後に再測定 |
| 再依頼率 | 同一指示の再実行・訂正往復の率 | セッション記録 | 依頼文起因なら `prompt-economy`、能力起因なら階層を上げる |
| 検証ゲート一発通過率 | 安価モデル成果物のCI初回green率 | CIログ | 検証手段の不足なら `harness-engineering` へ |

規律:

- **counter-metricsのない割当表は運用しない**(過剰最適化を検出できない)
- 悪化1種別を全体の反証にしない。部分的に巻き戻し、他の割当は維持する
- 高品質が必要なタスクは高価でよい。USD/taskの最小化を単独KPIにしない
- 計測の実装(指標定義・収集・レビュー周期)は `llm-cost-observability` の領分

## 8. アンチパターン集

| アンチパターン | なぜ損か | 修正 |
|---|---|---|
| 既定モデルのまま全作業 | 最上位モデルの常用は他のどの節約も飲み込む(構成比が過半になる) | 構成比を確認し、タスク種別で割当を設計 |
| 「品質最優先=常に最上位」 | 機械的タスクでは品質差がほぼ出ない一方、単価差は確実に乗る | 品質はタスクに紐づける。効くタスクにだけ温存 |
| 検証手段なしの階層引き下げ | 差し戻しで節約が逆転 | 割当は検証手段とペアでのみ |
| 委任結果のファイル読み直し | 二重払い(委任費+本体の再読費) | 出力契約の構造化 |
| 数往復の小タスクをspawn | 初回キャッシュゼロの起動費>分離の便益 | メインセッション直 |
| 磨きなしの全量ファンアウト | 失敗プロンプトを全量に複製 | 2〜3件で磨いてから展開 |
| fan-out数の一律制限で対処 | 委任自体は正当。二重払いは残る | 二重払い診断チェックリストから |
| 外部委譲で「安くなった」と報告 | 計測範囲外へ逃げただけの可能性 | 委譲先込みの総コストで比較 |
| セッション途中のモデル・effort切替 | キャッシュ全損で次ターンが最も高くなる | 冒頭か `/clear` 直後に固定(`context-economy`) |
| 節約額の単独KPI化 | 過剰最適化(手戻り増)を検出できない | counter-metricsとセットで運用 |
